## R1 — Custody: can anyone but the owner get value out of a sealed vault, or an emptied vault survive?

**No. I could not break the pairing, and I tried the shapes the prompt names.**

- **The pairing.** SEAL walks forward from its own index for a top-level `burn_vault` binding asset (account 0) *and* owner (account 2); BURN walks backward for a top-level `open_for_redemption` binding the same pair. Both indices match the actual account structs (verified against `BurnVault`/`OpenForRedemption`). The instructions sysvar is address-pinned and sees top-level instructions only, so a burn hidden in a CPI is invisible to SEAL and an open reached by CPI reports the wrapper's index to BURN. WR.1–WR.4 exercise exactly this with a real forwarding program.
- **A thawed vault leaving a transaction unburned.** I specifically attacked the mid-transaction transfer: `[open(alice), transfer vault→bob, sweep, burn]`. The burn's owner check reads the asset's *current* owner (bob) and fails `NotTheOwner`; naming bob as the burn's owner breaks SEAL's match (it bound alice). Either way the transaction fails atomically and the vault stays sealed. There is no ordering in which the thaw survives.
- **The emptiness proof.** I recomputed the classic token-account offsets: delegate COption tag at 72..76, state at 108, delegated amount at 121..129, close-authority tag at 129..133 — all correct in both BURN loops. Token-2022 accounts with extensions are refused by the exact-165 length check in both loops; a bare 165-byte Token-2022 account has no extensions and no hidden balance, so accepting it is sound. The reserve loop requires *both* ATA derivations per mint declared; the Token-2022 derivation for a classic mint cannot exist as a token account (the ATA program refuses `IncorrectProgramId` — measured by the probe), and a raw System account at that address is skipped by the owner check. The second loop re-applies the same three authority checks to every declared PDA-owned token account (the round-24 fix), and refuses declared live Core assets.
- **The rate limit.** It is exactly a rolling window over a 64-entry ring of i64 timestamps: the cap-th most recent entry must be at least `redeem_window_secs` old, so at most `cap` redemptions land in any window of that length ending at a redemption. `live = minted_total − burned_total − bare_burns_retired` is read from pinned configs; underflow is impossible (each counter counts distinct minted vaults). The ring write only persists if the whole burn lands.

**R1 verdict: the seal holds.**

## R1s — The sweep helper

**(a) Nobody but the owner can make it move value.** Called directly it needs the asset-signer PDA's signature, which only Core can produce; through Core, `ExecuteV1` approves only `authority == owner` on the pinned binary (SR.5, SR.5a refuse a stranger and an owner-added transfer delegate with `NoApprovals`; SR.5b pins the collection authority to MINT's off-curve PDA; SR.5c/5d are the both-ways control). While frozen, Core refuses Execute (0x9, 3.7), so the helper is unreachable outside a redemption. The one plugin route that could widen this (AgentIdentity) cannot be added by an owner (R24.1a) — this remains Core-version trust, correctly carried as limit 40.

**(b) The pair list.** Same source twice: the first pair transfers and closes; the second `read_token` sees a System-owned closed account and fails `IllegalOwner` — SR.12a/SR.12b pin that the refusal is the closed-source read, not the first guard. A source that is also a destination forces `signer == dest`, refused. A wSOL source is an ordinary 165-byte classic account: transfer then close (rent to the owner). A delegate on a source cannot be planted by a stranger (Approve needs the PDA's signature) and does not block an owner transfer. A frozen source reverts the redemption (SR.14) — the documented limit-28 class. A non-ATA destination is fine (only mint-and-owner are checked). The destination wallet being another vault's asset-signer is the owner moving their own money — not a vulnerability. Odd account count: refused (SR.7). Zero pairs: the lamports-only sweep (SR.13).

**(c) Destination checks.** The destination is chosen by whoever builds the transaction, and (a) establishes that is the owner. A System transfer to a non-existent destination is refused — atomically, nothing moves, the owner re-signs; the canonical destination (the fee-paying owner) always exists. This is documented as a client obligation (item 50, round 25 D9). Not a security hole.

**(d) The lamport sweep.** `signer.lamports()` is read after the pairs; token transfers and closes do not touch the PDA's lamports, so it is the live balance at execution. Nothing between the sweep and the burn can credit the PDA except the redeemer's own instructions (which would fail their own burn). Core's BurnV1 does not credit the asset-signer (measured fact 4). BURN's `lamports == 0` sees exactly what the sweep left.

**(e) Interaction with the emptiness proof.** A closed account is System-owned with zeroed data, so BURN's reserve loop skips it for the right reason (owner is not a token program). The prior-transaction rule is sufficient: after the page creates the three reserve ATAs, every account a stranger can create at a derivable address either already exists (the sweep names it and moves the live balance) or cannot be created (Token-2022 ATA for a classic mint; raw accounts at ATA-program PDAs). A stranger *can* create a **non-ATA** classic token account owned by the vault PDA (create_account at a fresh address + initialize needs no PDA signature) and deposit into it — the sweep can name it only if the page finds it via `getTokenAccountsByOwner`, and BURN will never see it undeclared. That is destruction, not blocking, and it is exactly accepted limit 44 as written. **No account a stranger can create blocks a redemption; the residual is the documented destruction of undeclared holdings, which currently has no preventive control because the page (item 50) is not built.**

**(f) Does it fit.** S8.0's 1,061 bytes is a landed serialization of claim + open + helper(3 pairs) + burn with the owner as payer; the +52/+96 for compute-budget and a separate payer are offline arithmetic (see INFO-3 below). A fourth reserve cannot exist (`MAX_RESERVE_MINTS = 3`, written once). The in-line monthly's pool account is already in the measured shape (claim and burn both carry it). The 23-byte margin claim is arithmetically consistent.

**(g) Evidence.** I looked for an arm that cannot fail or fires for the wrong reason. SR.12b is a genuine discriminator. SR.4a's exact-lamports reconciliation (stranger's gift + prior wallet balance + closed-account rent + asset-rent delta − fee, cross-checked against the helper's own log line) can fail in every leg. SR.5e verifies the refused attempts preserved balances, owner and seal. The helper's deployed bytes are proven identical across `dist/`, `target/deploy/` and the fresh localnet rebuild (`build-mainnet.sh` N6 repair) — and it has no `localnet` feature at all, so the tested bytes are the shipped bytes by construction. **I found no vacuous arm in SR.*.**

## R2 — The community pool

**The invariant "the pool always holds at least ceil(owed)" holds, and I verified it analytically, not just against P.32:**

- `credit`: `owed += floor(avail·10¹²/w)·w ≤ avail·10¹²`, and the pool's balance already includes `avail` (credit moves no tokens), so `ceil(owed_new) ≤ ceil(owed_old) + avail = balance`.
- `claim`: each payment subtracts exactly `pay·10¹²` from `owed` and `pay` sats from the balance; since `ceil(S − pA) = ceil(S) − p` for integer p, the invariant is preserved *exactly*, even across multi-vault batches and duplicate records (a duplicate pays 0: the first settlement leaves `pending mod 10¹² < 10¹²`).
- `retire` (all three flavors) only ever subtracts from `owed`, never from the balance.
- `distribute` refuses `PoolShort` before crediting; `monthly_inline` uses `saturating_sub` and no-ops on a shortfall.

**Counters under every ordering.** `pending_count`/`pending_this_epoch` are consistent under request → distribute → join, request → retire same-epoch, request → distribute → retire later-epoch (the `request_epoch == dist_epoch` guard correctly skips the already-reset `pending_this_epoch`), and double-retire is refused. F21.1 exercises the two hard orderings. **Liveness:** every gate (`JoinWaitingFirst`, `BoostsExpireFirst`, the frozen-pool deferral) has a permissionless exit (join, expire, forfeit-and-redeem), so nobody can make distributions or redemptions impossible for others; the launch-tick path correctly refuses the burn route (`NoActiveVaults`) so a first activator cannot open the door alone. SPEC's weaker wording on pre-join revenue (round 24 W11) is the true rule and is what the code does; item 55 covers the unsplit-revenue edge at its measured cost.

## R2b — The $CBOB boost

**A boost earns exactly N distributions.** Bought at epoch E (after any in-instruction monthly), `end = E+N`; the distribution that advances the epoch to E+N is the Nth it earns, and `advance_epoch` moves its ring count to `boosts_due` at exactly that point; the `BoostsExpireFirst` gate then blocks the N+1th until expiry, and expiry reweighs at the accumulator the Nth left. BO.21/BO.21a/BO.35/BO.35a measure both orderings of boost-plus-distribution in one transaction. **Nothing earned is lost or gained on a weight change:** `reweigh` moves the owed share to `carry` and restarts the debt at the new weight, so `owed_of` is invariant across boost, expiry, claim normalization and retire — I re-derived this by hand for every transition and it is exact. **The ring and totals agree past epoch 64:** the ring is a per-epoch *count*, so two live boosts sharing an end epoch (possible; see LOW-1) aggregate correctly, and the 260-epoch host test drives four wraps through the program's own functions against a record-derived model, including wrapped early-retire and due-retire branches (BO.38/BO.38a land the wrapped early-retire on chain). No record can be expired twice (`boost_weight == 0` guard), early (`dist_epoch < boost_end_epoch` skip), or never (the gate plus the crank). A vault whose token account is gone cannot block distributions: `expire_boosts` needs only records. The one-sided `BoostTermsMoved` rule and the owner-only check (current owner read from the asset bytes at execution) are as ruled and measured (BO.26/BO.30/BO.33).

**LOW-1 — a comment asserts a false invariant about the boost ring (the code is safe).**
*Construct:* `programs/cbob-vault-mint/src/lib.rs`, the `BOOST_RING` comment ("a boost may last at most `BOOST_RING - 1` distributions, so two live end epochs never share a slot") beside `boost_vault`'s `c.boost_expiring[i] += 1`.
*What is gained:* nothing today. Two live boosts **can** share an end epoch (buy at epoch 10 with N=10 and at epoch 15 with N=5: both end at 20) — the ring handles it correctly because it is a per-epoch *count*, not a per-boost slot. The comment's stated impossibility is false, and the true constraint (the slot must not be processed between purchase and end) actually permits N=64 and breaks at 65, so 63 is one stricter than needed. The risk is a future maintainer "correcting" the ring into per-boost slots, or raising the bound on the comment's reasoning, during a change to code that is otherwise frozen forever.
*Evidence if I am right:* the host test `the_boost_ring_wraps_exactly_against_a_model` already models per-epoch counts (multiple buys land in one slot), which contradicts the comment while confirming the code.
*Fix:* rewrite the comment to state the real constraint. Comment-only; no code change.
