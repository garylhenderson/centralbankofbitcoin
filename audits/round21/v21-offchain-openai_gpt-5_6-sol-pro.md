# Audit findings

## R1 — Commitment scheme

### CRITICAL — A public deterministic deck plus Bank-controlled mint ordering lets the Bank allocate every valuable level

**Exact construct**

- `deck_seed` is published when `commit_deck` succeeds.
- `bank/deck.mjs` deterministically derives the complete deck from that seed.
- Every `mint_vault` requires the Bank’s signature.
- The assigned card is selected by the global `minted_total` index.

The commitment fixes cards to indices. It does **not** bind customers to indices before the Bank learns the cards.

**What a cheating Bank controls**

The Bank needs only its ordinary mandatory mint co-signing key. It does not need:

- the admin key,
- a validator,
- a manipulated blockhash,
- a false Merkle root,
- or a second seed.

After the public seed reveals that index `i` is Level V and index `i+1` is Level I, the Bank signs the favoured customer’s transaction first and delays or refuses the other transaction. The next successful mint consumes index `i`.

This directly contradicts the stated purpose of preventing the Bank from “handing the good cards to whoever it liked.” A randomly shuffled, publicly known queue does not solve allocation fairness when one party controls admission to that queue.

**Gain**

The Bank can direct high-emission levels to itself, affiliates, or selected customers. Since levels determine recurring cbBTC distributions, this is an ongoing transfer of customer revenue, not cosmetic NFT rarity.

**Checkable evidence**

A validator test can demonstrate this without modifying any program:

1. Commit a valid seed and matching deck.
2. Find adjacent indices with different levels.
3. Prepare valid mint transactions for Alice and Bob.
4. Submit them in Alice/Bob order and record the resulting levels.
5. Repeat on a fresh validator with Bob/Alice order.

The recipient of the valuable card follows the Bank-selected transaction order.

**Fix**

Bind claimants to positions before the deck becomes known. Examples:

- Commit an ordered list of eligible owner pubkeys before revealing entropy, then require index `i` to mint to the committed owner at `i`.
- Use a permissionless FIFO registration account whose entries are fixed before seed publication.
- Use per-owner randomness derived from entropy plus a precommitted owner identity, with a quota-preserving assignment protocol.
- Use an independently operated randomness/allocation service with an on-chain verifiable result.

Merely hiding `deck_seed` until mint time does not suffice if the Bank can still choose transaction ordering after learning each result.

---

### CRITICAL — `commit_deck` still accepts an arbitrary root unrelated to the program-derived seed

**Exact construct**

```rust
let seed = hashv(&[&salt, &bh]).to_bytes();
c.deck_seed = seed;
c.deck_root = root;
```

No instruction verifies:

```text
root == deckRoot(buildDeck(level_caps, seed))
```

The comments explicitly acknowledge this, but the security consequence remains active.

**What a cheating party must control**

To create an off-seed deck:

- the MINT admin signs `commit_deck` and chooses the arbitrary root;
- the Bank signs mints and controls their order.

If those roles collude, they can commit any quota-respecting deck and mint proofs against it. The seed stored on chain is then decorative.

Even without Bank ordering, the admin can select a root that does not correspond to the published seed. Detection after commitment does not revert the root, repair already-minted levels, or recover misdistributed cbBTC.

**Gain**

Arbitrary level allocation under a root that the program accepts as authoritative.

**Checkable evidence**

Add a test that:

1. Performs a valid `commit_seed`.
2. Derives the program’s resulting `deck_seed`.
3. Builds `root_bad` from an unrelated seed.
4. Calls `commit_deck(root_bad, correct_salt)`.
5. Mints using a proof under `root_bad`.

The current program should accept both steps. On-chain evidence would show:

- a stored `deck_seed`,
- a `deck_root` that recomputation proves is unrelated,
- successful vault proofs against that unrelated root.

**Fix**

Do not open minting merely because `deck_root != 0`.

Possible fixes:

- Have a separate independently controlled verifier attest to the exact `(seed, caps, root)` relation and require its signature on chain.
- Commit the fully constructed deck or a succinct proof generated by a verifiable computation system.
- Replace the off-chain shuffle with an on-chain assignment construction that can be verified incrementally.
- At minimum, require a separate authority independent of both MINT admin and Bank to approve the calculated root.

An alarm is not equivalent to preventing an invalid root, especially when the root is one-shot and payouts are irreversible.

### HIGH — The program-derived `current_slot + 32` does not remove slot choice from the submitting admin

**Exact construct**

```rust
let now = Clock::get()?.slot;
c.deck_slot = now.checked_add(DECK_SLOT_LEAD)?;
```

The caller cannot put a slot number in instruction data, but it can choose **when** to submit `commit_seed`. Solana’s leader schedule is known in advance. The admin can wait for a submission slot whose `+32` target belongs to a colluding or bribable validator.

**What collusion buys**

A target-slot leader can certainly:

- censor transactions in its slot;
- skip or fail to produce the target slot, causing no hash to exist.

Whether it can efficiently grind the exact SlotHashes value into a favourable deck needs a controlled-fork measurement; it should not be assumed either way. Transaction selection and PoH entry construction give the leader influence, but the practical grinding rate is not established by this bundle.

The code contains no rule preventing submission timing around a known leader schedule.

**Paused interaction**

`commit_seed` and `commit_deck` ignore `paused`. The admin can:

1. pause,
2. wait for a chosen leader configuration,
3. commit the seed,
4. inspect the resulting public deck,
5. either proceed or leave the deployment permanently unusable.

Pause prevents mints, not selective launch or selective abandonment.

**Gain**

At minimum, a colluding target leader gets a deterministic launch-kill switch. If blockhash grinding is practical, it may also bias the deck.

**Checkable evidence**

Two separate measurements are needed:

1. Show that submitting `commit_seed` in chosen execution slots predictably places `deck_slot` in a selected validator’s scheduled slot.
2. On a controlled multi-validator cluster, produce competing versions of the target slot while varying transaction/entry contents and compare the resulting slot hashes and decks.

**Fix**

Use entropy that the admin cannot target by scheduling around a public leader schedule, such as a verifiable randomness service with multiple independent contributors.

If SlotHashes remains:

- derive from multiple future produced slots, not one leader;
- define the selected slots independently of submission timing;
- mix contributions from enough distinct leaders that one target leader is insufficient;
- document and measure the remaining validator threshold.

---

### MEDIUM — Selective abort remains possible; one-shot state prevents rerolls but does not force a launch

After seeing the seed, the admin can simply never call `commit_deck`, or can commit no valid production root. Nothing forces revelation because revelation was replaced by immediate seed publication, but nothing forces completion either.

The one-shot config prevents repeated draws within that config. It does not stop:

- abandonment before customers mint;
- deployment replacement through program upgrade;
- an upgrade that clears or rewrites commitment state;
- launching only when the result is commercially favourable.

This is less severe before any customer funds exist, but the stated “non-revelation is impossible” is too broad. Seed publication is unavoidable after successful `commit_deck`; completion of the protocol is not.

**Evidence**

On chain, the config would remain forever with:

- nonzero `deck_salt_hash`,
- a fixed expired `deck_slot`,
- zero `deck_root`.

**Fix**

Define an explicit pre-mint abort policy. If a failed launch is permitted, make it publicly auditable and require a new program/config identity rather than silently resetting the same commitment. Move upgrade authority before the draw or require a timelocked multisig decision to abandon it.

## R2 — `blockhash_of_slot`

### HIGH — A naturally skipped target slot permanently bricks minting

**Exact construct**

The code asks for one exact numerical slot:

```rust
blockhash_of_slot(&ctx.accounts.slot_hashes, want)?
```

SlotHashes contains hashes for produced slots. A scheduled slot can be skipped and therefore never acquire an entry. In that case this is not an ageing-window problem: the requested hash never existed.

Because `commit_seed` is one-shot and there is no reseed, the deployment can become permanently unable to commit a deck from an ordinary cluster event.

**Gain**

A target-slot leader can intentionally stop minting forever by skipping its slot. The same result can happen accidentally due to validator failure.

**Checkable evidence**

On a controlled validator:

1. Call `commit_seed`.
2. Arrange for the exact target slot to be skipped.
3. Wait for later slots.
4. Repeatedly call `commit_deck`.

Every call should return `DeckSlotUnavailable`, despite the target being recent, and the state remains unrecoverable.

**Fix**

Commit to a deterministic **produced** slot, for example the first produced slot at or after the target boundary. The selection rule must be unique and independent of when `commit_deck` is submitted. Store enough boundary information to prove which produced slot was selected.

Do not add an unrestricted reseed instruction; that would create repeated draws. Recovery needs a deterministic fallback sequence fixed before any entropy is known.

---

### LOW — The documented “512 slots” window is actually 512 retained entries

`SLOT_HASHES_MAX = 512` bounds the declared vector length. Retention is based on entries, not necessarily exactly 512 numerical slot increments. Skipped slots mean the age in slot numbers can differ.

The parser enforces:

- at most 512 entries;
- sufficient bytes for those entries;
- exact-slot lookup.

It does not enforce “within 512 numerical slots.”

**Evidence**

Compare the oldest and newest slot numbers in SlotHashes during a period containing skipped slots. Their difference can exceed `n - 1`.

**Fix**

Rewrite the documentation as “up to 512 retained produced-slot hashes,” and measure the actual wall-clock retention under mainnet skip rates.

---

### Parser assessment

The raw layout used here is consistent with bincode serialization of:

```text
Vec<(u64, Hash)>
```

namely:

- little-endian `u64` count;
- 40-byte entries;
- little-endian `u64` slot;
- 32 raw hash bytes.

The “newest first” assumption is not used by the search.

Truncation, oversized count, zero hash, zero count, and missing slot all fail closed. A duplicate target slot returns the first copy rather than rejecting the malformed structure. A genuine pinned sysvar should not contain duplicates, but if the parser’s stated goal is to reject malformed data, duplicate slots should produce `BadSlotHashes`.

## R3 — Distribution tombstone handling

### HIGH — `!raw` and every non-Asset key are treated as a confirmed burn

**Exact construct**

```js
tomb = !raw || raw.data.length < 1 || raw.data[0] !== 1
```

This does not identify a Core BurnV1 tombstone. It identifies all of the following as “burned”:

- RPC returning `null`;
- an absent account;
- zero-length data;
- a non-Core-owned account;
- any future Core account key other than `AssetV1`;
- malformed or truncated account data.

The comment says “anything else still halts,” but the code does the opposite for these cases.

**Gain**

A transient or inconsistent RPC answer can silently remove one activated holder from the denominator. The remaining holders are then overpaid, and the omitted holder receives nothing.

An attacker controlling or compromising the configured RPC can selectively return `null` for chosen vault accounts and redirect that holder’s proportional share to everyone else.

**Checkable evidence**

Mock `fetchAsset` to throw and make the subsequent `getAccountInfo(v)` return:

1. `null`;
2. a System-owned zero-data account;
3. a Core-owned account with a non-Asset, non-tombstone key.

In every case the current code adds the vault to `burnedSinceIndex`, omits its balance and level, and continues the distribution.

**Fix**

Recognize only the measured Core tombstone:

- account must exist;
- owner must equal Metaplex Core;
- data must match the measured `Key::Uninitialized` tombstone shape.

For example, if the measured shape is exactly one byte with value zero:

```js
tomb =
  raw !== null &&
  raw.owner.equals(CORE) &&
  raw.data.length === 1 &&
  raw.data[0] === 0
```

Every other result must halt.

Absence must not mean burn. A burned asset is measured to leave a surviving Core-owned account, so `null` contradicts the expected burn evidence.

---

### HIGH — The same overbroad liveness test remains in the payment loop

**Exact construct**

```js
if (!stillThere || stillThere.data.length < 1 || stillThere.data[0] !== 1) {
  done[v] = { ..., skipped: 'vault is no longer a live Core asset' }
  ...
}
```

The round-20 repair copied the payment loop’s existing predicate instead of validating whether that predicate was itself sound.

This is the one-of-N defect in the opposite direction: both sites now agree, but both agree on a fail-open classification.

**Gain**

On a resumed plan, an RPC `null` or malformed response marks a live holder permanently `skipped` in the payment ledger. Later retries do not pay it because `done[v]?.skipped` is terminal.

**Checkable evidence**

Use an existing plan and return `null` from the per-payment `getAccountInfo`. The ledger will gain a durable `skipped` row even though the asset remains live on a healthy RPC endpoint.

**Fix**

Create one shared `classifyCoreAssetAccount(raw)` helper with outcomes:

- `live`;
- `burn_tombstone`;
- `unknown/malformed`.

Use it in both loops. Only `burn_tombstone` may skip; `unknown/malformed` must stop without writing a terminal skipped row.

---

### Inner catch direction

This part behaves as described:

```js
catch { tomb = false }
```

A thrown RPC exception leads to `unreadableLevels` and then a distribution refusal. That direction is closed.

The defect is that a successful RPC call returning `null` is treated as a burn, despite being semantically just as uncertain.

## R4 — Repair ordering and unfailable checks

No later `commit_deck` check establishes state required by an earlier check. Current handler order is coherent for the named error cases:

1. already-committed root;
2. zero proposed root;
3. seed exists;
4. salt matches;
5. target hash exists;
6. state write.

One caveat is deliberate: before any seed exists, `commit_deck(zero_root, ...)` returns `BadDeckRoot`, not `SeedNotCommitted`. The suite tests that separately and pins the result.

### LOW — The lead-time property has no assertion and can regress to zero while the new suite remains green

**Exact construct**

The suite checks that `commit_seed` succeeds and later reads whatever `deck_slot` was stored. It never asserts:

```text
deck_slot == commit_seed execution slot + 32
```

Nor does it assert that the target blockhash did not exist when the commitment landed.

If `DECK_SLOT_LEAD` were changed from 32 to 0, the current flow would likely still:

- commit the salt;
- find the current slot in SlotHashes by the time it reads;
- derive matching JS/Rust seeds;
- pass 2.0e–2.0h.

**Evidence**

Mutation-test the program with:

```rust
const DECK_SLOT_LEAD: u64 = 0;
```

If the suite remains green, the central “salt committed before entropy existed” property is untested.

**Fix**

Record the landed `commit_seed` transaction slot and assert:

```text
stored_deck_slot == transaction_slot + DECK_SLOT_LEAD
stored_deck_slot > transaction_slot
```

Also add the zero-lead mutation to a mutation-testing job and require that the suite fail.

## R5 — New test arms

### Negative reachability

The pinned negatives currently reach their named checks:

- `2.0c`: nonzero root before seed → `SeedNotCommitted`.
- `2.0d`: first seed attempt with zero hash → `BadSaltHash`.
- `2.0f`: second seed after success → `SeedAlreadyCommitted`.
- `2.0i`: nonzero root and mismatched salt after seed → `BadSalt`.
- `2.0a`: zero root after seed → `BadDeckRoot`.
- `11.9`: second deck after root exists → `DeckAlreadyCommitted`.

`2.0e` is a positive arm, and `2.0g` checks locally parsed sysvar data rather than a program error.

### MEDIUM — 2.0h is not independent of the handwritten SlotHashes layout

Both sides use the same assumed raw layout:

- Rust: `8 + i * 40`;
- TypeScript: `8 + i * 40`.

Thus 2.0h proves:

- Rust and Node SHA-256 concatenation agree;
- both parsers selected the same 32 bytes.

It does **not** independently prove those 32 bytes are the canonical blockhash of `deckSlot`. Both implementations could share an offset or stride mistake and still compare equal.

**Evidence**

Mutate both parsers to the same wrong offset. If the selected bytes remain nonzero and in bounds, 2.0h can still pass.

**Fix**

Fetch the block through an independent RPC representation, such as `getBlock(deckSlot).blockhash`, decode its base58 bytes, and compare them to the sysvar-extracted hash. That provides a third implementation not based on the raw account offsets.

### 11.11 vacuity assessment

The repaired probes are no longer vacuous in the original way:

- each result must fall below 64;
- depth 7 must exceed depth 11;
- depth 11 must exceed depth 13;
- production depth must fit at least two attributes.

However, the exact published values `29 / 18 / 13` are only printed, not pinned. A major geometry change could yield `10 / 5 / 2` and all three assertions would pass.

**Fix**

If those exact figures are relied on in SPEC, pin them as literals or derive and pin explicit minimum margins.

### Offset verification

The hardcoded offsets are consistent with the shown `MintConfig` layout:

- `deck_root`: 529–560
- `deck_salt_hash`: 561–592
- `deck_slot`: **593–600**
- `deck_seed`: **601–632**

Thus `OFF_DECK_SLOT = 593` and `OFF_DECK_SEED = 601` match the current Borsh layout including the 8-byte Anchor discriminator.

# Accepted limits review

## 1. Is any accepted limit worse than stated?

### HIGH — Limit 9 overstates a procedural refusal as a closed redemption property

It says:

> “So a foreign nested asset fails the redemption CLOSED.”

That is true only when the sanctioned `bank/cosign.mjs` policy is used. The on-chain BURN program cannot enumerate the foreign asset. Accepted limit 1b correctly says the signing policy is skippable by the Bank key holder.

**Actual limit**

A foreign nested asset:

- is refused by the sanctioned co-signer;
- is not continuously detected;
- is not prevented on-chain;
- can be orphaned if the Bank signs through another tool or its key is compromised.

**Evidence**

Construct a redemption that omits the foreign nested asset and sign it directly with the Bank key, bypassing `bank/cosign.mjs`. The on-chain burn has no way to discover the undeclared asset.

**Fix**

Rewrite “fails the redemption CLOSED” as “the sanctioned co-signer fails closed.” Keep the custody/policy dependency explicit in item 9 itself, not only in item 1b.

---

### HIGH — Limit 15 incorrectly says minting cannot move the quorum bar

Accepted limit 15 says:

> “the quorum DIVISOR is snapshotted at proposal creation so minting cannot move the bar”

But the implementation description elsewhere says execution uses:

```text
max(snapshot supply, live minted supply)
```

Therefore minting during a proposal can raise the divisor and raise quorum. It cannot lower the bar, but it can move it upward.

**Gain**

A Bank able to mint during an open vote can:

- create new voting assets;
- allocate them to allies;
- raise the quorum requirement;
- potentially block a proposal by dilution, or help pass it by voting the newly minted assets.

This is broader than “a vault minted during a proposal may vote.”

**Evidence**

Create a proposal at supply `S`, then mint `N` vaults before execution. Compare the required quorum before and after. The required vote count should rise according to the live-supply arm.

**Fix**

Rewrite the limit to state both powers:

- newly minted vaults may vote;
- minting can raise, but never lower, the quorum divisor.

If this remains accepted, the buyer-facing disclosure must describe it as Bank influence over an open vote, not merely eligibility of a late vault.

# Additional findings

### MEDIUM — The product documentation claims “assigned by fate” while the implemented allocation is admission-controlled

This is the buyer-facing form of the R1 ordering defect. The documentation repeatedly describes the level as fate/randomness, but a mandatory co-signer can choose which customer consumes each already-public index.

The disclosure must not call this ungameable unless claimant-to-index binding is implemented.

**Evidence**

The ordered-mint experiment described in R1 produces different customer outcomes from the same committed deck solely by changing Bank signature order.

**Fix**

Either implement claimant binding or disclose that the Bank controls admission order and therefore can influence who receives each level.

# GIVEN THAT NO HUMAN FIRM WILL EVER SEE THIS

Nineteen rounds of language-model review cannot provide several forms of evidence the project still needs:

1. **Run a hostile multi-validator entropy experiment.**  
   Operate at least three validators, control the target leader, intentionally skip slots, create competing target-slot productions, and measure whether the chosen blockhash and resulting deck can be biased. Archive ledgers and hashes.

2. **Build a state-machine model of commitment and allocation.**  
   Model actors separately: MINT admin, Bank signer, validator leader, customer, and upgrade authority. Check properties such as:
   - no actor can choose which customer receives a known card;
   - no coalition below the declared trust threshold can bias or reset the draw;
   - every committed state either opens minting or enters an explicitly recoverable abort state.

3. **Adopt mutation testing, not just positive regression testing.**  
   Automatically mutate:
   - `DECK_SLOT_LEAD` to zero;
   - remove the salt check;
   - replace the root with arbitrary bytes;
   - change SlotHashes offsets;
   - classify `null` as burn;
   - swap customer mint order.  
   Certification should fail unless each security-relevant mutation is killed by a named test.

4. **Run production-scale shadow distributions before holding customer funds.**  
   Use roughly 2,100 real test assets against the intended RPC provider, with injected:
   - 429 responses;
   - timeouts;
   - `null` account reads;
   - DAS lag;
   - burns during each phase;
   - process crashes and resumes.  
   Compare the generated plan to an independently reconstructed reference ledger.

5. **Create an independent payout implementation.**  
   A second, read-only program written from the specification should reconstruct levels, activation, denominator, and expected payouts from chain data. It must not import `distribute.mjs` helpers or use its ledger. Compare every live settlement before sending.

6. **Use staged financial caps and a canary population.**  
   Do not begin with the full customer pool. Limit total cbBTC under management, number of vaults, and daily payout value. Raise caps only after reconciled live cycles with no unexplained divergence.

7. **Commission a public adversarial test campaign.**  
   Even without a firm, independent researchers can attack a funded devnet/mainnet-beta canary under a published bounty. Explicitly reward:
   - unfair level allocation;
   - RPC-induced payout omission;
   - commitment resets;
   - validator entropy influence;
   - ledger replay or double-payment.

8. **Separate operational authorities in reality.**  
   The fairness argument currently collapses if MINT admin and Bank cooperate. Put them under distinct organizations or independently governed multisigs, document the coalition threshold, and test incident recovery with one authority unavailable.

The immediate release blockers from this review are the claimant-ordering defect, arbitrary root acceptance, exact-slot permanent failure, and overbroad burn classification.
