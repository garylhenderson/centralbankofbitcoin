## R1 — Custody (open↔burn pairing, emptiness proof)

No finding. What I verified and how it would be falsified:

- **Pairing is symmetric and binds asset AND owner in both directions.** SEAL walks `current+1..` for `burn_vault` matching account 0 (asset) and account 2 (owner); BURN walks `0..current` for `open_for_redemption` matching the same indices. I recomputed the account positions against both `BurnVault` and `OpenForRedemption` contexts: asset is index 0, owner is index 2 in both. A drift would be visible as suite arms 3.1c–3.1f going red; they are pinned to the Anchor derivation.
- **`load_instruction_at_checked` sees only top-level instructions**, which is load-bearing both ways: a CPI-buried burn cannot satisfy SEAL, and a burn reached by CPI sees the outer index and still needs a genuine top-level open. I could not construct a wrapper that borrows another vault's open/burn because both halves bind the asset pubkey, not just the discriminator.
- **Atomicity closes "thawed vault leaves the transaction unburned."** If the burn reverts for any reason (emptiness, rate limit, declaration), the whole transaction reverts and the thaw is undone. There is no instruction that reseals, so there is no state where a vault is thawed and alive after the transaction. Evidence if I were wrong: a landed transaction containing `RedemptionOpened` for an asset whose Core account is still `Key::AssetV1` with non-zero PDA holdings. The alarm's signature walk is the detector for exactly this.
- **Emptiness proof.** I re-mapped the SPL token-account offsets the burn checks: delegate option `[72..76]`, delegated_amount `[121..129]`, close-authority option `[129..133]`, amount `[64..72]`, state `[108]`. These match the classic 165-byte layout. Reserve ATAs are derived deterministically per mint × {classic, Token-2022}, so a substitute account cannot be offered; a Token-2022 account with extensions fails `len == 165` (`ReserveHasExtensions`), which is the correct fail-closed direction given confidential balances read zero in the base field. The second loop extends the same delegate/close/amount/extension checks to any *declared* non-reserve token account owned by the PDA. The undeclared-account gap is real but is accepted limits 9/44 and I have nothing to add to it.

## R2 — Community pool

No finding. Verified:

- **Solvency invariant `pool ≥ ceil(owed_scaled/ACC_SCALE)`.** `credit` adds `delta = floor(avail·ACC/w)` and `owed += delta·w ≤ avail·ACC`; since `avail = balance − ceil(owed_old)`, the new `ceil(owed)` cannot exceed `balance`. `claim` reduces both balance and `owed_scaled` by the same whole-sat amount; `retire` reduces `owed_scaled` by the vault's pending without touching balance. I could not find a path that credits more than `avail`. Evidence if I were wrong: suite P.32 (`bal ≥ owedCeil`) going red at any point; it is asserted after the full lifecycle.
- **Two-step activation.** `join` requires `dist_epoch > request_epoch` and sets `debt = weight·acc_current`, `carry = 0`, so a vault's owed is `weight·(acc − acc_at_join)`: it earns only distributions that ran *after* it joined. The `JoinWaitingFirst` gate (`waiting_to_join = pending_count − pending_this_epoch`) blocks any distribution while an earlier-epoch requester is unjoined, and it is checked on `distribute` *before* the $GARY burn and in `monthly_inline` before crediting. I traced the counters through request/join/retire/advance_epoch and found no underflow: `join` correctly does **not** touch `pending_this_epoch` (it only fires in a later epoch, after the reset), and `retire` decrements `pending_this_epoch` only when `request_epoch == dist_epoch` (the F21 repair). This is the one counter family I worked by induction rather than by suite alone; F21.1/F21.2 are the on-chain confirmation.
- **The literal invariant in the brief, "no vault is ever paid for revenue that arrived before it joined," is not what the code guarantees, and the SPEC says so** (round-22 F2): a vault is never credited by a distribution that ran *before* it joined, but revenue already sitting undistributed in the pool is shared by everyone joined at the next distribution, new vault included. The one genuinely unclosed edge is accepted limit 55 (unsplit revenue in the revenue address), which I confirmed is real: `split_revenue` is not called inside activate/distribute, so a join+split+distribute sequence can share not-yet-split income. I treat it as correctly accepted, not as a new finding.

## R2b — $CBOB boost (the least-audited code)

I could not break it. Detailed verification follows; two evidence gaps are reported as INFO.

- **Exactly N distributions.** A boost bought at epoch `E` stores `end = E + epochs` in `boost_expiring[end % 64]`. `advance_epoch` increments `dist_epoch` then moves `boost_expiring[dist_epoch % 64]` into `boosts_due`. So the boost is active for the distributions that advance the epoch to `E+1 … E+epochs` (exactly `epochs` of them) and becomes due when the epoch reaches `end`. `BoostsExpireFirst` (`boosts_due == 0`) gates `distribute`, the `w == 0` tick, and `monthly_inline`, so no distribution runs past a due boost. Therefore a boost cannot earn N+1.
- **Ring collision.** I tried to construct two live boosts sharing a slot with *different* end epochs. For a second boost to share slot `s` it would need `end₂ ≡ end₁ (mod 64)`, i.e. `end₂ ≥ end₁ + 64`; but `end₂ = dist_epoch_at_buy + epochs ≤ dist_epoch_at_buy + 63`, and for the first boost to still be un-moved we need `dist_epoch_at_buy < end₁`, giving `end₂ < end₁ + 63 < end₁ + 64` — contradiction. The `epochs ≤ 63 = BOOST_RING − 1` bound (enforced at `initialize` and again in `set_boost_terms`) is what makes this hold; `MAX_BOOST_EPOCHS_BOUND = 63` is not arbitrary.
- **No loss/gain on weight change.** `reweigh` sets `carry = owed`, `debt = new_weight·acc`, so `owed = new_weight·acc + carry − debt` equals the old owed exactly. I checked this for boost-on (`boost_vault`), boost-off (`expire_boost`), claim normalisation (`carry = pending − pay·ACC`, `debt = weight·acc`), and retire. `total_active_weight` moves by `±boost_weight` at each reweigh and by the full weight at retire; `boost_weight_total`, `boosts_active`, `boosts_due` and the ring are all adjusted in `unschedule_boost` for both the due and not-yet-due cases. The suite's `books()` recomputation (`p.w==w, c.wt==bw, c.active==n, ring+due==active, solvency`) is the on-chain witness.
- **Same-transaction cases.** `boost_vault` runs `monthly_inline` first, so a due month credits at the *old* weight and the boost starts after it; `[distribute, boost]` and `[boost, distribute]` both give the boost exactly the distributions after it exists. Retire of a boosted vault before due (BO.16) and after due (BO.17) both clear the ring/`boosts_due` via `unschedule_boost`. I confirmed `retire` calls `unschedule_boost` before zeroing nothing (it leaves `boost_weight` set but `retired=true`, and `expire_boosts`/`claim` skip retired), so there is no double-unschedule.
- **No liveness block.** `expire_boosts` needs only records (not token accounts), records are public PDAs, and anyone may pass them in batches of ≤30; a vault whose cbBTC account is gone can still have its boost expired, so `BoostsExpireFirst` is always clearable. `boost_vault` does not require `boosts_due == 0`, which is correct (buying a boost cannot wedge the gate).

**INFO-1 (evidence gap): no arm expires the same boost twice.** It is prevented by construction (`expire_boost` requires `boost_weight > 0`; expiry zeroes it; `expire_boosts` and `claim` both skip `boost_weight == 0`), and a duplicate record in one `expire_boosts` call re-loads the already-zeroed record and skips. But there is no assertion proving a second `expire_boosts`/`claim` on an expired record changes nothing. Evidence if the claim is false: `boosts_due` or `boost_weight_total` underflowing (abort) or going negative in a two-expire arm. Fix: one arm that expires a due boost, then calls `expire_boosts` on the same record again and asserts `bc()` unchanged.

**INFO-2 (evidence gap): no arm changes boost terms while a boost is live.** The code captures terms at purchase (`boost_vault` reads `boost_weight`/`boost_epochs` into locals and stores them on the record), so a `set_boost_terms` between purchase and expiry cannot alter a live boost — but this is read-verified, not suite-verified. Fix: boost X, `set_boost_terms` to different weight/epochs, run X's remaining distributions, assert X was paid at the *original* boosted weight.

## R3 — Level draw

No finding. I re-derived the entropy independently (as L.3c now does) and checked the skip handling:

- `blockhash_in_window` pins the sysvar id, bounds `n ≤ 512`, bounds the buffer, picks the **smallest produced** slot in `[want, want+64]`, and refuses an all-zero hash. The layout read (`u64 count`, then 40-byte entries) matches the bincode `Vec<(Slot, Hash)>` sysvar; the suite's raw re-derivation uses the same offsets and agrees with the stored entropy.
- FIFO is enforced by `index == revealed_total`; a burned head-of-queue vault still draws (burned detected positively as Core-owned/1-byte/key-0) and advances the FIFO, so the queue cannot stall at a dead vault. Reschedule targets `now + 16`, a future slot, and is logged/counted. Accepted limits 25/26 were corrected in round 22 and I find the corrected statements accurate (a skip of C's target slot stays with the same leader within its 4-slot group because the search takes the smallest produced slot; same-slot cohorts share `reveal_slot` and thus A/B/C). I do not find them worse than stated.

## R4 — Governance

No finding. Verified quorum `ceil(supply·quorum_bps/10000)` with `need > 0`, threshold as floor `yes·10000/cast ≥ threshold_bps`, turnout `yes ≥ ceil(supply·10%)`, and key-change `yes ≥ ceil(supply·50%)`. With the ruled 21%/51% the minimum passing YES is 10.71% > 10%, so the turnout floor is redundant exactly as limit 35 states. The electorate is snapshotted (`index_snapshot`, `quorum_supply`) and the divisor is the snapshot, not `max(snapshot, live)`, so mid-vote minting can neither vote nor raise the bar. Ordering marks (`last_round_id`, `last_guardian_id`, `last_arm_id`, `last_boost_id`) skip overtaken actions as logged no-ops; the RT3-4 fix (moving the round mark *before* the already-over check) is present. The restart skip in GOV (`stopped_at >= created_at`) and the `StopIsNewer` check in MINT (`stopped_at < created_at`) agree on the same-second tie (round-22 F12 repair), and I found no third site with that comparison. I could not construct a minority path to a key change (needs half of all live vaults) or a permanent governance freeze short of redeeming every vault (accepted limit 45).

## R5 — Charter claim

No finding. The Merkle proof is domain-separated (leaf 0x00 / node 0x01) with sorted pairs, defeating second-preimage; identity is by address against `pob_root`, so a hot-wallet-minted lookalike is not in the tree (C.8). The PoB is CPI-burned as its owner in the same instruction, owner-signed, so a third party cannot spend someone else's leaf and a PoB holder cannot double-spend (the address is unre-mintable). `pob_extra` accounts are passed to Core's burn with `is_signer=false` in every meta, which I confirmed in the builder loop. The window is clock-only and cannot reopen. The remaining hot-wallet risk (a REJECTING oracle hook) is accepted limit 46 and unchanged.

The suite is genuinely adversarial (wrong-reason pinning via `because`, floors that must equal counts, independent re-derivation of the draw and the rate window). Beyond INFO-1/INFO-2 above:

**INFO-4 — arm 9.13 ("re-mint a burned asset address") fires for a different reason than its name.** It is refused because the `VaultRecord` PDA for that address already exists (Anchor `init` error 0x0), *before* Core is ever asked; Core's own refusal is a v5 measurement, not re-proven in v6. The `because('9.13','custom program error: 0x0')` comment acknowledges this. The property still holds, but if the record-PDA check were ever removed, the Core-side guarantee would be untested in this codebase. Fix: a sim arm that deletes/ignores the record and asks Core to `CreateV2` over a burned asset directly (the sim already has burned assets).

**INFO-5 — the off-curve-owner hazard (accepted limit 43) has no on-chain prevention and no on-chain test.** Arm 5.2 is refused by `AccountNotSigner` (a non-signer), which is a different property from "a PDA that signs via CPI"; SPEC concedes this. The only control is the alarm's `unredeemable_owner`. Since a vault minted by CPI to a PDA is permanently sealed, and `mint_vault` does not check stack height, this remains detection-only. I record it as an evidence gap rather than a new finding because it is accepted, but it is the one place a buyer-facing promise ("only you can open it") silently becomes false for a DAO/multisig buyer.
