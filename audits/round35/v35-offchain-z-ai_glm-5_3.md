## Findings

### F1 — MEDIUM — The placeholder upgrade-authority key is a launch-critical secret with no recorded custody, no gate, and no stated backup

**Construct:** `audits/round34/VALIDATION.md` and `SPEC.md` road step 9 record that all five claimed program ids on mainnet carry upgrade authority `FZjLB4e9mVMZTWA6YR1KbXVbByTqWsHpHy5sK83yJYUY`, "a key held on the box, which must not be lost before step 11". That requirement has no mechanism anywhere in the tree.

**What is lost:** the key itself. Losing it means neither the step-9 upgrade to the `dist/` bytes nor `set-upgrade-authority --final` can ever be signed: all five ids hold the inert placeholder forever, and the only recovery is new program ids — the exact "new ids, a program change" outcome the claiming was meant to prevent — at the worst possible moment, requiring re-derivation of every PDA and a re-run of the whole rehearsal machinery. This is the same order of consequence as the MEDIUM round 34 filed, now self-inflicted by key loss instead of by a stranger.

**Why this is an omission and not a choice:** every other launch-critical secret in this system is pinned and checked. The swap operator is a RULED value in `launch/mainnet-init.json` with on-curve and not-the-guardian rules in `scripts/check-launch-params.mjs`; the $CBOB release wallet is a RULED entry with a pin (limit 56); the crank and operator key files are mode-600-checked by their loaders. The placeholder authority key has none of these. Worse, the tree's own gate *actively prevents* recording it casually: `check-launch-params.mjs` refuses any key not in its `covered` set ("has no launch validation rule"), so it cannot even be written into the launch record without deliberately adding a rule — and no rule was added.

**Evidence if I am right (checkable in minutes):** `grep -rn "FZjLB4e9" /opt/cbob-vaults` returns hits only in `audits/round34/VALIDATION.md` and `SPEC.md`; `jq 'keys' launch/mainnet-init.json` contains no placeholder/upgrade-authority entry; the `PINS` list and `covered` set in `scripts/check-launch-params.mjs` contain no such key; no file in `bank/` or `scripts/` reads a keypair whose public key is that address; no backup arrangement for it is stated anywhere (the R2 nightly backup is named only for `cbob-release.json`).

**Fix:** add a RULED `placeholder_upgrade_authority` entry to `launch/mainnet-init.json` (the pinned address, the key file path, the custody source) with a checker rule — `isKey`, plus a file-exists/mode-600 check like the loaders perform, plus a public-key-equals-the-pin check; state its backup arrangement; ideally move it off-box or into hardware until step 9, since it is needed for exactly one ceremony. And arm the watcher cron against mainnet now (it is read-only): with the ids deployed, the five placeholder hashes and the live authority can be baselined and watched from today, which also makes limit 13's written mitigation ("the alarm reports any program still upgradeable") true in practice for the pre-lock window rather than only after the lock deadline is set.

### F2 — LOW — The split-history growth residual is real, attacker-influenceable, and unwritten in the carry list

**Construct:** `bank/alarm.mjs` persists `next.seenSplits = D.dedupeSeenSplits([...seenSplits, ...prev.seenSplits])` every pass with no horizon; `bank/detectors.mjs`'s `detectSplitHistoryGrowth` pages `split_history_large` (HIGH, level) above 50,000 entries and its remedy text is "Splits older than every open revenue cycle's return can be pruned from state.json by hand."

**What is lost:** nothing today — the round-34 repair genuinely removed the per-cycle filter-and-sort blowup (one sort per pass, binary searches after). What remains is that nothing ever prunes: a stranger still adds entries for one fee and one sat each (~96,000/day within the read budget, ~10 SOL for 2M entries per the verdict's measurement), the pretty-printed `state.json` grows ~168 bytes per entry and is stringified, fsynced and renamed every 30 minutes, and the only control is a human reading a HIGH page and hand-editing a state file. The round-34 verdict's recommended repair was automatic pruning below the oldest verifiable cycle; the shipped repair deliberately did not take it, and VALIDATION.md records what was built — but the *residual* (unbounded growth, manual pruning as the sole control, the O(n log n) per-pass sort and the linear state write that continue until a human acts) appears in no accepted-limits entry. By this project's own discipline ("a limit left unwritten resets the freeze counter every time a fresh reader notices it"), the next round will re-measure this from scratch.

**Evidence if I am right:** `grep -n "seenSplits" bank/alarm.mjs` shows the unbounded union and no pruning call; `grep -n "split_history\|seenSplits" SPEC.md` finds the growth in no ACCEPTED LIMITS entry (only the round-34 L3 *recovery* residual is in limit 10); the measured growth numbers exist only in `audits/round34/VERDICT-offchain.md`'s L1 row.

**Fix:** either take the verdict's original repair (prune `seenSplits`/`seenSweeps` below the oldest open cycle's return minus a margin, with a both-ways arm that a pruned entry anchors nothing it should not), or write the residual into SPEC's accepted limits with the numbers: never pruned automatically, stranger-growable for one fee per entry, pages at 50,000, human prunes by hand, per-pass cost O(n log n) plus a state write linear in n until they do.

## R1 — The crank

I looked specifically for the four asked-for failures and did not find any; here is what I actually checked rather than a blank assertion.

**A plan the program will refuse.** I traced every planned instruction against its program context and refusal set. Joins are sent as `claim` with `crank_n=0` and only pending pairs, which the program joins without touching the pool (correct even under a frozen pool, matching SPEC's "join-only batches"); claims are planned only when the pool is readable and unfrozen, only into the recorded `vault_ata`, with frozen destinations deferred and missing/mismatched accounts reported rather than sent; the split is planned only with both destinations live and unfrozen and is refused locally when the decimals byte is unreadable; the distribute is planned only when due, with weight adjusted for pre-joins, retirements (level weight + boost) and pre-expiries, and against `owed_scaled` reduced by the retiring vaults' pending shares (round 24 I1). The remaining refusals are races, and the race classifier (`mintFailureCode`'s stack-attributed Anchor codes, `BENIGN`, `judgeDistributeRefusal`'s moved-epoch test with `PoolShort` never a race) covers each with a selftest arm. One deliberate conservatism worth naming: `plan.owed` is an *estimate* (planned against the pass's own projected accumulator), so a claim batch can occasionally carry a vault the program pays zero — the program skips it (`if pay == 0 continue`), costing an account slot, never a fee-wasting failure.

**A plan that pays or joins a dead vault.** `assets === 'burned'` is excluded from claims, pre-joins and post-joins; burned waiting vaults are retired, never joined; unreadable ('other') assets are reported and excluded, and one unreadable *eligible* vault suppresses the distribution entirely (matching `JoinWaitingFirst`). Unrevealed bare burns are retired at any level (I1).

**A reveal out of order.** The plan walks from `revealed_total` and stops at the first not-ready record; the send loop breaks on fail, benign and skip. Both lanes plan from the same on-chain counter, so a lane that loses a race gets `AlreadyRevealed` (benign) and stops — I could not construct an ordering violation, including across the two lanes.

**Value movement.** The selftest's structural pins hold (only MINT instructions, no token/SOL transfer constructs, free-path distribute). I verified all nine instruction account lists against the program contexts by hand (reveal's 9 accounts in order, split's 7, claim's 3 + pairs, etc.).

**The boost arithmetic, recomputed.** This is the youngest and subtlest part of the planner, so I re-derived both expiry cases against the program's carry mechanics. Pre-expiry (expired before the distribution at accumulator A): on-chain owed after = `level_w·δ + w·A + C − D`; the crank computes `(atExpiry + level_w·(acc − A))/ACC_SCALE` — identical. Post-expiry (the distribution makes the boost due, expiry runs at the post-distribution A′): on-chain, `reweigh(0)` at A′ sets `carry = w·A′ + C − D` and `debt = level_w·A′`, so owed after = `w·A′ + C − D` — which is exactly the crank's live-boost formula at `acc`, so treating post-expiry vaults as still-boosted for the owed estimate is *correct*, not an over-count. The denominator subtracts only pre-expiry boost weight, matching the program's schedule state at the distribution. No divergence.

**Fee budgeting.** `planCostLamports` counts every transaction the send loop actually emits (including the ceil-divided pre-join, pre-expire, post-expire and claim batches); `budgetPlan` keeps the floor in reserve on every branch and keeps the FIFO head. A mid-pass failure still burns its fee, but only out of slack, never the floor.

**(b) Pyth verification.** I recomputed the `PriceUpdateV2` offsets (disc 8, write_authority 32, verification tag at 40, feed id 41–72, price 73, conf 81, expo 89, publish_time 93) — consistent with `readPyth`, the selftest fixture writer, and the fork test's clock-rewriting stub, all three independently. **(c) Deviation filter.** `orcaSpot = (sqrt_price/2^64)²` in raw units and `meteoraSpot = (1+binStep/10⁴)^(−activeId)` are the right quantities in the right direction; I sanity-checked the mainnet read (1.0015^5920 ≈ 7,145 lamports/sat ≈ the SOL/BTC ratio at the pinned prices). **(d) Minimum out.** Same oracle read, 150 bps under expected, in each venue's output raw units (Orca `other_amount_threshold`, Meteora `min_amount_out`), byte-verified by the judge and execution-verified by the fork (a floor 5 % above the oracle is refused by each program with nothing moved).

**(e) The judge.** Within its stated scope (it catches our defects, never a same-tree tamper — accepted 10(3)) I could not route value past it: exact seven-instruction sequence, one signer, exact wrap amount and destination, SyncNative/close only, both ATA creations keyed to the operator, output account, amount, floor, direction and price-limit bytes pinned, priority fee refused, and any extra ComputeBudget instruction impossible because the sequence length is fixed. Venue-internal accounts (tick/bin arrays, reserves, oracles) are left to the venue programs, and the load-bearing backstop is that even a fully misrouted swap cannot pay below the on-chain floor — plus revenue.mjs's post-sign delta check.

**(f) Derivations.** Orca tick-array starts (`floor(tick/1408)·1408`, current then two below) and the string-seeded PDA, and Meteora's `floor(id/70)` with current then two above, bitmap-as-program-id when absent, `host_fee_in` None, event authority — all fork-proven against the real programs on cloned live state, which is the only kind of proof that settles a published-interface question like the bin-array size. **(g) wSOL.** Exact-in consumes exactly `lamportsIn`; a pre-existing balance is synced, not spent, and returned by the close; wSOL has no freeze authority; a delegate on our own account needs our signature to exist; idempotent create handles a stranger-created ATA. **(h) Failure and retry.** `classifySendFailure`'s three outcomes are correct and armed (preflight refusal, landed-and-failed, expired-unlanded → refused; landed-and-succeeded → recorded; anything the chain cannot settle → unknown, cycle open). Meteora is reached only on `refused`; an unknown send throws with the candidate signature preserved and the next run refuses at the open-cycle guard; `cycleIsOpen` cannot read a failed or unreturned cycle as closed (the `'0'`-string truthiness bug is pinned by its own arm).

**(i) Bounds within the tolerance.** Honest execution costs ~16 bps fee plus ~1–2 bps impact for a 10 SOL swap in the Orca pool; the floor allows 150, so a sandwich or a pool held at the filter's edge can extract at most ~130 bps of the swept value per cycle (~0.13 SOL), ~16 SOL/month at the 40 SOL/day throughput ceiling — ~0.13 % of royalty flow, strictly dominated by the operator-key trust. A fast market breaks the cycle rather than trading badly (pools >100 bps from the stale oracle are skipped). A manipulated thin Meteora pool can only fail the floor (a refused cycle, recoverable by hand), never extract within it. **The one number never stated:** the single-RPC residual (limit 10(b)) for the swap path is bounded — a fully malicious endpoint can place its fake oracle at most 100 bps inside the filter and the floor 150 bps under that, degrading the enforced floor to ~250 bps below the pool's true price, ≈2.5 % of the swept value per cycle, ≈7 % of what the operator key itself can take. Within the stated trust; worth adding the number to limit 10's text. **Operator key worst case:** unchanged — cap × cooldown windows (10 SOL/6 h) until the guardian stops it; the swap rewrite removed Jupiter's HTTP reply but the key's sweep power was never the swap's to bound.

## GIVEN THAT NO HUMAN FIRM WILL EVER SEE THIS AND THE PROGRAMS WILL BE IMMUTABLE, what should this project do before launch that AI audit structurally cannot?

1. **Physically verify custody of every secret the box holds.** An audit can read that a file is mode 600; it cannot verify that a backup exists, restores, or that a key is anywhere safe at all — which is exactly the hole F1 sits in. Before launch, a human performs a restore drill from the nightly backup for `cbob-release.json`, the swap-operator key, the crank key and the placeholder authority key, and records it. Move the placeholder authority key (and ideally the release wallet) off-box with a written recovery path.
2. **Witness the one-time, uncorrectable writes with a second pair of eyes.** The launch checker validates the JSON, not the signed transaction (round 24 A6). Before broadcasting the four `initialize` transactions, Gary personally decodes them and compares every parameter against `launch/mainnet-init.json`; after landing, every value is read back from the chain by a tool that is not the box.
3. **Run the dress rehearsal with hands on the keyboard** — item 22's five named items, above all the forced post-swap failure walked through the hand recovery (22.4). Every step of that runbook ("look up every recorded signature with `getSignatureStatuses`… read the operator's wSOL and cbBTC balances") is a human skill under stress that no assertion suite exercises.
4. **Break the single-RPC and single-box trust from outside.** Stand up a second, off-box watcher (a laptop cron against a second provider) that independently fingerprints the five program bytes, the Pyth accounts and the two pools, and alerts through a channel the box cannot mute. Nothing in-tree can watch the box's owner (limit 10(3)); this is the only structural answer.
5. **Verify the deployed bytes and the lock from a machine that is not the box.** After each step-9 upgrade and before each `set-upgrade-authority --final`, dump each program from an independent machine and compare against `dist/SHA256SUMS`; dump again after `--final`. Otherwise the box is grading its own homework.
6. **Time the human half of every bound.** The sweep bound is "cap × windows until the guardian pulls the stop" — run a live stolen-operator-key drill against the rehearsal deployment and measure how long the stop actually takes a human; write the measured number into limit 10. Do the same for the guardian-replacement vote path.
7. **Re-make the charter-window custody decision in writing** (limit 46). No audit can hold the Giraffish Moments key cold through the 7-day window; a human must decide, and the decision should be re-confirmed with Gary immediately before the window opens.
