## Confirmed findings

| M1 | MEDIUM | **`seenSplits` and two other alarm state lists grow without bound, and the round-34 repair does not bound them.** `alarm.mjs` 774 persists `dedupeSeenSplits([...seenSplits, ...prev.seenSplits])` every pass with no horizon; `detectSplitClaims` now sorts and binary-searches that list each pass, so the per-pass cost is O(n log n) in the total splits ever seen, and `split_history_large` pages HIGH at 50,000 entries but never prunes. `logGaps` (round 32 L3) is never trimmed while any gap is unreviewed, and a stranger can add one padded transaction naming a program per fee, growing it by up to 8,000 entries a pass. `seenSweeps` (743) is likewise never pruned. At the 2,000-transaction-per-program-per-pass budget, about 96,000 splits a day fit with no `scan_gap`; the alarm's `state.json` grows by roughly 168 bytes per split, and the sort cost is measurable in seconds at 100,000 entries. The bound that remains is the deadman: a pass that never complete pages `run_failed`, but a pass that merely slows to 45 minutes pages nothing until the `flock -n` window closes. **Repair:** prune `seenSplits` and `seenSweeps` below the oldest cycle the window can still verify (minus a margin), and cap `logGaps` at a hard maximum with the oldest dropped first (the loud direction: a real gap is re-padded and re-paged). |
| M2 | MEDIUM | **`sortedSplits` WeakMap cache never hits across passes, so the round-34 speedup is overstated for the steady state.** `detectSplitClaims` builds `allSplits = [...seenSplits, ...prev.seenSplits]` fresh every pass, so the array reference passed to `sortedSplits` is new every pass and the WeakMap misses. The cache only helps within a single pass (e.g. `closesCycle` called multiple times for the same list). The 34 s → sub-second claim in the round-34 verdict is true for a single pass at a fixed size, but the per-pass cost still grows as O(n log n) in total splits ever seen, and the steady-state pass time trends upward with no floor. **Repair:** sort once per pass at the top of `detectSplitClaims` and thread the sorted list through; or prune (M1). |
| L1 | LOW | **`detectSplitClaims` does not anchor `splitSig` claims older than `verifyLastN` (200) cycles.** A cycle with a `splitSig` is only in `recent` if it is among the last 200 cycles that have a split or a non-rejected sweep. An old cycle's `splitSig` is still checked against `seenSplits` (which is never pruned), so a fabricated signature is caught; but the anchoring check (that the split is at or after the return and as large as it) is skipped for old cycles. A cycle that recorded a valid split and then had its `splitSig` cleared (a crash between split and save) is never re-anchored automatically. **Lower bound the window to the oldest open cycle, not a fixed count.** |
| L2 | LOW | **`satsPerLamport` in `oracleFloor` is computed in floating point and used for the 100 bps deviation filter.** `Number(sol.price) * 10 ** sol.expo / (Number(btc.price) * 10 ** btc.expo) / 10` — at the 2026-10-05 prices (SOL/USD ~120, BTC/USD ~85,000, both expo -8) the result is ~0.0014 and the relative error of double precision is ~1e-16, far below the 100 bps gate. Not exploitable today, but a future feed with a very large exponent (a depegged stablecoin, a sub-cent bps feed) could push `Number()` past 2^53 and flip a pool from "used" to "skipped" or vice versa. **Compute the deviation in BigInt against the scaled oracle output, not in floating point.** |

The operator key's worst case is still the per-sweep cap × cooldown windows until the guardian stops it; the 100 bps deviation gate and 150 bps floor bound what a sandwich or a thin Meteora pool can take per cycle. **No new defect in the swap hop.**

## GIVEN THAT NO HUMAN FIRM WILL EVER SEE THIS AND THE PROGRAMS WILL BE IMMUTABLE

Three things this project should do before launch that AI audit structurally cannot:

1. **A live dress rehearsal with a stranger in the room.** AI reads code; it does not watch a human operator under time pressure while a red team floods the RPC, pads transactions to grow `logGaps`, and sweeps the operator's dust into a vault mid-redemption. Item 22's named pass/fail list is the right shape, but it must be run with an adversary who has read this verdict and is trying to break the off-chain pipeline, not just the programs.

2. **A reproducibility witness for the deploy.** `scripts/build-mainnet.sh` proves the mainnet artifacts reject the test key and prints their sha256. The bridge from "these sha256 values" to "the deployed bytes" is a human watching the deploy and running `solana program dump` + `sha256sum` themselves, on a machine that did not build the artifacts. AI cannot be that witness; it cannot confirm that the file it audited is the file that was deployed.

3. **A bound on the alarm's state before the lock.** M1 is the one surviving defect that gets worse with time and can be triggered by a stranger for the price of transaction fees. Once the programs are locked, the alarm is the only thing that can still be changed — and it is the one piece of the system whose state is allowed to grow without bound. Prune `seenSplits`, `seenSweeps`, and `logGaps` before the freeze, and add a regression assertion that `state.json` size after a 90-day synthetic run is below a named ceiling.
