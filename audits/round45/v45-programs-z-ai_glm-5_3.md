**Unknown outcomes re-read.** Yes — and then, for any multi-transaction step, the driver **stops** rather than resumes. That is the conservative direction and it is where my first finding lives.

### Findings

**V45-1 (LOW) — the `rescue` step has a crash window that bricks it, and the driver's mid-step crash recovery is an undocumented manual state edit.**
*Construct:* `scripts/rehearsal-steps.mjs`, the `rescue` step. The treasury→holder return transfer is sent with `coreTransfer(...).sendAndConfirm(umiFor(key('treasury')), ...)` — directly, not through the driver's `send()`, so it is never recorded in `rec.sigs` — and `st.rescued = true` is saved only after it. The step's `done` requires `owner === holder && st.rescued === true`.
*What an accident gains:* nothing, and that is the point — no funds are ever at risk. A crash after the return transfer confirms leaves status 'unknown' with `rec.sigs` empty → `nextAction` returns 'run' → the re-run skips the nesting (`st.nestedSent` is already true) and enters `crankUntil(... owner === treasury ...)`, which is now false forever → five full crank passes → `throw 'after 5 full passes the crank had not done it'`. The step is bricked; the only recovery is a hand edit of `st.rescued = true` in the state file, which is discoverable only by reading the source. The same conservative 'stop' fires for every multi-transaction step (sale-round, crack, sweep-back) on a mid-step crash; the steps are internally idempotent so a manual reset to 'pending' is safe, but nothing tells the operator that, and for `rescue` the naive reset does not even work.
*Evidence if I am right:* run the driver to the rescue step, kill the process after the return transaction confirms but before the state write (or construct the state directly: `nestedSent: true`, vault-3 owned by the holder key, `rescued` absent, status 'unknown'), then re-run — the step throws after five crank passes with the crank having nothing to do.
*Fix:* make the run's tail idempotent on the read-back (if the vault is already with the holder and `nestedSent`, set `st.rescued` and return), and add one line to the STOP message naming the safe manual edit per step — or a `--resume <step>` that re-enters the step's own idempotent run path after the read-back.

**V45-2 (LOW) — `revenue-cycle-1`'s done-check cannot accept a legitimate Orca refusal, and each operator restart then runs another full real-SOL cycle.**
*Construct:* `scripts/rehearsal-steps.mjs`, `revenueCycle(1, 'orca', {})`: `done` requires `closedCycles().length >= 1 && closedCycles()[0].swapVenue === 'orca'`, hard-coding the venue *order* of the ledger's closed cycles.
*What an accident gains:* if Orca refuses for a real reason during cycle 1 (the read-time pool/oracle filter, or the pool itself), `revenue.mjs` correctly falls back to Meteora and closes the cycle — the cycle is legitimate, ledgered, and `--audit`-clean — but the done-check never passes. The step throws "the step ran but its read-back does not show it done", and every operator re-run starts another complete cycle (~0.1 SOL of real SOL swept, swapped and split each time; the real cost is fees and slippage, cents per cycle) until `--max-sol` stops the rehearsal. The record shows the meteora cycles, so the failure is visible, but the error message gives no hint that the cause is a legitimate fallback.
*Evidence if I am right:* run cycle 1 with Orca refusing for a real reason — the exact mechanism cycle 2 deliberately forces (`CBOB_REHEARSAL_FORCE_ORCA_REFUSAL`) — and observe: the ledger row closes with `swapVenue: 'meteora'`, `--audit` is clean, and the step still throws.
*Fix:* accept "cycle 1 completed on either venue AND the forced-refusal cycle completed on Meteora" (item 22.3's purpose — exercising both venues — is met in either order), or record a PARTIAL verdict and stop rather than throwing.

**V45-3 (LOW) — the driver does not set `ALERT_STATE_DIR`/`ALERT_LOG` for the alarm job, which SPEC item 53 prescribes.**
*Construct:* `scripts/rehearsal-run.mjs`, `job()`: the alarm runs with `CBOB_REHEARSAL_NOTIFY` (the rehearsal log script) and `CBOB_ALARM_REHEARSAL=1`, but not with the router-state isolation SPEC 53 names: "run it either `--dry-run`, or with the router's `ALERT_STATE_DIR` and `ALERT_LOG` pointed at a rehearsal directory … so a rehearsal stream can never mute or close a production one."
*What an accident gains:* if the alarm's alert router keeps its dedup/recovery state at a path outside the rehearsal tree's substituted root, rehearsal notices share production alert streams: a rehearsal CRITICAL could open a production stream and a later rehearsal RECOVERY close it, masking a real production alert for the rehearsal's duration. Whether this happens depends on `bank/alarm.mjs`'s notice path, which is not in my bundle; the local proof does not settle it (its alarm step checks the exit code and the REHEARSAL marker, not where notices went, and a fresh rehearsal may fire no notices at all).
*Evidence that would decide it:* read `bank/alarm.mjs`'s notice path. If every notice goes through the script named by `CBOB_REHEARSAL_NOTIFY` and no other router state is shared, this is closed; if the router state lives outside the repo root, it is shared.
*Fix:* set `ALERT_STATE_DIR` and `ALERT_LOG` to rehearsal directories in `job()` for the alarm, exactly as SPEC 53 instructs, or prove the notify override isolates the router and record that in SPEC.

**V45-4 (INFO) — the driver's new-address creates have no `checkNewAddress` guard, so limit 59's grief stops the rehearsal with the wrong remedy.**
*Construct:* `scripts/rehearsal-steps.mjs`, `ceremony-collection` (and the `vault-N` keys): the collection keypair is generated into `.rehearsal-keys` and the create is sent with only an existence check (`if (!(await conn.getAccountInfo(kp.publicKey)))`) — the web ceremony page's `checkNewAddress` three-state guard ('fresh'/'landed'/'taken') is not mirrored.
*What an attacker gains:* a slot leader who sees the create in flight can fund the address first. The create is then skipped (the account exists), `st.collection` is recorded anyway, and the read-back returns either 'absent' ("THE PIN IS WRONG") or "is not a Metaplex Core account" (the `broken()` STOP: "close every rehearsal program … make a NEW rehearsal tree") — the heavy remedy — when deleting `.rehearsal-keys/vault-collection.json` for a fresh key suffices. Nothing is lost but the deploy rent (recovered by the close) and time.
*Evidence if I am right:* pre-fund the generated collection address before the step runs; the create is skipped, the step records the address, and the driver STOPs with a remedy that does not match the cause.
*Fix:* read the address before creating (as the page does) and swap in a fresh key when it is 'taken'.
