## R5. The swap and the revenue cycle

This is where I spent the most care, because round 25 audited it and the prompt asks me to prove or break nine specific properties.

**(a) The oracle math.** `oracleFloor`: `sats = lamports × sol_price × 10^(es−eb) / (btc_price × 10)`. With both expos at −8: `num = lamports × sol`, `den = btc × 10`, `expected = num/den` (BigInt floor). Check units: lamports=1e9, sol=120.45×1e8 (expo −8 → price×1e8 cents-scale… actually Pyth expo −8 means price is in units of 1e-8 USD), so `lamports × sol_price = 1e9 × 1.2045e9 = 1.2045e18` (units: lamports × 1e-8 USD). `btc × 10 = 8.5929e11 × 10` (sats × 1e-8 USD × 10). Ratio = 1.2045e18 / 8.5929e12 = 140,178… wait: 1.2045e18 / 8.5929e12 = 1.40178e5. Hmm, 2 SOL should be ~2× 120.45/85929 × 1e8 sats = 2 × 140,178 = 280,356 sats. For 1e9 lamports (1 SOL): 140,178 sats. ✓. The `/10` in the denominator: sats = lamports/1e9 × (sol×1e-8)/(btc×1e-8) × 1e8 = lamports × sol / (btc × 1e9) × 1e8/1 … let me just do it cleanly: sats = (lamports/1e9 SOL) × (sol_usd/btc_usd) × 1e8 sats/BTC. sol_usd = sol_price × 10^es, btc_usd = btc_price × 10^eb. So sats = lamports × sol_price × 10^es × 1e8 / (1e9 × btc_price × 10^eb) = lamports × sol_price × 10^(es−eb) / (btc_price × 10). **The formula is exactly right.** Exponent handling: `e = es − eb`; if `e ≥ 0` multiply num by `10^e`, else multiply den by `10^(−e)` — correct for both signs, in BigInt, no float. Rounding: `num/den` BigInt division floors — the *expected* is floored, then `minSats = expected × (10000−150)/10000` floors again. Both floors are conservative (the floor is lower), which is the safe direction for a minimum-out. `satsPerLamport` uses `Number(sol.price) × 10^sol.expo / (Number(btc.price) × 10^btc.expo) / 10` — a float, used only for the *deviation filter*, not for the floor. Float precision: prices ~1.2e9 and 8.6e12 as Numbers are exact (< 2^53); the division introduces ~1e-16 relative error, far below 1 bps. **No overflow risk in the BigInt path** (u128-scale products). **The floor is genuinely below an honest pool's return** if the pool is within 100 bps of the oracle and the fee+impact ≤ 150 bps — the fork's SW.8/SW.9 record executed prices; I cannot re-run them, but the arithmetic bound is: honest return ≥ oracle × (1 − 100bps pool deviation) × (1 − fee) × (1 − impact) and the floor is oracle × 0.985. With Orca's 0.16% fee, the floor leaves ~0.9% for impact+deviation combined at the gate's edge. For a 10-SOL swap in a $10M pool, impact is ~0.1% or less. **Sound, with the stated residual that the oracle itself can be off.**

The receiver program verifies Wormhole signatures before writing. **(e) The judge.** I re-read `judgeSwapInstructions` against the eight round-25 tampers and the round-39 C15 recommendation (pin `host_fee_in`, flags, key count). **(f) Account derivation.** Orca tick arrays: `orcaTickArrayStarts` gives `[s0, s0−span, s0−2span]` where `s0 = floor(tick/span)*span` — the array holding the current tick, then the two *below* (a_to_b moves the tick down). At a tick-array boundary: `s0` is the array *containing* the current tick (floor), so a tick exactly on a boundary starts that array — armed. An uninitialised array: the Orca program initialises tick arrays on demand in a swap? **(g) wSOL handling.** Wrap exactly `lamportsIn` (System transfer, judged exact), SyncNative, swap, close back to the operator. If the operator's wSOL ATA already exists with a balance: `createAtaIdempotent` is a no-op, the System transfer *adds* `lamportsIn` to the existing lamports, SyncNative credits the *whole* lamport balance as wSOL, the swap consumes only `lamportsIn` (the instruction's amount), and the close sweeps the *remaining* wSOL (from the pre-existing balance) back to the operator as SOL. **Nothing is stranded; the pre-existing balance returns to the operator.** If frozen: the swap's transfer from the frozen account fails → whole transaction reverts → nothing moved. If delegated: the swap uses the owner's authority, not the delegate, so a delegate cannot intercept; the delegate could have moved funds *before*, which is the operator-wallet-holds-nothing-else rule (limit 10, residue 1). If created by someone else: an ATA at the canonical address is owned by the operator regardless of creator; `createAtaIdempotent` succeeds; the balance case above applies. If the swap consumes less than the input: impossible — it's an exact-input swap of `lamportsIn`; the close returns whatever remains (zero from this cycle's wrap, plus any pre-existing). **All sound.**

**(h) Failure and retry.** Orca first; Meteora only on `refused` (preflight refusal, landed-and-failed, or expired-unlanded — `classifySendFailure` distinguishes these by asking the chain). An unconfirmed send (`unknown`) stops the cycle with `rememberAttempt` preserving the candidate signature. Double-count in the ledger: a cycle row is written once (`led.cycles.push(cycle)` before the sweep); a landed-but-unconfirmed sweep sets `cycle.sweepSig = verdict.sig` (not a second row). A cycle read as closed: `cycleIsOpen` requires a split (`splitSig` or `splitByOther`) — a return alone leaves it open; `closesCycle` anchors on the return's chain time. **Every path leaves the ledger open until a cbBTC return is proven, and the return is proven by the delta check (`delta < guaranteed` throws) before `returnedSats` is recorded.** One residual I checked: if the *return* transaction's confirmation times out, `rememberAttempt(cycle, 'Return', ...)` preserves the candidate and the throw propagates — the row has `returnSig` unset, `returnedSats` unset, cycle open, paged. ✓.

**(i) Adversary extraction within tolerance.** With a 100 bps deviation gate and a 150 bps floor: a sandwich attacker pushing the pool to the gate's edge (100 bps) still delivers ≥ oracle × (1 − 0.0100) × (1 − fee) ≥ oracle × 0.9824 (Orca) — above the 0.985 floor? 0.99 × 0.9984 = 0.9884 > 0.985. ✓ (the gate is *inside* the floor's tolerance, so a gated pool always satisfies the floor even at the edge, before impact). A stale-but-accepted oracle (up to 180 s old): SOL/BTC moves ~0.1–0.5% in 3 minutes in violent conditions; the floor is relative to the *oracle*, so a 50 bps true-market move against the oracle is absorbed by the 150 bps tolerance; a >150 bps true move in 3 minutes makes the swap refuse (nothing moved) or land at the floor (bounded loss = 150 bps of the cycle). A manipulated Meteora pool (~$0.9M, ~10× thinner): the deviation gate still applies (the pool must be within 100 bps of the *oracle*, which the manipulator does not control), so pushing Meteora to the gate's edge costs the manipulator the price impact of doing so in a $0.9M pool against the oracle — and the extraction is still capped at ~150 bps of one 10-SOL cycle ≈ 0.015 SOL ≈ $2.50 at $170/SOL. Per month at the 34 SOL/day ceiling: 150 bps × 34 SOL × 30 ≈ 1.5 SOL ≈ $260/month, *if* an attacker can hold a pool at the gate's edge through every hourly cycle without the alarm's `prog.meteora.hash`/deviation pages and without the pool's own arbitrageurs correcting it. **Not material at the ruled cycle size.** The operator key's worst case: cap × windows until the guardian stops (stated, limit 10), now bounded by two pool programs and the oracle rather than an HTTP reply — the *detection* half is `sweep_unledgered_state` (state-derived, flood-immune) plus the walk. **The ledger cannot read a failed cycle as closed:** `cycleIsOpen` returns false only for `sendRejected` rows (which never carry a sweep) or rows with a split; a failed cycle has neither. ✓.
