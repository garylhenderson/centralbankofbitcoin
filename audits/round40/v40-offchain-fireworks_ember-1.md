## R1. The crank (`bank/crank.mjs`)

I traced every planned instruction against MINT's account constraints and refusals:

- **No plan the program refuses for a wrong reason.** `activate` keys match `Activate` (config mut, record mut, asset, vault_token, pool_token); `claim` batches carry `crank_n = 0` and pairs; `expire_boosts` batches of 20 ≤ `MAX_EXPIRE_BATCH = 30`; `split_revenue` keys match `SplitRevenue` with the decimals byte read from the mint (`splitDecimalsByte` refuses a null read rather than sending 0); `distribute` sends `burn = 0` with no remaining accounts. Races are either in `BENIGN` (and asserted *not* to swallow `BoostsExpireFirst`/`JoinWaitingFirst`/empty-key errors) or re-judged against a fresh config read (`judgeDistributeRefusal`, with `PoolShort` always a fault).
- **No dead vault is paid or joined.** `claims`, `preJoins` and `joins` all skip `assets[r.asset] === 'burned'` and report `'other'`; `retireBurned` runs first each pass. The residual — a bare burn landing *between* the crank's read and its send — is accepted limit 27, and the alarm's `claim_deferred_frozen`/event reading covers the log line.
- **No out-of-order reveal.** The reveal run walks strictly from `revealed_total` and breaks at the first not-ready record; a burned unrevealed vault is revealed with `[]` (via `revealAttrSource`) so the FIFO advances past it, which matches MINT's burned-asset path (skip the Core write, advance `revealed_total`). `readySlot` is a documented lower bound; a skip-slot race costs at most a benign `RevealTooEarly` fee.
- **Money arithmetic matches MINT.** I recomputed the three non-trivial cases against `credit`/`owed_of`/`reweigh`/`join`: a pre-joined vault's delivery (`w·Δacc`), a pre-expired vault's delivery (`carry + w_level·Δacc`), and the distribution's `avail` against `owedAfterRetire` (retirements free the retiring vault's `pendingScaled` before the credit). All three match the program's order of operations (retire → join → expire → split → distribute → expire-after → activate → claim), which the new R39 C01 arm now pins.
- **Nothing moves value anywhere the program doesn't pin.** The crank signs only as fee payer; the selftest's source arms (only the nine permissionless MINT instructions, no token/system transfer construction, no program but MINT) are still present and the instruction set is unchanged.

`budgetPlan` keeps the floor in reserve on every branch and runs the base plan whenever covered; I verified the arithmetic (`baseCost + keep·(SIG+RENT) ≤ lamports − floor`).

## R5. The swap and the revenue cycle

- **(a) Oracle math.** `sats = lamports·sol·10^(es−eb) / (btc·10)`; I verified both exponent signs (e = 0 at the live −8/−8; the e = ±1 algebra closes), the floor is rounded *down* (`expectedSats·9850/10000`, sub-sat, conservative), and `satsPerLamport` cannot overflow (prices ~1e10–1e13, exact in float64). The floor (oracle − 150 bps) sits far below an honest fill (Orca fee 16 bps + ~1 bp impact at 10 SOL on ~$10M), so it doesn't refuse honest swaps — consistent with the fork's SW.8/SW.9 measurements, which I did not re-run.
- **(b) Pyth.** The account is derived (shard 0, feed id, under the push-oracle program), required to be *owned* by the receiver, fully verified (level byte 1 at offset 40), and to carry the expected feed id; offsets (40/41/73/81/89/93) match the selftest fixture and the fork reads the real cloned accounts. Only the receiver program can write the account; a replayed old-but-signed price is caught by the 180 s age check against the *chain* clock, and a >30 s future stamp is refused. The Clock sysvar is the same clock MINT uses; an unreadable one refuses the cycle.
- **(c) Deviation filter.** `orcaSpot` = (sqrt/2⁶⁴)² in raw units = sats/lamport (A=wSOL, B=cbBTC, correct direction); `meteoraSpot` = 1/(1+bin_step/10⁴)^activeId (X=cbBTC priced in Y=wSOL, correctly inverted). Float error (~1e−16 relative) is fourteen orders below the 100 bps gate; it cannot pass a pool it should refuse.
- **(d) Minimum out.** The same oracle floor (`minSats`) rides Orca's `other_amount_threshold` and Meteora's `min_amount_out`, both in cbBTC sats (the output token's base units). Same floor the filter assumed.
- **(e) The judge.** It requires the exact seven-instruction sequence: CU limit 400 000 and *no* price instruction anywhere (a second CU instruction makes the count ≠ 7), both ATA creations for the operator's own wallet+mint, one System transfer of exactly `lamportsIn` into the operator's own wSOL account, SyncNative, the swap with the pinned pool, the operator's wSOL in and cbBTC out at the pinned key positions, amount and floor in the data, Orca's exact-input/a_to_b/min-price bytes, and exactly one close back to the operator. What a tampered builder can still route past it: only pool-internal accounts (vaults, tick/bin arrays, oracles) that the *venue program* validates against the pinned pool on chain, and Meteora's `host_fee_in` (a fee-share diversion that comes out of the pool's fee, not the operator's output, which is bounded on chain by `min_amount_out`) — the round-39 C15 recommendation, within tolerance, not a new defect. The box-owner residue is accepted limit 10.
- **(f) Derivation.** Orca tick arrays use the ASCII decimal start (minus sign included for negatives; `Math.floor` handles the boundary correctly), the oracle PDA, and vaults read from the pool; Meteora's bin arrays (active, two above for Y→X), bitmap-or-program-id, `host_fee_in` None, event authority and both token programs match the published interfaces and are proven by the fork (not re-run here). An uninitialised array or a boundary crossing fails on chain → refusal → fallback; the floor binds regardless.
- **(g) wSOL.** Wrap exactly `lamportsIn`, sync, swap exact-input, close back. A pre-existing balance returns to the operator on close; a frozen or delegated wSOL account fails the swap on chain (refusal, fallback, loud); nothing is left wrapped.
- **(h) Failure and retry.** `classifySendFailure` asks the chain: preflight refusal, landed-with-error, and expired-never-landed are `refused` (safe to try the next venue — nothing moved); landed-and-succeeded is recorded; anything unsettled stays open and loud (`rememberAttempt`, no retry). A confirmation timeout on a swap that later lands is recorded as landed, never double-swapped. Every path leaves the cycle open until a cbBTC return *and* a split are proven (`cycleIsOpen`), and the ledger cannot read a failed cycle as closed (`sendRejected` with a sweep signature or amount is itself CRITICAL).
- **(i) Adversary bound.** Worst case per swap is the on-chain floor: oracle − 150 bps, plus oracle staleness drift within the 180 s window; the 100 bps deviation gate bounds pool manipulation at build time. At the ruled 10 SOL / 6 h cap that is ~0.15 SOL per cycle, ~0.5 SOL/day if *every* swap is driven to the floor — bounded by the cycle size, and it is accepted limit 10's stated design, not a new hole.

## Findings

### LOW — the poster's and the revenue recovery's scanners abort on one unreadable transaction, where the alarm continues

**Construct.** `bank/revenue.mjs` `splitsSince` calls `await readParsedTransaction(conn, s.signature, { truncatedLogs: 'flag' })` with no per-transaction catch; `bank/redemption-poster.mjs`'s main loop does the same and then throws on a null. `bank/alarm.mjs`'s walk, by contrast, records `tx_unreadable`, holds that cursor, and finishes the pass (round 32 L2).

**What an accident gains/costs.** Nothing is gained; the cost is: in `splitsSince`, a single transaction in the recovery window that fails validation (or an RPC error envelope) rejects the promise, which aborts the open-cycle recovery block *before* `closesCycle` runs — so a cycle that *is* closable by on-chain split evidence is not closed automatically and goes to hand recovery instead, and the whole revenue run exits 3 ahead of the open-cycle guard's more specific error. In the poster, the throw aborts the run before `writeLedger`, so the cursor does not advance and redemptions *older* than the unreadable transaction are never reached (newer ones already drafted this run are kept in the queue; nothing drafted is lost).

**Evidence if right.** A stub `conn` whose `getSignaturesForAddress` returns two signatures and whose `readParsedTransaction` rejects on the first makes `splitsSince` reject before any `closesCycle` call; the same stub makes the poster's loop throw with no state write and no queue entry for the older redemption. A *permanent* trigger is a transaction whose version is not legacy/0/1 — `validateParsedTransaction` refuses `version` — i.e., a future transaction-version activation, which is the stated "Transaction-format boundary".

**Bounds (why LOW, not higher).** It is loud (revenue exits 3 and pages its stage; the poster exits 3); it needs a validation-failing transaction an honest RPC does not produce today, or a compromised RPC — which accepted limit 10(b) already trusts with every price, pool and floor; the open cycle wedges the revenue job regardless; and the poster is a drafts-only PROCEDURE job (item 50).

**Fix.** Catch per transaction in both scanners — skip and count, mirroring the alarm's `tx_unreadable` — so one unreadable transaction aborts neither the recovery nor the draft walk.

### INFO — observations, stated for the record (not defects)

- **`royalties_unswept` threshold vs the job's sweep threshold.** The alarm pages at `sweep_floor_lamports` (1 SOL) while the revenue job sweeps at `MIN_SWEEP_LAMPORTS` (0.01 SOL), so a *dead* revenue job is silent until 1 SOL of royalties accumulates. This is stated in limit 7 ("a sweepable 1 SOL or more, a day without a sweep"), it is royalty SOL only, and a *running-but-failing* job pages per stage. Stated, not worse.
- **Crank fee floor vs a sustained capture backlog.** The reveal lane reserves only `FEE_FLOOR_LAMPORTS` (0.005 SOL); the full pass's non-reveal base cost exceeds it only past ~1 000 pending captures/claims, in which case the full pass is refused and `crank_silent` pages within 3 h while the reveal lane keeps working. Loud, bounded, operator tops up.
- **Meteora `host_fee_in` is not pinned by the judge** (round-39 C15 recommendation). A tampered builder could route the host fee to a stranger, but it is paid out of the pool's fee share, not the operator's output, which is bounded on chain by `min_amount_out`. Within the 150 bps tolerance; already a recorded recommendation.
