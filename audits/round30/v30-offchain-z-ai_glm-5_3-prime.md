## R1 — The crank (`bank/crank.mjs`)

No new defect. I traced the planner against the bundled MINT source line by line:

- **Ordering** matches every program gate: retire → preJoin batches → preExpires → split → distribute → postExpires → activate → claims. `BoostsExpireFirst` and `JoinWaitingFirst` are both satisfied by construction; activations after the distribute avoid red-team 3 finding 6.
- **The owed arithmetic** is the program's, including the hard cases: a pre-expired boost is owed `atExpiry + level_weight × (acc − cfg.acc_scaled)` (exactly what `expire_boost`'s `reweigh` plus the distribution produces); a pre-joined vault is owed `weight × (acc − cfg.acc_scaled)`; a retiring vault's share is freed before the distribution is planned (round 24 I1); the tick path advances no accumulator.
- **The denominator** `w = total_active_weight + preJoinWeight − retiringWeight − expiringWeight` is the weight the program will see at `distribute`, because every input to it is sent before the distribute in the same pass.
- **Dead vaults** are never paid or joined: positively-burned assets are retired, `'other'` (null RPC) assets are excluded and reported, and an unreadable *eligible* vault suppresses the distribution (matching `JoinWaitingFirst`).
- **Reveals** are strictly in mint order from `revealed_total`, hash-checked before any fee, `[]` only for a positively burned asset, and the run breaks (rather than retries) on skip/revealed/mismatch.
- **Value movement**: every instruction is a permissionless MINT instruction; the key signs as fee payer only; the selftest's source assertions (no transfer, no other program) hold against the bundled source.

Two notes, neither worth a finding: a refused distribute still sends the `postExpires` batch, which the program accepts as a no-op (the boosts are not yet due) — one wasted transaction fee, no page; and the planner's `acc` estimate can under-shoot if mint revenue lands between plan and send, which only delays a sat to the next pass (the program computes the real owed).

## R2 — The alarm (`bank/detectors.mjs`, `bank/alarm.mjs`) and the scanners' family

### Finding 1 — MEDIUM — the round-29 M1 repair closed one trigger of a halting class, not the class

**Construct:** `bank/alarm.mjs` `main()`, the per-signature loop (`const tx = await readParsedTransaction(conn, s.signature, { truncatedLogs: 'flag' })` — no try/catch); the same shape in `bank/redemption-poster.mjs` `main()` and in `splitsSince` in `bank/revenue.mjs`. The throw path is `validateParsedTransaction` in `bank/txread.mjs`, which throws on every field it cannot validate.

**What an attacker or an accident gains:** any validation throw other than the truncation marker kills the whole alarm pass (one generic `run_failed` page, no findings computed, no state written, every cursor held — permanently wedged until a human edits the cursor), kills the poster run, and kills the revenue recovery path. This is byte-for-byte the failure shape round 29 filed as M1; only the trigger differs. The round-29 verdict's repair column prescribed "isolate refusals per signature in all three consumers"; the shipped repair (per VALIDATION.md) added flag mode for the truncation marker only. The class is therefore still open, and it is not disclosed: SPEC's "Reader coverage boundary" discloses the *lost event lines*, not the *halting*.

**Candidate second trigger, to be measured before this is called attacker-reachable:** a transaction whose resolved `accountKeys` contain the same pubkey twice. `validateParsedTransaction` requires `keys.size === m.accountKeys.length`; a hand-built legacy (or v0 static-plus-lookup-table) message that lists a duplicate key — legal at the instruction level, and I believe legal at the message level — would make the RPC's jsonParsed `accountKeys` contain the duplicate and the reader throw. The attack is the round-29 shape at the same price: pad the transaction with memo instructions, name the MINT program id as an unused read-only key, pay 5,000 lamports.

**Evidence that would exist if I am right:** on the existing local-validator harness (the one `tests/expiry-budget.mjs` and the round-29 truncation measurement used), send a successful legacy transaction that (a) contains a duplicate account key in its message and (b) names the MINT program id as an unused read-only account; assert `err: null`; fetch `getTransaction(..., { encoding: 'jsonParsed', maxSupportedTransactionVersion: 1 })` and inspect `message.accountKeys` for the duplicate; run `readParsedTransaction` on the result; run the source-extracted alarm walk (the selftest already extracts it) and assert it dies with the cursor unchanged. If the runtime refuses duplicate message keys, the trigger is dead and this finding rests on the RPC-schema-drift residual alone — still a real deviation from the verdict's prescribed repair, but no longer one-fee attacker-reachable, and I would downgrade it.

**Fix:** wrap each per-signature read in all three consumers; on a validation throw, record a durable, paged, persisted gap (the `logGaps` mechanism already exists — extend it to `read_gaps`), still run the instruction-derived detectors where the parsed shape permits, and advance the cursor only past a recorded gap. Add the stranger-shaped duplicate-key arm to the selftest so the question of whether it is legal is settled by measurement, not by me.

### Finding 2 — MEDIUM — the redemption poster permanently wedges on a redemption whose level was not yet drawn

**Construct:** `bank/redemption-poster.mjs` `main()`: inside the per-signature events loop, `draftPost({ ..., level: rec.level, ... })` is called *before* the queue dedupe and *before* `st.cursor = s.signature`. `draftPost` deliberately throws on `level` outside 1..5 (its own selftest: "an undrawn level is refused, not posted as Level undefined").

**What an attacker or an accident gains:** a redemption of a vault whose level is still 0 — reachable, because nothing in SEAL's open, BURN's burn, or MINT's `retire_redeemed` reads the level, and a holder who mints and redeems inside the reveal window (or while the FIFO is backed up) produces exactly that record — makes `draftPost` throw, which aborts `main()` before the cursor is written. The next run re-walks the same signatures, re-reads the same `CBOB_REDEEMED` event, and throws again. **The poster is wedged permanently** until a human hand-edits `poster-state.json`. The poster is the public per-redemption alarm channel that the 2.1% cap's visibility rests on ("a thief emptying vaults through leaked keys does it in public, one post at a time"); a wedge silences every future redemption post. The operator does see the error each run (exit 3, "level 0 is not I..V"), but nothing tells them the walk is wedged or how to fix it.

**Evidence:** run the poster (or its source-extracted loop, as the selftest already does) against a walk containing one `CBOB_REDEEMED` event whose `VaultRecord` has `level: 0`; run it again; assert `poster-state.json`'s cursor is unchanged and the second run throws at the same signature. The reachability half — that an unrevealed vault can be redeemed — is checkable in the existing suite harness by redeeming a freshly minted, unrevealed vault with its three reserve ATAs pre-created empty.

**Fix:** catch per-event. Queue a REJECTED hand-draft entry with the reason ("the vault's level was not yet drawn when it was redeemed; draft by hand from the record") — the truncated-logs path two lines up already does exactly this — and advance the cursor. Also guard the unguarded `(await conn.getAccountInfo(recAddr, 'confirmed')).data` (an RPC blip currently throws the same wedge, though that case self-heals on retry).

### Finding 3 — MEDIUM — the daily reconcile lane has no liveness watch; its silent stop is the fourth site of a three-site repair

**Construct:** `scripts/cron-install.sh`'s deadman line watches only `$ALARM_STATE` (`bank/state.json`, the 30-minute watcher's state). `bank/alarm.mjs`'s `watchdog_gap` reads only `prev.startedAt` from that same state. The reconcile writes `state.json.reconcile` (`at` timestamp) and nothing reads it. The reconcile's own failure path (`RECONCILE_FAILED` + a page) fires only on an *exception*, not on silence.

**What an attacker or an accident gains:** a deleted or hand-edited reconcile cron line, a crontab that stops firing it, or a wedged-but-alive `.alarm.lock.reconcile` holder (limit 7: a live holder is never stolen from) stops the daily `--reconcile` — the only state-based control for undeclared token accounts (accepted limits 9 and 44's post-hoc half; `detectUndeclaredTokenAccounts` runs nowhere else) — with **no page from anything**. The 30-minute watcher keeps running quiet, so the silence looks like health. This is precisely the shape limit 7's round-23/24 mitigations closed for the crank (`crank_silent`), the reveal lane and revenue (`royalties_unswept`): a fix applied to three of four identical sites, which is this project's signature defect, committed under a limit whose text names only the three.

**Evidence:** source-only and verifiable by inspection: grep the tree for any reader of `state.json.reconcile`'s `at` or mtime — there is none; the deadman's `find` names `ALARM_STATE` only. A behavioural check: remove the reconcile cron line (or hold its lock with a live process), let 48 hours pass, and assert that no stream pages — nothing will.

**Fix:** extend the deadman to a second line (or a second `find`) on `state.json.reconcile` with a ~30-hour bound, or have the 30-minute pass read the reconcile state's `at` and raise a `reconcile_stale` level finding. Either is five lines and matches the existing pattern.

## R5 — The swap (`bank/swap.mjs`) and the revenue cycle (`bank/revenue.mjs`)

I worked through all nine sub-questions. No new defect beyond Finding 4 below.

**(a) The oracle math.** Correct for every exponent sign: `sats = lamports × sol.price × 10^(es−eb) / (btc.price × 10)`, with the exponent difference applied to whichever side keeps the fraction exact; both divisions floor, which is conservative to under one sat against a 150 bps tolerance — immaterial. `satsPerLamport`'s BigInt-to-Number conversions are safe at the pinned feeds' magnitudes (price ~1.2e10, well under 2^53); a feed with a large positive exponent would lose precision, but the feeds are pinned and measured. The floor really is below an honest pool's return: the fork measured 10 SOL executing 29–30 bps under the oracle on both venues against a 150 bps floor, which leaves ~120 bps for fee (16 bps on Orca) plus impact plus oracle error.

**(b) Pyth verification.** The `PriceUpdateV2` offsets (disc 8, write_authority 32, verification tag at 40, feed id 41..73, price 73, conf 81, expo 89, publishTime 93) are internally consistent with the selftest fixture *and* proven against real cloned accounts by the fork's SW.7 (which drives the real `market()` and gets sensible prices). The account is derived (shard 0 + feed id under the push oracle) and must be owned by the receiver, so only the push oracle program's own writes land there; a chosen price or an old `publishTime` written into that account requires the Pyth upgrade key — the disclosed third-party trust (limit 10 (d)), watched at HIGH. The clock is the Clock sysvar, an unreadable one refuses the cycle, and a `publishTime` more than 30 s ahead is refused.

**(c) The deviation filter.** `orcaSpot` = (sqrt_price/2^64)² = raw cbBTC per raw SOL = sats per lamport; `meteoraSpot` = 1/(1+bin_step/10⁴)^active_id = sats per lamport for X=cbBTC, Y=wSOL — both the right quantities in the right direction, and both proven empirically by the fork on real pool state (SW.0: both within 100 bps; a 90,000 bps unit error would refuse both). Floating point at the 100 bps boundary is wrong by ~1e-10 bps; it cannot pass a pool that should refuse by any material margin.

**(d) The minimum out.** Same oracle read as the deviation filter (revenue.mjs re-prices after the sweep and uses `m2.f.minSats` for both the venue gate and the on-chain floor), in base units (sats), at the byte offsets both programs read (Orca `other_amount_threshold` at 16, Meteora `min_amount_out` at 16) — proven by the fork's refusal arms (a floor 5% above the oracle refused by each program with nothing moved) and by the judge's floor-equality check.

**(e) The judge.** Complete for its documented scope. It requires the exact seven-instruction sequence with the amount and floor it was told: the CU limit exactly 400,000 and no priority fee (any `setComputeUnitPrice` is refused by discriminator, and any extra instruction breaks the length), both ATA creations for the operator's own wallet and mint with the exact key list, the wrap of exactly `lamportsIn` into the operator's own wSOL ATA, SyncNative of that account, the venue swap with the pinned pool, the operator's own wSOL in and cbBTC out at their pinned slots, the amount, the threshold, and for Orca the direction and minimum sqrt-price limit, and exactly one Token close of the wSOL account back to the operator, last. Token instructions are limited to SyncNative and CloseAccount. What it deliberately does not pin — the venue-owned accounts (vaults, tick/bin arrays, oracle, bitmap, `host_fee_in`) — is validated by the venue programs against the pool, and a value-moving miss is caught after signing by the post-swap delta check. A tampered module remains the accepted box-owner residue (limit 10 (3)); I found nothing a tampered *builder defect* could route past it.

**(f) Account derivation.** The three Orca tick arrays (the array holding the current tick, then the two below — the direction an a_to_b swap crosses) and the three Meteora bin arrays (active, then the two above — the direction a Y→X swap crosses) match the published interfaces, are pinned in the selftest against measured mainnet values, and are proven by real swaps landing on the fork. A tick exactly on an array boundary starts that array. An uninitialised array makes the venue refuse — the cycle stays open and loud (round 29 C13's optional-hardening disposition; I agree).

**(g) wSOL handling.** Wrap exactly `lamportsIn`, sync, swap, close. A pre-existing wSOL balance is preserved (SyncNative syncs the total, the swap sells only `lamportsIn`, the close returns the entire remaining lamports — balance plus rent — to the operator). A frozen ATA fails the swap loudly; a delegate does not affect the owner-authority transfers; the ATA is the canonical derivation, so "created by someone else" is the same account and their rent is returned to the operator. Nothing is left wrapped: the close is unconditional, last, and pinned by the judge.

**(h) Failure and retry.** Orca first; Meteora only on a REFUSED send — preflight refusal, landed-and-failed (read off the signature's status with `searchTransactionHistory`), or expired-and-absent — never on an unconfirmed one (`rememberAttempt` preserves the candidate and the cycle throws). A confirmation timeout on a swap that later lands is classified `landed` from the chain status and recorded, so no double swap and no double count. Every path leaves the ledger open until a cbBTC return is *proven*: `cycleIsOpen` treats an intent-only row (unknown send) as open, a returned-but-unsplit row as open, and a swept-but-unreturned row as open; a `sendRejected` row closes only because nothing moved, and a refused row that carries a sweep signature is itself a CRITICAL (`rejected_row_has_sweep`). I checked all four cases against the detectors; a failed cycle cannot read as closed.

**(i) The extraction bound, and the operator key's worst case.** The worst execution any cycle accepts is 150 bps under the oracle's expected output. On the ruled cap (10 SOL per 6-hour cooldown, ~1.41M sats per cycle at the fork's prices), that is ~21,000 sats ≈ $20–25 per cycle; at four windows a day, ~$85–100 per day, ~$2,500–3,000 per month — at most 1.5% of the royalty throughput ceiling, on royalty revenue only. The attack costs: pushing the pinned Orca pool (~$10M liquidity) 100 bps requires inventory of the order of $100k through it, and the sandwich's round trip eats most of the 150 bps it extracts; Meteora is ~10× thinner so pushing it is cheaper, but the same 150 bps output cap applies; a stale-but-accepted oracle (≤180 s) only yields if the pool has *not* moved with the market, because the 100 bps pool-agreement check compares the pool to that same stale oracle — a moved market makes both venues unusable until the oracle catches up (sponsored feeds post ~every minute or on 0.5% moves). My conclusion: the tolerance is real, bounded, disclosed (limit 10 states the checks "do not establish a hard bound on deviation from the true market price"), and the cycle size does not make it material against the attack cost. The operator key's worst case is unchanged from limit 10's statement: keep swept SOL at cap × cooldown windows until the guardian pulls the stop (never a vault, the pool, or sale cbBTC); what the key now *trusts* — the two pool programs and the oracle rather than an HTTP reply — adds at most one cycle's cap per attack (a replaced venue program could ignore the floor, but the post-swap delta check throws, the cycle stays open, and the alarm's HIGH on that program's hash fires within one 30-minute pass), all stoppable by the same guardian brake.

### Finding 4 — LOW — `splitsSince`'s 10-page bound is fillable with noise, blocking the automatic open-cycle recovery

**Evidence:** the page bound is source-visible (`for (let page = 0; page < 10; page++)`); the indexing of unused read-only keys is round 29's own measurement; the cost arithmetic is 10,000 × 5,000 lamports.

**Fix:** derive the split scan from the MINT program's signature walk (already gap-paged at 20,000 with a loud `scan_gap`) rather than the revenue ATA's, or raise the bound and page a gap when it is hit. At minimum, state the bound in limit 10's hand-recovery text.
