## R2 / R2b — The pool and the boost

I attacked the invariant "the pool always holds at least ceil(owed)" at every mutation. `credit`: `delta·w ≤ avail·SCALE`, so `ceil(owed_new) ≤ ceil(owed_old) + avail = balance`. `claim`: subtracts `pay·SCALE` from both sides. `retire` (both paths, including the frozen-pool forfeit): subtracts the full pending from owed only. `join`/`reweigh` leave `owed_scaled` untouched, and `reweigh` provably preserves each vault's `owed_of` (carry = old pending, debt = new weight × acc). I also verified `owed_scaled == Σ owed_of` is preserved by every operation, which the suite's `ledger()`/`books()` checks confirm on chain after every money operation. The counters: `pending_this_epoch ≤ pending_count` always (same-epoch retires decrement both; joins only happen after an epoch boundary zeroed the counter — F21's arms cover the retire shapes); `waiting_to_join` uses `checked_sub`. The ring: a boost's end slot `e+N` with `N ≤ 63` cannot be consumed by an earlier `advance_epoch` because the previous consumption of that slot was at `e+N−64 < e`, and the `BoostsExpireFirst` gate prevents the epoch from passing `e+N` while the boost is live — no early expiry, no double expiry (`boost_weight = 0` guards), no never-expiry (records-only `expire_boosts` never needs a token account, which is the point of it). A boost earns exactly the distributions at epochs e+1…e+N (BO.21/BO.21a/BO.35/BO.35a measure both orderings). Liveness: every gate (`JoinWaitingFirst`, `BoostsExpireFirst`) is clearable by a permissionless instruction naming only records; a vault whose recorded ATA was closed (only its own owner could close it, via Execute) refuses claims naming it but blocks no one else. The two-step activation and the launch tick behave as documented, including the second-call monthly-tick-then-join path (the tick is a crediting-nothing distribution, so no backlog capture). SPEC's *weaker* wording on pre-join revenue (round 24 W11) is the true one — I checked both sentences against the arithmetic. No defect found.

### F3 — LOW — The widest measured redemption-page shape cannot rescue even one stray classic token

**Construct.** SPEC item 50's client obligations ("Mind the legacy packet" / "Offer to rescue stray CLASSIC tokens … mind the packet above, since each pair costs bytes") against the measured numbers in the same item: S8.0 = 1,061 bytes (owner payer, no compute budget), +52 for the compute-budget pair, +96 for a separate fee payer → 1,209 of 1,232, "23 bytes to spare."

**What an accident gains.** Nothing is stolen; a holder loses stray tokens. One rescue pair adds two new account keys (64 bytes) plus two indices in the Execute instruction's account list (2 bytes) ≈ 66 bytes — and even one new key (33 bytes) overflows the 23-byte headroom. So a page built to the fully padded shape can sweep its three reserves and nothing else; the stray-rescue obligation and the widest shape are mutually exclusive. The page must drop the compute-budget pair (which S8.1a shows the redemption does not need: 168,343 CU against the 800,000 default for four instructions) or the separate fee payer, or move to v0. SPEC warns "each pair costs bytes" but never states the arithmetic that makes the two obligations incompatible in that shape.

**Evidence if I am right.** The arithmetic above from SPEC's own measured figures; a serialization of the 1,209-byte shape plus one extra pair will exceed 1,232.

**Fix.** State the mutual exclusion concretely in item 50's client obligations (the page's shape must be conditional on the coverage check's findings), and add a suite arm that serializes the widest shape plus one rescue pair and asserts the overflow, so the constraint is pinned rather than implied.

## What this project should do before launch that AI audit structurally cannot

1. **Have someone who did not write the programs write tests from SPEC.md and HOLDER-GUIDE.md alone, and run them.** Every assertion in this tree was authored by the code's author; an AI round reads the source and the author's tests but never executes anything of its own. The highest-value target is the pool/boost state machine: the suite's own `ledger()` and `books()` checks are exactly the right oracle — wire them to a random driver that fires mixed sequences of mint, reveal, activate, distribute, claim, boost, expire, retire and redeem against the real programs on the pinned-Core validator, asserting the invariants after *every* transaction. The host tests do a model version of this for the ring; the on-chain fuzzer does not exist anywhere. Random orderings are where the author's tests and the AI's reading share the same blind spot.
2. **Reproduce the pinned Core binary from source.** Round 25 N3 says it outright: the Core source is not proven identical to `f03e7537…`, and every custody property — the ExecuteV1 authority rule the sweep helper's whole access control rests on — is a measurement against bytes whose only provenance is "dumped from mainnet." Build Core from its tagged source with the pinned toolchain and compare hashes before the lock.
3. **Run the dress rehearsal's alarm walk over no-CPI transactions.** Item 22's live alarm passes should deliberately include a `capture_entropy`-only transaction and a plain SOL transfer. That settles F2 and any other reader boundary the fixtures never modelled, before the reader meets a live deployment.
4. **Put a second pair of eyes on the four `initialize` transactions before they are signed.** Item 38's A6 is honest: the checker validates the JSON, not the signed transaction. Decode the actual transactions and diff every argument against `launch/mainnet-init.json` in front of a witness; a wrong value is permanent.
5. **Move the $CBOB release key off the box and audit the swap operator wallet's contents at the rehearsal.** Items 56 and 10's operational halves (custody, "holds nothing but cycle funds") are facts no reading can vouch for; the rehearsal is the last moment to check them cheaply.
6. **Fund a standing bug bounty sized to immutability before the lock.** After the upgrade authorities are removed, external reporters are the only discovery mechanism left for anything every round missed. Decide its size and scope now, while it can still influence the launch decision.
7. **Have a human who wrote neither the code nor the guide read HOLDER-GUIDE.md against the programs.** An AI round can check individual sentences; whether the guide's overall emphasis honestly represents the risk profile is a judgement this process structurally renders only one sentence at a time.
