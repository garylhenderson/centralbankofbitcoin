## R1 — Custody: can anyone but the owner get value out of a sealed vault?

**No path found.** What I checked, by construction:

- **The pairing.** SEAL's `open_for_redemption` walks the instructions sysvar *forward* from `current+1` requiring BURN's `burn_vault` discriminator with account 0 = asset and account 2 = owner; BURN walks *backward* from `current` requiring SEAL's `open_for_redemption` with the same two bindings. Both bind asset AND owner, so neither half can be borrowed from another vault's redemption in the same transaction. The sysvar holds top-level instructions only, so a burn or open hidden inside a CPI is invisible to the walk — and the reciprocal checks plus `retire_redeemed`'s `get_stack_height() == TRANSACTION_LEVEL_STACK_HEIGHT + 1` (i.e., depth 2, direct CPI from a top-level instruction) close the wrapper shapes: a wrapped burn behind a genuine open fails `NotFromBurn` at the retire CPI *after* the Core burn, reverting everything (WR.2); a wrapped open before a genuine burn fails `NoPrecedingOpen` because the top-level instruction at that index is the wrapper, not SEAL (WR.3). I re-derived both failure chains from the code; they hold.
- **`retire_redeemed`'s sysvar check** is sound: at stack height 2 the caller is necessarily the program of the current top-level instruction, and the check requires that instruction to be `burn_vault` with account 0 = this asset.
- **The emptiness proof.** I recomputed every offset against the 165-byte classic layout: delegate COption tag 72..76, state 108, delegated_amount 121..129, close-authority tag 129..133, amount 64..72 — all correct. Both token-program ATA derivations are required declared for every reserve mint; the Token-2022 derivation for a classic mint can never exist (the ATA program refuses, measured by the probe; only the ATA program can create accounts at those PDA addresses), so it always arrives as a System-owned empty account and is skipped. - **The rate limit** is a true rolling window over the last 64 redemption timestamps: the k-th most recent (k = min(cap,64)) must be a full window old, so at most cap−1 prior redemptions plus the new one fall in any window ending at a landing. ## R1s — The sweep helper

**(a) Access control.** Direct calls need the asset-signer's signature, which only Core provides via `ExecuteV1`; Core (this pinned binary, per SR.5/5a/5b/5c/5d and the R24.1 pins) approves Execute only for `authority == owner`, refuses transfer delegates and collection authorities (`0x1a`), and the AgentIdentity route cannot be added by an owner or by MINT's off-curve PDA. While frozen, Core refuses Execute (`0x9`), so the helper is unreachable outside a redemption. A malicious program CPI-ing the helper with its own PDA can only move its own PDA's funds — the source-owner check confines it.
**(b) Pair list.** Duplicate source: the first pair closes it, the second `read_token` fails on the System-owned closed account (SR.12a/12b pin that the refusal is the closed account, not the owner guard). Source-also-destination is impossible (`signer != dest`, disjoint owners). wSOL sources are ordinary 165-byte classic accounts and sweep/close fine; a stranger can create a wSOL ATA for the vault and deposit raw lamports but cannot `SyncNative` (needs the PDA's signature), so `amount` stays 0 and the close simply gifts the lamports to the owner. Frozen sources revert the redemption (SR.14) — client must not name them. Non-ATA destinations are allowed by design (a feature, not a hole). `dest` = the vault's own signer is refused; `dest` = another vault's asset-signer is the owner moving value between their own vaults. Odd counts refuse; zero pairs is the lamports-only sweep (SR.13).
**(c) Destination checks.** The destination wallet is chosen by whoever builds the transaction, and through Core that is only the owner. A sub-rent-exempt credit to a non-existent account fails atomically (round-27 L10, item 50's client rule); R27.S1 now measures that a non-System-owned destination (a token account) receives the credit with its data unchanged.
**(d) The lamport sweep.** `signer.lamports()` is read at execution; nothing can deposit between the helper and the burn inside the same atomic transaction; Core's `BurnV1` does not credit the PDA (measured fact 4), so BURN's `lamports == 0` sees exactly what the sweep left.
**(e) Interaction with the emptiness proof.** A closed account is System-owned with empty data, so BURN's reserve loop skips it via the owner check — it passes *because it is no longer a token account*, the right reason. The prior-transaction preparation (SPEC step 1) is sufficient: any deposit into an existing reserve ATA is swept at live balance; a stranger cannot create an account at a reserve-ATA address (ATA-program PDA); a Token-2022 ATA for a classic mint cannot be created; a non-ATA classic stray is sweepable when named and destroyed when not (accepted 44); a nested Core asset is destroyed when undeclared (accepted 44) and blocks only if the page *declares* it — the page's contract is to warn, not declare.
**(f) Does it fit.** S8.0's 1,061-byte measurement is the real four-instruction shape (claim + open + one ExecuteV1 wrapping the helper with three pairs + burn); +52 for the compute-budget pair and +96 for a separate payer give 1,209 of 1,232. ## R2b — The $CBOB boost

**A boost earns exactly N distributions; nothing earned is lost or gained on a weight change; the ring always agrees.** Verified: `end = dist_epoch + N` with `N ≤ 63` and `end > dist_epoch`, so all live end epochs lie in `(dist_epoch, dist_epoch+63]` and two *distinct* live end epochs can never share a ring slot (|E1−E2| ≤ 62 < 64); `advance_epoch` drains slot `new_epoch % 64` exactly when a boost's end is reached, so it becomes due at exactly its end epoch; `unschedule_boost`'s two branches (due vs ring) match where the count lives; `reweigh` moves the owed share to `carry` and restarts the debt at the new weight without touching `owed_scaled`; `claim`'s inline expiry runs at the accumulator its last distribution left (the `BoostsExpireFirst` gate guarantees no distribution ran past it); no record can be expired twice (`require !retired`, `boost_weight > 0`, due-check) or never (the gate plus permissionless `expire_boosts`/`claim`).
