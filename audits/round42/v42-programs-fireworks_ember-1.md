### Finding (the only one)

**W-1 — LOW (page code; the documentation exception cannot apply, it changes page behavior).**
`web/src/lib/ceremony-reads.mjs` `collectionCreator` decides who created a candidate collection from the OLDEST transaction naming its address, and classifies on that one transaction alone: `if (tx.meta?.err) return { by: 'other', why: 'the first transaction naming it failed' }`. The comment above it — "the FIRST transaction naming its address is the one that created it" — is false when that first transaction failed. A failed `CreateCollectionV2` lands in history naming the address but creates nothing; Gary's retry then succeeds at the same keypair address. In that case (or when a stranger's failed decoy precedes Gary's real create), with nothing pinned — a reload in a fresh browser before SEAL exists — `resolveCollection` gets `by: 'other'`, the real collection is quietly ignored (an `ignoredBox`, not the prominent "pin it" warning, which is reserved for `unverifiable`), and step 0 is offered again, creating a duplicate collection naming MINT's PDA.

- **What an accident gains:** no theft and no holder value (nothing has minted); the cost is a duplicate collection and an operator who must notice the ignored box and pin by hand, on the one page whose outputs are permanent. The round-39 B4 ruling was "a stranger's decoy can never stop the launch" — this does not violate it (step 0 is still offered), which is why it is LOW and not higher.
- **Evidence if I am right:** offline, drive `collectionCreator` with a mock connection whose oldest signature's transaction has `meta.err` set and a later one is a successful launch-key `CreateCollectionV2` for the address — today it returns `'other'`; on a validator, a failed create followed by a successful one at the same address yields a history where the page offers step 0 with the real collection ignored. Both are measurable without mainnet.
- **Fix:** walk forward from the oldest signature to the first transaction that succeeded AND is a `CreateCollectionV2` for the address AND was paid and signed by the launch key, and classify on that one; or classify a failed oldest as `unverifiable` so it gets the prominent "pin it" treatment instead of a quiet ignore. Add a `ceremony.test.mjs` arm in the mock-conn shape above.

## R1. Custody — the seal/burn pairing

Attacked and could not break:

- **CPI wrappers.** A wrapped open reports the outer instruction's index; SEAL's forward walk then needs a genuine top-level burn for the same asset and owner, and BURN's backward walk over top-level instructions never sees the wrapped open (`NoPrecedingOpen`). A wrapped burn passes BURN's own pairing if a real open exists, but dies at MINT: `retire_redeemed` requires stack height exactly `TRANSACTION_LEVEL_STACK_HEIGHT + 1`, and top→wrapper→BURN→MINT puts MINT at 4. Both directions revert the whole transaction, thaw included. WR.1–WR.4 measure this; my read of the stack-height and sysvar logic agrees.
- **Two vaults, one transaction.** Both halves bind asset AND owner at fixed account positions (0 and 2), so neither half can be borrowed from a cohabiting redemption (3.9, 3.10, 4.10, 4.10a). The burn need not be last; nothing can act on the tombstone after it.
- **Account-index binding.** The positions are pinned constants in both programs, asserted against the Anchor derivations in the suite (3.1a–3.1f, 3.1q–3.1s), and the coupling fails closed (a drift breaks the match and halts redemption, never permits one).
- **The emptiness proof.** Reserve loop: every reserve mint's ATA under BOTH token programs must be declared; a token-owned account there must be PDA-owned, delegate-free, close-authority-free, exactly 165 bytes, and zero-balance; a Token-2022 ATA (170 bytes, measured) hits `ReserveHasExtensions`; a T22 ATA for a classic mint cannot exist (probe F4.2). Second loop: any declared Core account that is a live AssetV1 refuses (`VaultStillHoldsAVault`); any declared PDA-owned token account gets the same six checks. Undeclared holdings are destroyed — that is accepted limit 44, not a new finding.
- **A thawed vault leaving a transaction unburned.** SEAL thaws only with a matching burn later in the transaction; if that burn fails for any reason (rate limit, emptiness, retire), the transaction reverts and the thaw with it. There is no instruction sequence that persists a thaw.

No defect found in the pairing.

## R1s. The sweep helper

- **(a) Who can drive it.** Directly, it needs the asset-signer PDA's signature, which only Core produces, via `ExecuteV1`, which the pinned Core approves only for the asset's owner — and only on a thawed vault, since the PermanentFreezeExecute plugin rejects Execute while sealed (3.7, S6.2, SR.5/5a/5c/5d measure all of this on the pinned binary). The one plugin route that could approve anyone else (AgentIdentity) needs the collection's update authority, MINT's off-curve PDA, and no instruction in any of our programs adds an adapter (SR.5b, R24.1a/1c). Reached while frozen: no.
- **(b) The pair list.** Same source twice: the first pair closes it, the second reads a System-owned account and refuses `IllegalOwner` (SR.12a, and SR.12b pins that the refusal is the second, closed source). Destination twice: both transfers land, fine. Source-is-destination: refused, because `src_owner == signer` and `to_owner == dest` with `signer != dest` cannot both hold. wSOL source: swept and closed like any classic account. Delegate on a source: irrelevant to an owner-signed transfer and close. Kept close authority: the close reverts the whole call (R36.C5, 0x4) — the page moves such balances with a plain transfer instead. Frozen source: the transfer reverts (SR.14, 0x11). Non-ATA destination: any classic account of the destination wallet with the right mint works. Destination = the vault's own signer: refused (SR.10). Destination = another vault's signer: allowed, but that is the owner's own signed choice of where their own money goes, not a protocol hole. Odd list: `NotEnoughAccountKeys`. Zero pairs: lamports-only (SR.13).
- **(c) Destination not compared to the owner.** Safe, because (a) means the destination is always the owner's own choice; the page sets it to the owner and `signExact` pins the message. A sub-rent credit to a nonexistent destination is refused by the runtime (R41.C8a-c, now measured); the canonical destination (the owner, who pays the fee) always exists. A non-System destination takes the lamports fine (R27.S1).
- **(d) The lamport sweep.** It reads `signer.lamports()` at execution and empties a 0-data system account to zero; Core's Execute does not re-fund the PDA, and nothing else in the transaction can, except an instruction the owner themselves included. BURN's `lamports() == 0` reads exactly what the sweep left.
- **(e) Interaction with BURN's proof.** A closed reserve account is System-owned at BURN's check and skipped for the right reason (SR.4 lands). A reserve ATA that does not exist at page-build is created in the prior transaction (item 42); a stranger's later deposit into it is swept live. I could not construct an account a stranger can create for the vault that both escapes the sweep and passes BURN with value: T22-ATA-for-classic-mint is refused by the ATA program; a non-ATA classic account is sweepable when named and destroyed when not (accepted 44); a T22 non-ATA account is refused when declared and destroyed when not; a nested Core asset is refused when declared and rescued (CBOB) or destroyed (foreign, accepted 9/44) when not.
- **(f) Fit.** S8.0's 1,061 bytes is the measured four-instruction shape (claim + open + helper sweep of three reserves + burn, owner-payer); +52 for both compute-budget instructions and +96 for a separate fee payer gives ~1,209 of 1,232. A fourth reserve cannot exist (MAX_RESERVE_MINTS = 3, written once). The in-line monthly run's pool account is already in the measured shape (BURN carries it to `retire_redeemed`).
- **(g) Evidence.** SR.0–SR.14 and S8/S9b read as real arms with reason pins; SR.12b specifically guards the "refused for the wrong reason" case on the duplicate-source arm. `build-mainnet.sh` proves the helper's mainnet bytes identical to the localnet build AND to `target/deploy` (the bytes the suite and sim deployed); the helper has no `localnet` feature, so the tested bytes are the shipped bytes. The four keyed programs differ by the INIT_AUTHORITY swap only, which the script proves behaviorally and states honestly as not byte-proven — stated, not hidden.

No defect found in the helper.

## R2. The community pool

**The invariant "pool ≥ ceil(owed)" holds by construction, and I verified the arithmetic rather than trusting P.32:** `credit` adds `delta*w ≤ avail*SCALE` where `avail = balance − ceil(owed)`, so `owed_new ≤ ceil(owed_old)*SCALE + (balance − ceil(owed_old))*SCALE = balance*SCALE`; `claim` reduces pool and owed by the same sats; `join` adds weight with `debt = w*acc` (owed 0); `reweigh`/`expire_boost` move owed into `carry` without touching `owed_scaled`; `retire` only subtracts. `distribute` refuses `PoolShort` defensively.

**Counters under every ordering I could construct:** `activate` increments `pending_count` and `pending_this_epoch` together; `advance_epoch` zeroes only the latter; `join` requires `dist_epoch > request_epoch`, so it never owes a `pending_this_epoch` decrement; `retire` on a pending vault decrements `pending_this_epoch` only when `request_epoch == dist_epoch` (F21 measures both branches). `waiting_to_join = pending_count − pending_this_epoch` cannot underflow. The launch tick requires `!burn && pending_this_epoch > 0` with nobody waiting, so the first-activator attack is refused (3c.A3) and the join gate is refused before any $GARY burns (3c.A4b, 3c.A6c).

**Liveness:** `JoinWaitingFirst` is clearable by anyone (a free `claim` joins), `BoostsExpireFirst` is clearable by anyone (`expire_boosts` needs only records, never a token account), and a frozen pool forfeits rather than locks a redemption (3c.F0–F3). An explicit `distribute` from a frozen pool credits without delivering — that is stated in SPEC (red-team 3 finding 1's residue), not a new finding. No ordering I found makes distributions or redemptions impossible for others, and none breaks the invariant.

## R2b. The $CBOB boost

- **Exactly N distributions.** Bought at epoch E with end E+N; it earns E+1…E+N; the advance into E+N makes it due; `BoostsExpireFirst` blocks any further distribution until expiry; expiry reweighs at the accumulator its last distribution left. The two orderings (boost-then-distribute, distribute-then-boost) are measured (BO.21, BO.35), and the month-due case credits the old weight first (BO.22).
- **Nothing lost or gained on a weight change.** `reweigh` moves `owed_of` into `carry` and restarts debt at the new weight; `owed_scaled` is untouched; expiry inside a claim pays the boosted share whole, including into a frozen destination where it stays owed and is paid once when thawed (BO.37/37a).
- **Ring agreement past epoch 64.** `MAX_BOOST_EPOCHS_BOUND = 63` means every boost in a ring slot shares one end epoch; `advance_epoch` is unreachable while `boosts_due > 0` (both `distribute` and `monthly_inline` gate on it), so a slot is zeroed before it can be refilled. The host tests drive this through the program's own functions over 260 epochs with a model rebuilt from the records, with coverage minimums so it cannot pass by never reaching a branch; `tests/expiry-budget.mjs` executes twenty distinct due expiries under the default budget on a real validator.
- **No double/early/never expiry, no distribution blockade.** `expire_boost` requires due; `unschedule_boost` picks the due vs scheduled branch by `dist_epoch >= boost_end_epoch`; retire handles both (BO.16/17/38). Owner-only with the buyer's terms, one-sided by ruling (BO.6, BO.26, BO.30/31).

No defect found in the boost.

## R3. The level draw

The SlotHashes parse pins the sysvar key, bounds the count at 512, checks the buffer against the count, takes the smallest produced slot in `[want, want+64]`, and refuses an all-zero hash; the host tests cover skipped slots at A, B and C against an independent model, a full 512-entry buffer, and malformed inputs. ## Given that no human firm will ever see this and the programs will be immutable: what AI audit structurally cannot do, and what to do before launch

1. **Run the dress rehearsal for real (item 22), because it is the only evidence class this process has never produced.** The suite, sim and fork all run on a local validator. Nothing has ever run a distribution, a revenue cycle, or the alarm against a live cluster with real RPC rate limits, real DAS lag, real Pyth latency and ~2,100 vaults. Do item 22's five named items with their signatures recorded: the crank's live passes, the alarm's live rehearsal-mode passes, one full revenue cycle through Orca and one through Meteora with Orca forced to refuse, one forced post-sweep failure walked through the hand recovery to a clean `--audit`, and the DAS burned-asset read. No assertion suite substitutes for these; they are the only test of the parts that are I/O, not arithmetic.
2. **Sign the real pages with a real Phantom on a real phone and a real desktop extension.** The e2e and mock use keypairs and a test wallet. `signExact`'s byte-equality refusal exists precisely because some wallets inject or reorder instructions; whether Phantom's current build passes it, on the actual redemption, claim, buy and ceremony flows, is knowable only by doing it. One signed redemption of a dusted, stray-carrying rehearsal vault through the published-shape page is worth more than another hundred offline assertions.
3. **Exercise the Squads return path with the real Squads v4 vault.** The e2e stands in a local keypair for `bank_treasury`. `rescue_nested` lands the vault on an off-curve Squads vault whose return is a person's act; do one real rescue and one real return on the rehearsal deployment before a holder's vault depends on it.
4. **Have a human read the four decoded initialize transactions against the ruled values before signing.** The checker validates the JSON, not the signed transaction (item 38's own warning). The ceremony shows the values in plain words; Gary must actually read them — charter dates, the three tighten bounds, the guardian, the operator, the PoB root — because after the lock a wrong value is permanent and no alarm fires before it is written.
5. **Run a tabletop for the things the alarm can only detect.** Core, Orca, Meteora and Pyth are upgradeable by keys nobody here controls; Coinbase can freeze cbBTC. The alarm pages; it cannot prevent. Rehearse the human half once: "Core upgraded and redemptions refuse" and "the pool is frozen during a redemption rush" — who reads the page, who decides, what holders are told. Immutable programs mean the runbook is the only patch.
6. **Treat the box as compromised once, on purpose.** The revenue ledger, crontab and alarm are one user; no same-tree check vouches for them (limit 10's own admission). Before launch, one exercise: an operator with only the chain (not the box) reconstructs the revenue ledger from the transaction walk and confirms the alarm's state matches. If that is hard, fix the procedure now, because after launch it is the only audit of the trusted hop that survives a box compromise.
7. **Do the key ceremonies as ceremonies, not as commands.** The deploy authority, the $CBOB release wallet, the swap operator key, the PoB collection's hot wallet, and Gary's Phantom (INIT_AUTHORITY and guardian) are each a single point whose loss or theft has a stated, bounded, but real cost. Generation, backup, deletion and (for the hot wallet) the 7-day window's operational discipline are human acts no suite covers; write them down, do them with a witness, and record the hashes.
8. **Keep the two-clean-rounds gate honest about its own failure mode.** This process's most repeated defect was not in the programs; it was gates whose inputs changed shape underneath them (the coverage gate twice, the floors twice). The substitute for a human firm is the measurement discipline plus the coverage gate — so before the freeze is declared, run `scripts/audit-coverage.sh` strict, re-run the rehearsal-tree proof at the release commit (item 53 is stale by its own admission), and have one person who did not write the gate read the gate.
