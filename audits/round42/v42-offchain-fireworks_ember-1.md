## R1. The crank (`bank/crank.mjs`)

I looked for the four named shapes:

- **A plan the program refuses.** I traced every instruction's account order against MINT's `#[derive(Accounts)]` (reschedule/capture/reveal/retire/claim/expire/split/distribute/activate) — all match, including the two non-obvious ones: `split_revenue`'s config is *not* `mut` on chain and the crank sends it read-only; `distribute`'s `pool_token` is not `mut` and the crank sends it read-only. The tick is planned only when `w == 0`, `pending_this_epoch > 0` *after* this pass's retirements of this-epoch requesters (the L3 subtraction), the pool reads `ok`, and no eligible vault is unreadable — matching MINT's `NoActiveVaults`/`JoinWaitingFirst` order. A planned credit requires `avail > 0` against post-retire, post-split state, so `NothingToDistribute` and `PoolShort` are not plannable. The refused-distribute re-judge (`judgeDistributeRefusal`) treats the race codes as benign only when `dist_epoch` or `last_distribute_at` moved; `PoolShort` never. The one false-page residue: a 2-second Clock regression across the exact due boundary pages "action failed" once. Loud direction, not a defect.
- **A plan that pays or joins a dead vault.** `assets[r.asset] === 'burned'` → retired, never joined or paid; `'other'` (null read) → not joined, not paid, reported, and *no distribution planned* (so `JoinWaitingFirst` can't fire on chain). The preJoin destination is `r.vault_ata`, which MINT's pending-branch requires. A vault retired between plan and send is skipped on chain (`if !r.active { continue }`), not refused.
- **A reveal out of order.** Built from `revealed_total` upward, stops at the first not-ready, sent in order, breaks on the first failure or benign race. A capture planned this pass counts as ready only because the capture is sent first; if it lands, the reveal reads stored entropy; if it raced, MINT's inline capture or `AlreadyCaptured` covers it; if it was genuinely early, the reveal's `RevealTooEarly` is benign.
- **Value where the program doesn't pin it.** The crank signs only as fee payer plus the reveal's Core-rent payer; the selftest pins the discriminator list (`activate, capture_entropy, claim, distribute, expire_boosts, reschedule_reveal, retire_burned, reveal_level, split_revenue`) and the absence of any transfer construction. `split`/`distribute`/`claim` destinations are pinned on chain.

The money arithmetic in the planner (the part that decides *who* to claim) matches MINT line for line: preJoin debt = `weight × acc` at the pre-distribution accumulator (so a joined vault earns exactly this pass's share); a pre-expired boost's owed = `pendingScaled(boost, old acc) + levelWeight × (acc − oldAcc)`, which is what MINT's expire-then-claim computes; `retiringOwed` is subtracted before `available()` exactly as `retire` lowers `owed_scaled` before `distribute` reads it. The R39 C01 arm runs the *extracted* send block and pins the red-team-3 order (retire → join → expire → distribute → expire → activate → claims); I checked the extraction boundaries cover the whole send region.

## R5. The swap and the revenue cycle

- **(a) Oracle math.** `sats = lamports × sol.price × 10^(es−eb) / (btc.price × 10)`; the exponent split (num ×10^e / den ×10^−e) is correct for both signs; both divisions floor the *output*, the conservative direction for a minimum-out; the BigInt path can't overflow; the float `satsPerLamport` is used only by the 100 bps deviation gate where 1e-16 relative error is six orders under the gate. The pinned vector (280,355 / 276,149 at the 2026-10-05 prices) recomputes by hand.
- **(b) Pyth verification.** Offsets recomputed: disc 8, write_authority 32, verification tag at 40 (Full = 1, one byte), feed id 41..73, price i64 @73, conf u64 @81, expo i32 @89, publish_time i64 @93 — matches `PriceUpdateV2`. The account is a derived PDA of the push program *owned by the receiver*, so only the receiver program can write its data; a fabricated price needs a forged Wormhole VAA, an old-but-real price is bounded by the 180 s age rule, and the clock is the chain's (owner-checked Clock sysvar, byte 32), with a 30 s future bound. Ownership + derivation + Full + feed id is sufficient *given the stated trust* (limit 10(d)).
- **(c) Deviation filter.** `orcaSpot` = (sqrt/2⁶⁴)² in sats/lamport (wSOL 9 decimals, cbBTC 8 — raw units both ways, matching the oracle's sats/lamport); `meteoraSpot` = 1/(1+bin_step/10⁴)^activeId, the correct inversion for X=cbBTC, Y=wSOL. The L6 arms place the oracle 99/101 bps on both sides through the real `market()`.
- **(d) Minimum out.** Same `minSats` (oracle − 150 bps, floored) rides Orca's `other_amount_threshold` (offset 16, exact-input, a_to_b, min sqrt limit) and Meteora's `min_amount_out` (offset 16); both are cbBTC sats, which is what each program expects for this direction.
- **(e) The judge.** It is exact-sequence: seven instructions, each slot pinned by program, data bytes, and the value-moving keys; the amount, the floor, the Orca direction/limit, the output account (key 5 both venues), the wrap amount and destination, the single close back to the operator, no priority fee, no second signer, no Token instruction but SyncNative/CloseAccount. The two things it deliberately does not pin — the pool's own liquidity accounts and the bin/tick arrays — are refused on chain by the pool programs when wrong (a wrong array or vault fails the pool's own checks; the floor binds the rest), which is the stated trust. The eight round-25 tampers are each armed by name on both venues, and the round-24 judge is shown passing all eight (so the arms can fail).
- **(f) Derivations.** Orca tick arrays [s0, s0−span, s0−2span] for a_to_b (price pushed down), oracle PDA, vaults read from the pool; Meteora bin arrays [i, i+1, i+2] for Y→X (active bin pushed up), bitmap present-or-program-id, `host_fee_in` as the program id (Anchor None), event authority PDA, both token programs classic. An uninitialized array or a boundary crossing is the pool program's refusal → `refused` → next venue or open cycle; loud, nothing moves.
- **(g) wSOL.** A pre-existing balance returns on the close (R33.G4 measured); a frozen or delegated account fails the swap on chain, reverting the whole transaction including the wrap — the operator loses only the fee and the cycle stays open and loud; exact-input means nothing is left wrapped.
- **(h) Failure and retry.** `classifySendFailure` asks the chain: preflight refusal and landed-with-error and expired-never-landed are `refused` (next venue is safe); landed-and-succeeded is recorded; anything unsettled stops the cycle open. A confirmation timeout on a swap that later lands is recorded as landed, never double-swapped. The return and split record candidate signatures on uncertain sends; the split's catch falls back to the provably-empty proof only when the revenue ATA is genuinely empty, else throws open. Every path leaves the cycle open until a cbBTC return is recorded *and* the alarm's chain-anchored split check (`closesCycle`: at-or-after the return's block time, at least as large, claimed by no other cycle) can close it.
- **(i) Adversary bound.** Per cycle the take is bounded by the 150 bps floor relative to the oracle (≤ 0.15 SOL per 10 SOL cycle); a pool pushed past 100 bps is skipped, and at exactly 100 bps the floor still has ~50 bps of headroom after Orca's 16 bps fee. A stale-but-accepted oracle fails safe (a price drop makes the pool's output *under* the floor → refusal). The Meteora pool's thinness changes the push cost, not the bound, because the floor is oracle-relative. This matches limit 10's stated bound; not worse.
- **Operator key's worst case, re-bounded:** unchanged and as stated — the key calls `sweep_sol_for_swap` directly (the judge doesn't bind a thief who doesn't run the file), cap × cooldown windows until the guardian stops, never more than the PDA holds above the reserve. The ledger cannot read a failed cycle as closed (`cycleIsOpen` requires a return *and* a split; a refused sweep carrying a sweep signature is itself CRITICAL).

**One recommendation, not a finding:** limit 10(d) accepts detection-without-prevention for the four third-party upgrade keys, and the bound (cap × windows until the guardian stops) is the same shape as the operator key's. What the documents don't say explicitly is that the hourly revenue job never reads the alarm's state, so the "windows" are human-response hours even though the page is urgent. A one-line hardening — `revenue.mjs` refuses to start a cycle while a `prog.{orca,meteora,pyth_receiver,pyth_push}.{hash,upgrade_authority}` drift stream is open — would make detection into prevention for the unattended case, at the cost of halting royalty cycles during routine third-party upgrades until a human clears them.
