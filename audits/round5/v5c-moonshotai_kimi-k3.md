# FINDINGS

**1. HIGH — BURN never cross-checks `reserve_mints`; a SEAL-added mint is invisible to burn (D6 confirmed).**
`burn_vault` reads only `d[40..72]` (collection) and `d[72..104]` (bank) from the SEAL config. The derive/require/check loop iterates BURN's *own* `cfg.reserve_mints`. Exploit: (1) admin calls SEAL `update_config` adding mint X (additive-only, explicitly allowed); every SEAL `close_redemption` now demands X's ATA. (2) BURN's config isn't updated — three configs, three admins, one slip; the exact failure the "canonical config" pattern exists to catch. (3) A vault legitimately holds X in its PDA's ATA. (4) Owner+Bank sign `burn_vault` declaring only BURN's mints' accounts. X's ATA is never derived, never required, never checked; `lamports()==0` passes because the balance sits in the token account — the v1 lesson. (5) BurnV1 destroys the asset; X is stranded behind a PDA that can never sign again. Permanent destruction with valid owner+Bank signatures, while the BURN header comment claims the cross-check defeats "a trimmed reserve list." It inspects no list at all. **Fix:** parse `reserve_mints` from the SEAL config bytes (u32 len at [104..108], then 32-byte entries) and iterate *that* list, or require BURN's list ⊇ SEAL's in the cross-check.

**2. HIGH — Charter provenance is never written, and the first redemption wipes all attributes.**
`mint_vault` encodes the Attributes plugin with `attribute_list = []` and accepts no provenance args. `mark_opened` issues `UpdatePluginV1(Attributes{[{"redemption","opened"}]})`, which **replaces the list wholesale**. The business states provenance (Notice serial, Governor standing) is stamped at mint and is the ONLY surviving record after the Proof-of-Burn token and Notice are destroyed. No instruction in any of the three programs can ever write it: the plugin authority is the seal PDA, and SEAL writes only the redemption pair. And if provenance somehow existed, the first open/close erases it — a charter vault redeemed once loses its charter identity forever. Provenance record and anti-fraud stamp share one overwrite-only slot. **Fix:** add provenance pairs to `mint_vault` args and encode them in the CreateV2 list; make `mark_opened` read the existing Attributes from the asset account and re-issue the full list plus the redemption pair (or put the stamp in a separate plugin).

**3. HIGH — MINT admin can seize governance and redirect the 85%.**
`update_wiring` (admin signature only, no vote, no timelock) rotates `governance` and `treasury`. Neither exists in the SEAL config, so the divergence cross-check cannot catch it. Exploit: admin (rogue/compromised Squads signers) calls `update_wiring(governance=<own key>, treasury=<own account>)`, then `set_round(price=0, cap=0, opens_at=now-1, closes_at=i64::MAX)`, then mints to itself — the per-mint Bank co-signature is the only remaining brake — while 100% of future mint revenue flows to the admin. The header's "It may NOT set the round or the price — that is the governors' job and theirs alone" is unenforced; the 85/15 split has no on-chain existence (one treasury account). **Fix:** governance rotation requires the incumbent governance signature or a timelock; treasury rotation requires governance approval; enforce 85/15 on-chain with two destinations in `mint_vault`.

**4. MEDIUM — No lifetime supply enforcement; `minted_total` is write-only telemetry.**
No `require!` ever reads `minted_total`. `cap == 0` means unlimited; `set_round` resets `minted_this_round`, so any per-round cap is liftable by opening a new round — the very thing `minted_total`'s comment claims it prevents. Worst ratified vote: `price=0, cap=0, opens_at` in the past, `closes_at=i64::MAX` → unlimited free mints (Bank co-sig permitting), permanently diluting one-vote-per-vault governance and the 85% pool. The ~2,100 figure exists only in the brief. Also expressible: `price=u64::MAX` (every mint's transfer fails — minting DoS) and instant mid-round repricing between a buyer's simulation and landing. **Fix:** `require!(minted_total < MAX_SUPPLY)`; require `cap > 0` and `price > 0` for non-charter rounds; new rounds take effect only after the current round closes.

**5. MEDIUM — Fixed-offset SEAL-config reads: no discriminator/version check; `SEAL_PROGRAM_ID` is compile-time.**
MINT/BURN check owner and `len >= 104`, then read fixed offsets; they never verify `d[0..8] == Config::DISCRIMINATOR`. A SEAL upgrade that inserts/reorders a field before `bank` makes both read garbage → `WiringDiverged` → mint and burn halt until rebuilt (fail-closed, but redemption-only service for existing customers). A SEAL redeploy at a new address is silently ignored: MINT/BURN keep reading the old config and deriving the old seal PDA — and existing vaults' permanent plugin authority is create-only, pointing at the old seal PDA forever. The fleet can never migrate. **Fix:** check the discriminator, add a version byte to Config, make the seal program id a config value rotatable with governance approval.

**6. LOW — `burn_vault`'s `lamports()==0` is a 1-lamport DoS — but keep the check.**
Anyone can system-transfer dust to the asset_signer PDA and block burn. Curable: owner+Bank open → Execute a system transfer sweeping the dust → close → burn. Do NOT drop the check (see D4): BurnV1 never receives the PDA and cannot sweep it; dropping it strands — destroys — whatever lamports are legitimately there.

**7. LOW — `mint_vault`'s recipient never signs; only the asset-signer PDA is refused as owner.**
`owner` is an `UncheckedAccount`. With a Bank co-signature, a vault can be minted to any pubkey — including the seal PDA, mint PDA, or a config PDA that can never produce an owner signature — taking real payment for a permanently bricked vault. The Bank's simulation is the only guard. **Fix:** reject the programs' own PDAs, or require the recipient's signature.

**8. Informational.** Redemptions cannot be CPI-wrapped: the introspection sees only top-level instructions, so any future orchestrator that CPIs open/close makes the scan fail — fail-closed, but plan Bank tooling accordingly. `mint_vault`'s comment "its update authority must be mint_authority" is enforced only implicitly by the CreateV2 CPI failing, not by any check.

## WHAT I COULD NOT BREAK
- The 2-of-2: open and close both require owner+Bank; the open↔close introspection binds asset and owner; close validates bank/config itself; a matched-but-failing close rolls back the open atomically. No thaw-without-close, no tx ending thawed, no duplicate-instruction or ALT bypass; CPI-wrapping breaks the scan, fail-closed.
- Mid-tx ownership change: any transfer between open and close makes the scanned close fail `NotTheOwner` → full rollback.
- Reserve ATA hygiene: the checked bytes are exactly the fields the Token program itself reads; extensions (len≠165) refused; non-token accounts at ATA addresses correctly skipped.
- Stamp monotonicity: only the seal PDA can write Attributes; SEAL writes only "opened"; no removal path. Every value-removing path that leaves a resalable asset passes through `close_redemption` and is stamped (bare BurnV1 leaves no asset to resell).
- Mint payment atomicity: transfer and CreateV2 are one instruction; failure refunds automatically.

## THE SINGLE THING
Make BURN read the reserve set from the SEAL config it already trusts (parse the vec at offset 104). Today, one routine admin addition of a reserve mint to SEAL silently turns `burn_vault` into the destroy-customer-tokens path the entire three-program split was built to eliminate — with the owner's and the Bank's signatures on it.

# ADJUDICATIONS

**D1 — REJECTED.** BurnV1's only argument is `compression_proof: Option<CompressionProof>`; Borsh serializes an Option as a one-byte tag, so `[12, 0]` is exactly "BurnV1, None" — the 0 is mandatory, not extra. For CreateV2 the second byte is the leading u8 of the args struct on the deployed build. Decisively: the suite mints and burns real vaults against real cloned mainnet Core. "Every call reverts" is refuted by observation; this is precisely the class of prior finding that was wrong.

**D2 — REJECTED.** SPL Token packs `COption<Pubkey>` as a **four-byte** little-endian tag plus a 32-byte payload (36 bytes total) — which is why delegate spans [72..108] and close_authority [129..165]. The code checks exactly the 4-byte tags ([72..76], [129..133]) and `delegated_amount` [121..129]: precisely the bytes `Revoke` overwrites (tag := [0;4], delegated_amount := 0) and precisely the bytes the Token program itself matches in `unpack_coption_key`. The stale-payload phenomenon the auditor describes is real but lives in [76..108] and [133..165], which the code never reads. "1-byte tag" misreads the layout; there is no trap.

**D3 — REJECTED.** The treasury transfer and the CreateV2 CPI are two CPIs inside a *single* instruction. Solana rolls back the entire transaction — including the already-executed transfer — if any later step fails. Ordering inside an atomic instruction cannot strand a payment. "Paid and received nothing" is impossible.

**D4 — REJECTED.** The griefing observation is real — anyone may send lamports to the PDA and block burn — but the proposed fix is mechanically false and dangerous: BurnV1's account list never includes the asset_signer PDA, so Core cannot "sweep remaining lamports to the payer." Dropping the check would strand (destroy) arbitrary lamports an owner legitimately held there, re-opening a destroy-value path. The DoS is curable today (open → Execute a system transfer of the dust → close → burn), so the check is the correct trade.

**D5 — REJECTED.** `PermanentFreezeExecute` is a single-field struct `{ frozen: bool }`; the byte after the plugin ordinal *is* that bool, and 1 = true. The authority tuple `[1][3][32 bytes]` is exactly `Option::Some(PluginAuthority::Address(pubkey))` in Borsh (None=0, Owner=1, UpdateAuthority=2, Address=3). If the ordinal or layout were wrong, CreateV2 would fail to deserialize and revert — it cannot silently yield an unfrozen plugin. And the suite's open/close calls `UpdatePluginV1(PermanentFreezeExecute)`, which Core rejects unless the asset actually carries that plugin — so the plugin demonstrably exists, and since it exists, `frozen=true` at birth. Asserting `frozen` post-mint is fine hygiene; the claimed risk mechanism is refuted by the suite itself.

**D6 — UPHELD.** `burn_vault` reads only collection [40..72] and bank [72..104] from the SEAL config; it never parses the `reserve_mints` vec at [104..]. The derive/require/check loop iterates BURN's own list. After SEAL's admin adds a reserve mint (SEAL's `update_config` is additive-only), redemptions check the new mint's ATA while burns stay blind to it: a vault holding it burns cleanly if the caller simply omits that ATA from the declared accounts, stranding the tokens behind a PDA that can never sign again. The BURN header comment claims the cross-check defeats "a trimmed reserve list"; it does not inspect the list at all. Finding 1 above.
