## R2. The community pool's money

**The invariant "the pool always holds at least ceil(owed)" holds by construction.** `distribute`/`monthly_inline` credit only `balance − ceil(owed_scaled)`; since `delta·w ≤ avail·SCALE`, the new owed never exceeds what the pool holds. `claim` subtracts exactly `pay·SCALE` from owed and pays exactly `pay` out of the pool, carrying the sub-sat remainder. `retire` (both paths) subtracts the full pending share from owed — the forfeit and bare-burn paths return the share to the pool as unowed, the redeemed path requires pending < 1 sat first (`ClaimBeforeBurn`) unless forfeiting. Nothing else moves pool tokens: the only transfer out is `claim`'s, signed by the config PDA, paying only a recorded debt into the vault's recorded ATA. `PoolShort` is unreachable defensive refusal.

**Counters under every ordering.** `pending_count`/`pending_this_epoch`: request increments both; `advance_epoch` resets `pending_this_epoch`; `join` decrements only `pending_count` (correct — a joinable vault requested in an earlier epoch); `retire` decrements `pending_this_epoch` only when `request_epoch == dist_epoch` (F21.1/F21.2 measure both retire orderings). No underflow path exists because `dist_epoch` only advances and a same-epoch retire implies the request is still counted. `active_count`/`total_active_weight` move in exact pairs through join/retire/reweigh. The boost ring/counters are verified against independent models over 260 epochs including wraps, early and due retires at wrapped indices (host tests, BO.34/38).

**Liveness.** `JoinWaitingFirst` blocks distributions while an eligible vault waits, but joining is permissionless and needs only the record and the recorded ATA address — no liveness check gates it, so no vault can be a permanent blocker. A bare-burned waiting vault can be joined by a claim (accepted limit 27) but is retired first by every crank pass and by anyone. The self-nested case is the one permanent exception — see Finding 4.

**Round 24 W11 / SPEC's weaker rule:** the code implements the weaker rule (revenue already *in the pool* when a vault joins is shared at the next distribution; only the distribution that ran *before* the join is excluded), which is what SPEC now states. ## R2b. The $CBOB boost

**Exactly N distributions:** the boost is bought at epoch e, `end = e + N` (N ≤ 63); the distribution that advances the epoch *to* `end` makes it due; the next distribution is refused (`BoostsExpireFirst`) until expired; `expire_boost` requires `dist_epoch >= end`. Counting both transaction orders ([boost, distribute] and [distribute, boost], BO.21/BO.35) gives exactly N. **Nothing earned is lost or gained on weight change:** `reweigh` moves the owed share to `carry` and restarts the debt at the new weight; `owed_of = weight·acc + carry − debt` is invariant across the change (verified in the host model and BO.7c). **The ring/counters agree past epoch 64:** the host test drives four wraps with early/due retires at wrapped slots and checks every ring slot per index against the records. **No double/early/never expiry:** double is blocked by `boost_weight == 0`, early by the due check plus the skip in `expire_boosts` (BO.10b), never by the gate plus permissionless expiry (records only — no token account needed). **Nobody can block distributions by boosting:** the gate forces expiry first and expiry is free; a vault whose token account is gone fails only its own claim, not the distribution. The buyer's terms are checked *before* the burn CPI (`BoostTermsMoved` burns nothing); the favourable-move asymmetry is the ruled one-sided rule, stated as such.

## Findings

### MEDIUM 1 — The autograph size boundary does not state or measure the level-FIFO-halt consequence
**Construct:** `programs/cbob-vault-mint/src/lib.rs`, `reveal_level` (the strict FIFO `require!(index == ctx.accounts.config.revealed_total)` with no skip path) against Metaplex Core's fixed 32 KiB heap on `UpdatePluginV1`; SPEC item 40's round-28 validation block; HOLDER-GUIDE "Things to know before you open".
**What an attacker gains:** a vault holder who adds an owner-managed Autograph plugin to their vault *before* its reveal (the reveal normally lands within minutes, so this is a race the owner can win deliberately), then grows it — alone, or with any stranger's signatures once the book exists, each packet-bounded to ~1 KB — past the size where the reveal's `UpdatePluginV1` exhausts Core's heap, permanently halts the level FIFO at that vault. Every later vault becomes unrevealable and unactivatable (never earns), while redemptions still work; the programs are immutable and Core cannot shrink the asset (measured), so there is no recovery. The guardian can stop sales but cannot restart the queue.
**Evidence if I am right:** a probe that grows an autograph on a FIFO-head vault until MINT's reveal reverts with Core's allocation error while signature additions still land. **Evidence against:** the current measurements — the reveal succeeded at 10,150 bytes where the *clear* failed, and additions failed at 56 empty signatures on a 2.8 KB asset — are consistent with the reveal being strictly cheaper than any autograph write at the same asset size (both deserialize the same asset; the reveal's payload is the ≤ 640-byte attribute list, the addition's is the whole signature list), which would make the halt unreachable. That ordering is an inference, not a measurement, and item 40 itself says its observations are "not a proof for every plugin shape or size combination."
**Fix:** before the lock, run the growth experiment once and record which fails first; add to item 40 and the holder guide the FIFO-halt consequence and the measured threshold (or the measured impossibility). This is an afternoon of execution on a validator and it converts my inference into either a closed boundary or a real number.
