## Findings

### F1 — HIGH (conditional on one measurement): a host vault's owner can take a vault nested in its deposit address, during the host's own redemption, via Core `ExecuteV1` → Core `TransferV1`

**Construct.** `programs/cbob-vaults/src/lib.rs open_for_redemption` thaws the host's `PermanentFreezeExecute`. Between that thaw and `burn_vault`, the owner may issue any Core `ExecuteV1` whose inner instruction is signed by the host's asset-signer PDA. That is the whole mechanism the sweep helper relies on (SR.4, S8). Nothing in SEAL, BURN or MINT constrains the inner program id. A nested CBOB vault `V` has `owner == host's asset-signer PDA` (9.2). Core approves a transfer of `V` for its owner; the owner here is a PDA that Core itself signs for inside `ExecuteV1`. So the host's owner can build: `open(host)`, `ExecuteV1(host, inner = Core TransferV1(asset=V, authority=<host PDA>, new_owner=<host owner>))`, `burn_vault(host)` with `V` **undeclared**. BURN refuses only *declared* Core assets (`VaultStillHoldsAVault`); an undeclared one is invisible (9.5). After the transaction the host is burned and `V` is an ordinary vault owned by the host's owner, who then redeems it at leisure.

**What it contradicts.** Accepted limit 58: "a sealed host cannot execute, so even a deliberate nest is stuck", and the review-35 ruling that a vault sent to the wrong deposit address must go to the Squads, "never to a live host's OWNER". HOLDER-GUIDE honest list: "if a vault ends up inside another vault ... anyone can run the rescue, which moves it to the Bank's multisig, and the multisig returns it to whoever sent it." Proven impossibility 3 says the nested vault is "unredeemable while it is there" — true, but it is not *un-extractable* by the host's owner.

**Who gains, who loses.** The host's owner gains a whole vault (and everything inside it, by redeeming it afterwards). The loser is whoever misdirected the vault — the exact accident the rescue was built for, and also the exact outcome a solicitation ("send your vault to this deposit address") would produce. The redeem page does not build this (it offers the rescue and otherwise leaves `V` for the post-burn rescue, e2e V39-2), so it needs a hand-built transaction, which is within any adversary's reach.

**What is uncertain, stated plainly.** Two things must be measured on the pinned Core binary:
1. Whether Core's `execute` processor refuses an inner `program_id == mpl-core` (I do not recall such a guard in `processor/execute.rs`; the Solana runtime itself permits direct self-recursion).
2. Whether Core keeps a borrow on the host's collection account across `invoke_signed` (the inner `TransferV1` of `V` needs the same CBOB collection account). If it does, the inner CPI fails with `AccountBorrowFailed`.

**Evidence that would exist if true.** A suite arm: nest `INNER` in `OUTER` (as 9.1), then one transaction `[ixOpen(OUTER), coreExecute(OUTER, inner = Core TransferV1(INNER → alice)), ixBurn(OUTER, declare(OUTER.pda))]`. If it lands, `fetchAsset(INNER).owner === alice`, `OUTER` is a tombstone, and `rescue_nested(INNER, OUTER)` refuses `NotNested`. If Core refuses, record the exact error as the gate-5 pin and this finding is closed. Note the `web/src/lib/ix.mjs coreExecute` builder already produces the outer shape; the inner is the SDK's `transferV1` instruction.

**If true, what can be done.** Nothing in the frozen programs (BURN cannot enumerate; SEAL cannot inspect inner instructions). The honest remedies are in the fixable layer: (a) the crank should send `rescue_nested` itself, every pass, for every nested CBOB vault `detectNestedVaults` finds (it is permissionless and the Squads returns it), which shrinks the window to one crank interval; (b) the holder guide and SPEC 58 must say that the host's owner can keep a vault sent to their deposit address if they open their own vault before the rescue runs; (c) the alarm's `nested_vault` should be URGENT. Severity if confirmed: HIGH (a holder's entire vault to a stranger, under a promise the guide makes in the present tense; requires the sender's mistake, which the design explicitly set out to cure).

### F2 — Measurement that must be mandatory before the lock, not "recommended": the combined owner-reachable asset shape at the FIFO head

Round 42 C6 and limit 40 already state that a Core `UpdatePluginV1` that cannot complete at the FIFO head halts `revealed_total` forever. R34.G1b measured the maximal single-signature shape and R33.G2a/G2b the many-signer shape, each revealed. The unmeasured corner is their union: the 640-byte attribute budget, the 64/200 name and URI, all five owner plugins, and an Autograph grown by many signers to the ~10,240-byte CPI ceiling (hundreds of `String` allocations rather than one). Core deserializes every plugin during lifecycle validation in a 32 KiB heap; the many-small-strings shape is the one most likely to exceed it.

Why this deserves "required" rather than "recommended": the consequence is not one vault. Every vault minted after the attacker's can never be revealed, so never activated, so never paid, for the life of an immutable program; the only release is the attacker burning their own vault. Holders can still crack (redemption needs no level), so it is not gate (c), but it is a permanent loss of the payout right for everyone behind it. Evidence: build the shape on one vault (the existing R33 wrapper's `SIGSPDA!`/`PADTAIL!` paths suffice), make it the FIFO head, and assert `reveal_level` lands at the default budget. If it fails, the only pre-lock remedy is a program change (e.g. `reveal_level` tolerating a failed Core write by still advancing the FIFO), which must be decided before step 11.

### F3 — INFO (documentation): the "launch cohort shares the backlog" rule degrades to a cohort of one if nobody has requested activation by the month mark

`distribute` and `monthly_inline` tick the epoch when `total_active_weight == 0` **only if `pending_this_epoch > 0`**. If no vault has requested by `charter_closes_at + 30 days`, nothing ticks; the first request afterwards is in epoch 0, the next host ticks immediately (the period is long past due), and that vault joins alone. A second requester minutes later is in epoch 1 and needs another distribution — which the first joiner can trigger with 100 $GARY, taking the whole backlog. The holder guide's "At that one-month mark, the vaults activated by then join" is silently vacuous in that case. Evidence: a suite arm where the first `activate` lands after the period has elapsed with `pending_count == 0`, followed by any host and a `claim`, shows `active_count == 1` and a burn distribution crediting everything to it. Repair: one sentence in HOLDER-GUIDE and SPEC ("if no vault has asked to join by the month mark, the first to ask afterwards joins alone and can take the backlog with a 100 $GARY burn before any later vault joins"). No code change; the behaviour is a consequence of the ruled two-step.

### F4 — INFO (test documentation): `web/test/e2e-localnet.mjs` header contradicts what the test asserts

The header says "the redeem plan must refuse the host and point at the rescue; the rescue returns it to the host's owner". The assertions say the opposite (V39-2: the plan does not refuse; the rescue goes to `bank_treasury`, never the host's owner, R1 asserts exactly that). A reader auditing the e2e from its summary is told the pre-round-39 rule. Fix the comment.

### F5 — INFO (documentation, limit 40 "worse than stated?"): a Core upgrade that enables asset compression gives any owner a FIFO-halt and a self-brick

`reveal_level` accepts exactly two shapes for the head vault: a live `AssetV1` (`d[0] == 1`) or the one-byte tombstone. Core's `CompressV1`/`DecompressV1` exist in its interface and are currently `NotAvailable` on the pinned binary. If a future Core enables them, an owner could compress the head vault into a `HashedAssetV1` (key 2): `reveal_level` refuses `WrongAsset`, forever, for every vault behind it; SEAL/BURN refuse `NotACoreAsset` for the compressed vault itself. Limit 40 names three Core-change consequences; this is a fourth of the same class and costs one sentence to state.

### F6 — INFO (limit 26 slightly worse than stated): A's and B's leaders can choose which rotation supplies C

`try_capture` targets B and C at the first produced slot of a group two rotations after the previous hash's slot. A leader who skips **all four** of its slots pushes the next target one group later, i.e. a different validator becomes B's or C's leader. So the "every OTHER leader's influence is removed" sentence holds only against content grinding; by skipping its whole rotation, A's or B's leader can hand C to a chosen neighbour (at the cost of its own blocks). SPEC 26 already concedes C's leader chooses among many draws; it should add that a colluding pair can also select who C's leader is. The holder guide's wording ("the validator producing the last of those blocks can pick among several results") remains true.

## R1. Custody: the pairing and the emptiness proof

Verified by reading, with the arms that pin each:

- **Pairing.** SEAL walks top-level instructions after itself for BURN's discriminator with asset at index 0 and owner at index 2; BURN walks before itself for SEAL's with the same two positions; `retire_redeemed` demands stack height 2 and that the current top-level instruction is BURN `burn_vault` naming the same asset at index 0. A CPI'd open reports the wrapper's index, so BURN never finds it (WR.3); a CPI'd burn reports the wrapper's index so SEAL never finds it (WR.2); `retire_redeemed` via a wrapper refuses (WR.1). Two vaults in one transaction pair independently and are then rate-limited (4.9, 4.10a, S9b). Both halves bind owner, so no borrowing across vaults (3.9, 3.10). A thawed vault cannot leave the transaction unburned: the burn that satisfied the walk must execute or the transaction reverts, and the burn always CPIs `BurnV1` on the same account it read. Sound.
- **Emptiness proof.** Both reserve derivations required, delegate/delegated-amount/close-authority tags at 72/121/129 (D2 probe), length exactly 165 (Token-2022 extensions refused; a T22 ATA for a classic mint cannot exist, F4.2 and the mainnet probe), lamports of the asset-signer zero, declared Core `AssetV1` refused regardless of its owner. A closed account passes because its owner is System (`continue`), which is the right reason: closed-by-the-helper is indistinguishable from never-created, and the page's prior transaction removes "never-created" (R1s(e) below). A non-ATA token account and a nested Core asset remain invisible by construction (impossibility 2).
- **The one hole in custody the proof cannot see is F1**: not the host's own reserves, but an asset the host's PDA owns, moved out before the burn by the host's owner.

## R1s. The sweep helper

- (a) Only the asset's owner: the helper requires `signer.is_signer`; called directly nobody can sign for a Core asset-signer PDA (SR.1); through Core, `ExecuteV1` is approved only for `authority == owner` (SR.5/5a/5c measured 0x1a for a stranger, an owner-added transfer delegate, and a collection update authority on a control). While frozen, Execute is refused 0x9 (3.7). Sound against the pinned Core; limit 40 states the dependency.
- (b) Pair list: duplicate source → second `read_token` sees a System-owned closed account → `IllegalOwner` (SR.12a, pinned to "Provided owner is not allowed" and *not* the source-owner log, SR.12b). A destination cannot be a source (owned by `dest`, and `dest != signer` is enforced, SR.10). Native wSOL source: transfer of the wrapped balance then close returns lamports to `dest`; **unmeasured** (recommended arm). Delegated source: owner transfer and close ignore delegates; a foreign close authority reverts the close (R36.C5). Frozen source with balance reverts (SR.14); frozen with zero is closed (round 30). Non-ATA destination accepted (owner and mint only). Destination = the vault's own signer refused (SR.10); destination = another vault's signer accepted: the owner's own choice, nobody else's loss, **unmeasured**. - (c) The destination is not compared with the owner, and that is safe *because of (a)*: the only party who can make the helper run on a vault is the party whose value it is. A lamport credit below rent to a non-existent destination is refused by the runtime (R41.C8a); a credit to a non-System account lands (R27.S1). The page names the fee-paying owner.
- (d) The lamport sweep reads `signer.lamports()` at execution and sends all of it; nothing inside the same transaction can deposit afterwards except the owner's own later instructions; Core's Execute does not fund the PDA; BURN then sees exactly zero (4.5, SR.4a's exact lamport ledger).
- (e) Nothing a stranger can create blocks the burn: the six required addresses are ATA PDAs that only the ATA program can occupy (R34.G2), a Token-2022 ATA for a classic mint is refused by the ATA program (probe), and a created-with-dust classic reserve ATA is swept live. The prior-transaction rule is sufficient: once the three reserve ATAs exist, a stranger can only deposit, never re-create. Non-ATA accounts and nested assets are destroyed or orphaned, never blocking (limits 44, 58).
- (f) S8.0 asserts the helper redemption (claim + open + Execute(3 pairs) + burn, owner paying) is at most 1,232 − 148 bytes; it measured 1,061. The real page sends no compute-budget instruction (R40.U1 measured units within 200,000 per instruction) and the owner pays, so the page's shape is the measured one; strays are dropped to fit (`plan-redeem.mjs`). A fourth reserve is impossible (no instruction adds one).
- (g) Arms: SR.* refusals are each pinned to the helper's own error string with the program named (attP). Deployment bytes: `build-mainnet.sh` compares `dist/cbob_vault_sweep.so` with its own localnet rebuild **and** with `target/deploy/cbob_vault_sweep.so`, the file `run-tests.sh` and `sim/run-sim.sh` deploy. Holds.

## R2. The pool

I re-derived the invariant "pool ≥ ceil(owed)" through every state transition: `credit` adds `delta·w ≤ avail·SCALE` with `avail = balance − ceil(owed)`, so `ceil(owed')` ≤ balance; `claim` subtracts exactly what it transferred; `join` sets `debt = w·acc`, `carry = 0` (owed 0, pool untouched); `reweigh` (boost, expiry) moves owed into `carry` and resets debt, pool and `owed_scaled` untouched; `retire` subtracts the vault's owed and leaves the tokens in the pool; the frozen-pool forfeit is the same subtraction. The sum of per-vault `w·acc + carry − debt` equals `owed_scaled` after each (host test N1 and `ledger()` in the suite assert it). Tokens leave the pool only through `claim`'s Transfer signed by the config PDA. SPEC's weaker W11 wording (a joined vault shares what is in the pool at its first distribution) is what the code does; the stronger wording is not claimed anywhere I can find.

Counters under every host ordering: `pending_count`/`pending_this_epoch` move in `activate` (+1/+1), `advance_epoch` (this-epoch → 0), `join` (−1 count), `retire` (−1 count, −1 this-epoch only if same epoch); F21.1 pins the two retire branches. `total_active_weight`/`active_count` move only in `join`, `reweigh`, `retire`. I found no ordering that breaks them, including `activate` carrying its own record in the crank (R24.5 reverts whole).

Liveness: `JoinWaitingFirst` is dischargeable by any `claim` naming the record and its recorded ATA address (the account need not exist); `BoostsExpireFirst` by `expire_boosts` with records only. The one liveness consequence nobody can discharge is F3's dormant case (not a block, a cohort of one).

## R2b. The boost

Exactly N: a boost bought at epoch e has weight in the credits that move e→e+1 … e+N−1→e+N, is due at e+N, and the gate refuses the next credit until expired (BO.21/21a/35/35a measure both one-transaction orderings). Ring correctness past 64: live ends lie in (e, e+63], distinct mod 64, and `advance_epoch` clears the slot it moves to `boosts_due`; the host test drives 260 epochs through the program's own functions with per-slot assertions. Expired twice/early/never: impossible by `boost_weight == 0` after expiry, the `dist_epoch >= end` requirement, and permissionlessness. Weight changes never gain or lose earned value (`reweigh`). The terms are one-sided by ruling (BO.30/30a). No way to block distributions through a vault whose token account is gone: `expire_boosts` needs no token account.
