## R1. Custody: the seal, the pairing, the emptiness proof

I attacked the pairing from every side the code allows:

- **CPI wrappers.** SEAL's forward walk starts at `current + 1` and matches `BURN_PROGRAM_ID` + discriminator + asset (idx 0) + owner (idx 2); BURN's backward walk matches SEAL + discriminator + asset (idx 0) + owner (idx 2). A wrapped open reports the OUTER index, so a wrapper would need a genuine top-level burn for the same asset and owner later in the transaction — and BURN independently demands a genuine top-level open before it. Both halves bind asset AND owner, so neither can be borrowed from another vault's redemption sharing the transaction. The suite's WR.1–WR.4 (through the test-only CPI forwarder) pin exactly this, and I re-derived the account-index bindings from both programs' `Accounts` structs: `vault_asset` is account 0 and `owner` account 2 in both `OpenForRedemption` and `BurnVault`, matching the constants.
- **Two vaults in one transaction.** The rate limit runs inside `burn_vault` before the emptiness proof, so a second paired redemption in one transaction is refused `RateLimited` (not `NoTerminalBurn`), which is the correct refusal — the pairing accepted it (4.10a, S9b).
- **Emptiness proof.** The reserve loop requires every reserve mint's ATA under **both** token programs to be declared, PDA-owned, undelegated, extension-free and empty; the second loop applies the same delegate/close/extension/amount checks to any other declared SPL-owned account owned by the PDA. A Token-2022 account with extensions is refused by length (`ReserveHasExtensions`) in both loops. A declared nested Core asset is refused (`VaultStillHoldsAVault`). A non-ATA token account holding value and simply not declared is invisible — that is the completeness gap, stated in SPEC, covered by the redeem page and the alarm, and unchanged by design.
- **A thawed vault leaving a transaction unburned.** Not possible: the thaw is a Core plugin update inside the same transaction; if the burn reverts, the thaw reverts with it. Nothing can re-seal mid-transaction and nothing can end the transaction holding a thawed vault, because the burn is the only instruction that thaws and the pairing is the only path to it.

**No defect found.**

## R1s. The sweep helper

- **(a) Access control.** The helper's whole authority is Core's `ExecuteV1` rule. Direct calls need the asset-signer's signature, which only Core can produce; through Core, the pinned binary approves Execute only for `authority == owner` (SR.5/SR.5a refuse a stranger and an owner-added transfer delegate on a genuinely thawed vault; SR.5b pins the collection authority to MINT's off-curve PDA; R24.1a refuses the AgentIdentity route to an owner). While the vault is still frozen, Execute is refused by the seal itself (SR.3's `0x9`), so the helper is unreachable outside a redemption.
- **(b) Pair list.** Source must be owned by the signer; destination must be owned by the one destination wallet with the same mint; `signer == dest` refused; duplicate sources fail on the second pass because the first closed the account (SR.12a, pinned to the second source's owner read, not the first guard); a frozen source reverts the whole opening (SR.14); a kept-close-authority account reverts the close (R36.C5) and the page moves it by plain transfer instead. An odd or zero-pair list is legal: zero pairs is the lamports-only sweep (SR.13).
- **(c) Destination checks.** The destination wallet is chosen by the transaction builder, but under (a) only the owner builds it, and the owner sweeping to any wallet of their choosing is the owner's own act. A lamport credit below rent exemption to a non-existent account is refused by the runtime (R41.C8a–c), so a vault wallet never holds a sub-rent balance.
- **(d) Lamport sweep.** `signer.lamports()` is read at execution; inside one atomic transaction nothing can land between it and the burn, and BURN's `lamports == 0` check sees exactly what the sweep left (SR.4a measures the exact delta including gifts, released rent and fees).
- **(e) Interaction with BURN's proof.** The helper closes what it empties, so the closed account passes BURN's reserve loop because its owner is no longer a token program (`continue`). A missing reserve ATA cannot be named by the helper, but anyone can create a classic ATA permissionlessly — the page's prior transaction creates the vault's missing reserve accounts (item 42), and a stranger's dust in a pre-created one is moved at execution, so it cannot block. A Token-2022 ATA for a classic mint cannot exist (F4.2, measured), a non-ATA token account is undeclared-and-destroyed (limit 44), a nested Core asset is rescued (item 58).
- **(f) Fit.** S8.0 measures the three-asset redemption through the helper, claim included, at 1,061 bytes with the owner as fee payer, with room computed for the compute-budget pair (+52) and a separate fee payer (+96). A fourth reserve mint cannot exist (`MAX_RESERVE_MINTS = 3`, written once at SEAL initialize).
- **(g) Evidence.** SR.0–SR.14 and S8.* cover every refusal branch with its reason pinned; the helper's mainnet bytes are proven identical to the tested localnet bytes and to `target/deploy` by `scripts/build-mainnet.sh` (no `localnet` feature exists in its crate, deliberately).

**No defect found.**

## R2. The community pool

I re-derived the invariant "the pool always holds at least ceil(owed)" from the arithmetic: `credit` adds `delta·w` to `owed_scaled` where `delta = avail·SCALE / w`, so `owed` grows by at most `avail` (floor), leaving the pool holding `balance − avail ≥ ceil(owed_before)`; `claim` subtracts exactly `pay·SCALE` from `owed_scaled` where `pay = floor(pending/SCALE) ≤ pending/SCALE`, so owed falls no faster than the balance; `retire` subtracts exactly `pending`. `distribute` refuses `PoolShort` when `balance < ceil(owed)`. The suite's `ledger()`/`books()` recompute the whole accounting from every record after every money operation, and P.32/BK.* pin it.

Counters under every ordering: `pending_count`/`pending_this_epoch` are maintained on request, join and retire (F21 covers a waiting vault redeemed and one bare-burned, both leaving both counters); `advance_epoch` is the single place the epoch moves and the single place `pending_this_epoch` resets and due boosts are counted from the ring. The `JoinWaitingFirst` gate is checked before any $GARY burns on both trigger paths, and `monthly_inline` degrades gracefully (logs, never refuses its host) when early, empty, blocked by a due boost or by waiting joins.

Liveness: a distribution can always be run — the burn path is permissionless for anyone holding 100 $GARY, the free path is permissionless once due, and the in-line run rides on five host instructions. Nobody can make distributions impossible: a vault whose token account is gone is skipped by `claim` (deferred, still owed), and `expire_boosts` needs only records, so a due boost can always be cleared without any token account.

**Round 24 W11 (revenue that arrived before a vault joined):** SPEC's weaker wording is the true one — a vault that joins shares revenue already sitting in the pool at the next distribution (that is the point of the launch tick), and the only edge left is unsplit revenue in the revenue address (limit 55, accepted). I checked `monthly_inline`'s pool read: it validates mint, owner and state against the config before reading the balance, so a junk account standing in for the pool cannot suppress or fake a run (`WrongPool` is the only refusal).

**R2b. The $CBOB boost.** I re-derived exactly-N from the ring: a boost is scheduled at `end = dist_epoch + N`; the distribution that makes it due is the Nth it earns (the one it rode in on counts, BO.21/BO.35 pin both orderings); no distribution runs while `boosts_due > 0`; `unschedule_boost`'s two branches (due / not due) both decrement the correct counter, including at wrapped ring indices past epoch 64 (BO.34, BO.38, host unit test N1 driving 260 epochs through the program's own functions). ## Findings

### LOW-1 (web, redeem page): a helper stray whose receiving account is missing is silently dropped from the opening at the press, not named as left behind

**Construct.** `web/src/lib/plan-redeem.mjs`, `planRedemption`. In the first plan (before the prior transaction), `canReceive` is always true (`!s.noPrior`), so `noAccount` is empty and every helper stray is delivered. The prior transaction creates the owner's ATA for each stray's mint (`needOwnerAta`). At the press (`noPrior = true`), `canReceive(a)` requires `s.ownerAtaExists.has(ownerAta(mint))`. If the holder's receiving account for a **promised** stray's mint does not exist at the press — because the prior transaction that would have created it was never sent (the holder pressed "Open this vault" without completing set-up, or the set-up transaction failed on a step after the creates) — the stray is spliced out of `helperStrays` and lands in `noAccount`, which produces an ack box ("There is no account of yours to receive it…"). That box is only shown in the **first** plan; at the press, `prepareOpening` returns `stop: 'ack'` only for boxes not in `consented`, and the `noAccount` box's id (`left:ADDR`) was in the first plan's `ack` list, so it is consented — but the stray itself was in `known` (it was in `helperStrays` at the check), so the late-arrival logic does not cover it (it did not arrive late; its destination vanished). The press therefore sends an opening that **does not move** a balance the holder was told would come to them, without the round 39 V39-1 re-read catching it, because V39-1 re-reads the *source* accounts (`s.known`), not the destination accounts.

**What a holder loses.** The stray's balance stays in the vault wallet and is destroyed with the burn, after the holder ticked a box saying it would come to them ("Your vault also holds N units of X. The opening moves it to you too.").

**Evidence if I am right.** Offline: build a snapshot where a helper stray's mint has no `ownerAtaExists` entry and `noPrior` is true; `planRedemption` puts it in `noAccount` and `left`, and the redemption built from it omits the pair. On the mock (`web/test/mock-rpc.mjs`): complete the check, skip the set-up transaction, press once — the sent redemption lacks the pair.

**Why this is LOW and not higher.** It requires the holder to abandon a set-up step the page performs for them, and the dry run (`prepareOpening`) shows the actual deltas before signing, so an attentive holder sees the missing `+N` line. But the box text they ticked said it would move.

**Fix.** At the press, a promised stray whose receiving account is missing should stop the press with its own box (the round 39 V39-1 treatment applied to destinations as well as sources), or the re-plan should demand the one set-up transaction rather than silently dropping the delivery.

### LOW-2 (web, ceremony): the ceremony's step-0 re-read cannot distinguish "landed" from "taken" for the collection keypair, so a retry after an unknown outcome can create a second collection

**Construct.** `web/src/pages/ceremony.mjs`, the `collection` step. `checkNewAddress` is called with `{ publicKey: ctx.newCollection.publicKey }` — a plain object with only a public key, and `makeKey` is `() => null`. If the state is `'taken'` (a stranger funded the address), `na.kp` is `null` and the code appends `TAKEN_NOTE` and re-reads — but `ctx.newCollection` is **unchanged**, so the re-rendered step 0 builds `coreCreateCollection` with the same funded keypair, which the network will refuse again, forever, until the page is reloaded (which regenerates the keypair). The buy and claim pages pass a real Keypair and a real `makeKey`, so they swap correctly; the ceremony deliberately passes only the public address (round 39 C04: the key is used to sign, nothing else) but that same deliberation removed the ability to regenerate.

**What an attacker gains.** Nothing of value: a stranger funding the collection address costs them the rent floor at an address they cannot spend from, and the ceremony is simply stuck until reload. But a **retry after an unknown outcome** (the create landed but the confirmation timed out) is the dangerous case: `checkNewAddress` returns `'landed'` (Core owns it with data) and the page correctly adopts it — that half is sound. The stuck case is only the stranger-funded one.

**Evidence if I am right.** Offline: call `checkNewAddress` with the ceremony's shape and a funded mock account; the returned `kp` is the same object, and `steps()` rebuilds the same instruction.

**Fix.** Regenerate the collection keypair on `'taken'` inside the ceremony (the key signs once and is never kept, so a fresh one is free), or refuse the step with a plain "reload the page" message instead of looping.

### INFO-1 (SPEC 46 residual): an owner-managed freeze delegate on an individual Proof of Burn can cost that holder their charter claim, and the alarm does not watch per-asset plugins

**Construct.** Core permits a PoB's *owner* to add an owner-managed `FreezeDelegate` and freeze their own asset. `claim_charter_vault`'s CPI burn of the PoB is then refused by Core while frozen, for the whole 7-day window, and the window can never reopen. The claim page refuses a PoB carrying plugins it cannot read, but an owner-added FreezeDelegate is readable and the page's frozen check (`plan-get.mjs`) catches it — so the page protects this holder; a holder claiming by any other client is not. The alarm watches the collection account, not the 240 assets (round 22's stated blind spot), so the freeze is not paged.

**Who loses.** Only the holder who froze their own PoB, to their own claim. No one else's vault, vote or payout is affected.

**Fix.** One sentence in SPEC 46's per-asset blind-spot paragraph naming owner-managed plugins alongside the hot key's, and one line in the holder guide's honest list.

### INFO-2 (docs): HOLDER-GUIDE's "the draw job checks every minute" understates the queue's real bound

The guide says "the draw job checks every minute, and busy queues can take longer." The real bound is stronger and worth saying plainly: a vault's draw is written only when every vault minted before it has been drawn (strict FIFO), so under a sustained mint burst a vault can wait many minutes, and if a vault ahead of it is never captured and never rescheduled the queue stalls until someone reschedules it. The alarm pages on reschedules and on a stalled queue, so this is detection-covered, but the guide's sentence could be read as "about a minute" rather than "behind every earlier vault." Wording only.
