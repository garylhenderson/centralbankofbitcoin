### R41-1 — MEDIUM — the launch ceremony treats a dusted config-PDA address as a fatal, unrecoverable state; the state is recoverable on chain, so the stop is false, and the recovery is the manual initialize the ceremony exists to replace

**Construct.** `web/src/lib/reads.mjs` `anchorAccount`:

```js
const a = await account(conn, addr, PLAIN[name] || name)
if (!a) return null
if (!a.owner.equals(program)) throw new ReadError(`${name} at ${addr} is not owned by its program.`)
```

used by `web/src/lib/ceremony-reads.mjs` `readStep` for the `seal`, `mint`, `burn` and `gov` steps; and `resolveCollection` in the same file, which for a non-null, non-SEAL-owned `SEAL_CFG` returns `conflict: 'the SEAL settings account is not owned by SEAL'`, which `web/src/pages/ceremony.mjs`'s preflight turns into a hard `STOP` (`if (conflict) { line(false, \`STOP: ${conflict}.\`); return null }`). A dusted MINT/BURN/GOV config passes preflight and instead aborts `steps()` at its step (the throw propagates to `run()`'s catch and prints a refusal box), after earlier steps have already landed.

**The attack.** The five program ids are claimed on mainnet and public; the four config addresses (`["config"]` under SEAL, `["mint-config"]` under MINT, `["burn-config"]` under BURN, `["gov-config"]` under GOV) are derived from them. Anyone, today, can send ≥ 650,240 lamports (mainnet's 0-byte rent floor) to each — a `SystemProgram.transfer` to a nonexistent address creates a System-owned, 0-byte account there, permanently (nobody can sign for that address to remove it). Total cost ≈ 0.0026 SOL, set-and-forget, no timing needed: the ceremony date is announced in advance.

**What the page does vs what the chain does.** The page reports a wrong-owner fatal state and stops. On chain, the state is recoverable: Anchor's `init` takes over a System-owned, zero-data account — **measured in this suite**: R31.W2a initializes SEAL's config over a stranger's pre-funded 1,000,000 lamports and asserts SEAL owns it afterwards. The mechanism (allocate + assign on an existing System-owned account) is size-independent, so all four configs initialize over dust. Only the page refuses.

**What an attacker gains.** A launch-day block of the sanctioned ceremony — the one-time road-step-10 gate — with a message that gives no hint the state is recoverable. The recovery is either a hand-built initialize transaction (twenty ordered arguments, exactly the error-prone manual path items 38 and 50 exist to eliminate; the ceremony is the only sanctioned builder in the tree) or a page fix, rebuild and re-run. No value is at risk; nothing is lost; the delay and the forced manual path are the damage.

**What it contradicts.** The project's own invariant, built across three rounds: round 37 V2's design and round 39 B4's replacement of round 38 V38-3's STOP exist precisely so that "a stranger's decoy can never stop the launch" (`web/README.md`: "a stranger's decoy can never stop the ceremony this way"). A dusted config PDA stops it. Round 40's drift-sweep instruction scoped the sweep to "every page that reads an ATA by address" — config PDAs are not ATA addresses, which is exactly why this site was missed while every ATA site was fixed.

**Evidence that would exist if I am right.** On a local validator: send 650,240+ lamports to SEAL's config PDA; load the ceremony page (localnet profile) or call `resolveCollection(conn, profile, baseIds, {})` — it returns the `conflict` and preflight prints `STOP: the SEAL settings account is not owned by SEAL`. Then send SEAL's initialize over that same account — it lands (R31.W2a already proves this half; the dust shape is the same System-owned/0-data state). The gap is only in the page's read.

**Fix.** Apply the `absentIfDust` semantics to the config-PDA reads the ceremony makes: in `anchorAccount` and in `resolveCollection`'s SEAL read, treat owner = System ∧ data length 0 as ABSENT (return `null` / "SEAL not initialized", no conflict), keeping the refusal for any other non-program owner. Post-launch this is unreachable (the configs exist and are program-owned), so the change is safe for every holder page that shares the reader. Add the mirror arms: an offline arm (a dusted config reads as absent, never as a conflict or a throw; control: a non-System foreign owner still stops), and an e2e arm that dusts all four config addresses before the ceremony and asserts every step still initializes and re-reads clean.

**Grading, honestly.** Round 40 graded the sibling finding (V40-2: ceremony ATA dust, recoverable by one CLI create) LOW. This one is the same user-visible consequence — a false permanent-failure STOP at the ceremony, for pocket change — but it blocks earlier (preflight), it can close the whole ceremony rather than one step, and its recovery is materially worse: one CLI `spl create` versus hand-writing an initialize. It is also performable today, before anyone is watching. MEDIUM is the honest grade; if the team judges the recovery acceptable (adapting the suite's initialize builders), LOW is defensible, but the false STOP and the violated "nothing a stranger does may stop the ceremony" invariant stand either way.

## R2 — The community pool's money

**The invariant "the pool always holds at least ceil(owed)" holds at every mutation.** `credit` adds `delta·w ≤ avail·SCALE` to `owed` while subtracting exactly `avail` from the balance, so `ceil(owed)` never exceeds the balance. `claim` subtracts `pay·SCALE` from `owed` and `pay` from the balance — the margin is unchanged. `retire` (all three variants) subtracts `pending < SCALE` from `owed` without touching the balance. `join` and `reweigh` never touch `owed`. `monthly_inline` uses `saturating_sub` on the ceil, so a short pool credits nothing. Claims are bounded per-vault by `floor(pending/SCALE)` and the sum of all `pending` equals `owed` (asserted by the suite's `ledger()` after every money operation in sections IN, 3c and P, and by `BK.*`), so the pool cannot be overdrawn. `PoolShort` is unreachable in honest operation.

**The counters.** `pending_count`/`pending_this_epoch`: requests increment both; `advance_epoch` zeroes the epoch counter; joins (which require `request_epoch < dist_epoch`) decrement only the total; retires decrement the epoch counter only when `request_epoch == dist_epoch`. The identity `waiting = pending_count − pending_this_epoch` cannot drift, and F21.1/F21.2 exercise both retire branches. `total_active_weight`, `active_count`, and the boost totals are asserted against a full re-read after every operation.

**Liveness.** Every gate is passable by anyone: `BoostsExpireFirst` (records-only, permissionless, and a claim stores the expiry even when the payment is deferred for a frozen destination — verified in the code path), `JoinWaitingFirst` (joining is a free claim), `MonthNotElapsed` (wait, or burn 100 $GARY — the burn is checked and CPI'd only after every gate, so a refused distribution burns nothing, PG.7a/3c.A6c). A frozen pool stops delivery but not redemption (the forfeit), and the in-line run never credits from a frozen pool. I could not construct a liveness deadlock.

## R2b — The $CBOB boost

**A boost earns exactly N.** Bought at epoch e with length N (1 ≤ N ≤ 63), it is live during the distributions that advance `dist_epoch` from e to e+N — exactly N of them — and due at e+N; the gate refuses the (N+1)-th until it is expired. Both transaction orderings are measured (BO.21/BO.21a for [boost, distribute], BO.35/BO.35a for [distribute, boost]). **Nothing earned is lost or gained at a weight change:** `reweigh` moves the owed share to `carry` and restarts the debt at the new weight, leaving `owed_of` invariant; claims settle to a sub-sat carry and restart the debt exactly. **The counters always agree:** the ring slot is set at purchase, consumed exactly once by `advance_epoch` (which zeroes it), and decremented by `unschedule_boost`'s not-due branch; `boosts_due` is the mirror on the due branch; `ring + due == active` is asserted per-slot over 260 epochs (four wraps) by the host test driving the program's own functions, including early retires at wrapped slots (BO.38) and due retires (BO.17). No record can be expired twice (`AlreadyRetired`/skip guards), early (`BoostNotDue`), or never (the gate plus the permissionless expiry). Nobody can block distributions by boosting (expiry needs only records) or by a vault whose token account is gone (same). The buyer's-terms rule is one-sided exactly as ruled, and the owner check reads the asset's owner bytes at execution (BO.33/33a).
