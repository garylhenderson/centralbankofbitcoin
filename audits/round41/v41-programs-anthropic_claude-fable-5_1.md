## R2. The pool

I re-derived the invariant **pool ≥ ceil(owed_scaled / 1e12)**:
- `credit`: `delta = floor(avail·S / w)`, `owed += delta·w ≤ avail·S`; since `delta·w` is an integer ≤ `avail·S`, `ceil((owed + delta·w)/S) ≤ ceil(owed/S) + avail = balance` (explicit path: `avail = balance − ceil(owed)`; inline path: `saturating_sub`). 
- `claim`: pays `pay = floor(pending/S)` whole sats and subtracts exactly `pay·S` from `owed`; `balance − pay ≥ ceil(owed/S) − pay = ceil((owed − pay·S)/S)`.
- `retire`/forfeit subtract from `owed` only.
- Nothing but the config PDA can move cbBTC out of the pool.

Per-vault accounting: `owed_of = w·acc + carry − debt` is always ≥ 0 because every write sets `debt = w·acc` (join, claim, reweigh, retire) with `carry ≥ 0` and `acc` monotone. A claim normalises to `carry = pending − pay·S`, `debt = w·acc`, so `owed_of` after = sub-sat carry exactly. `reweigh` moves the whole owed share to `carry` and restarts `debt` at the new weight, so a weight change gains and loses nothing (host test N1 asserts `owed_scaled == Σ owed_of` across 260 epochs). `total_active_weight` is added as the level weight at join and subtracted as `weight_of` (level + boost) at retire; boosts move it by `after − before`.

Counters: `pending_this_epoch` counts records with `pending && request_epoch == dist_epoch`; `advance_epoch` zeroes it, which is exactly right because every such record now has `request_epoch < dist_epoch`. `retire` of a pending record decrements `pending_count` and, only if same-epoch, `pending_this_epoch` (F21.1). `waiting_to_join` can never underflow.

Liveness: every gate has a permissionless exit that needs only records or keys: `JoinWaitingFirst` → `claim` with `(record, vault_ata-key)` pairs, which join without the destination account existing; `BoostsExpireFirst` → `expire_boosts` with records only; `NoActiveVaults` at launch → the free tick once due. A griefer who requests activation on many vaults (each a funded, sealed vault) only makes the crank send join-only claims; the vaults then share payouts, so it is not a block.

**Round 24 W11, SPEC's weaker rule:** "a vault is never credited by a distribution that ran before it joined" holds (join sets `debt = w·acc`). The stronger wording is false by design (the launch cohort shares the backlog), as SPEC says.

One behaviour worth stating plainly because the holder guide does not: **a 100 $GARY distribution resets the monthly clock** (`credit` stamps `last_distribute_at = now` on every path). A party burning 100 $GARY every 29 days keeps the free monthly path from ever becoming due. Nothing is lost (a burn distribution distributes everything), so this is not a defect; it is the meaning of "30 days since the last distribution", which the guide ("A payout is due every month") slightly over-promises as a cadence. INFO.

## R2b. The boost

Exactness: bought at epoch e after the host's `monthly_inline`, `end = e + N`; `advance_epoch` to `e+N` moves the ring slot to `boosts_due`; no `credit` runs while `boosts_due > 0` (both paths). So exactly N distributions (BO.21, BO.35 for both orders in one transaction). Ring: N ≤ 63 and due boosts leave the ring at the advance, so slot `(e+63) % 64 = (e−1) % 64` is empty at epoch e (I checked the only competitor would be a boost of 64 epochs, which cannot exist); host tests N1 and the ring model agree with that reading. `unschedule_boost` takes the due branch or the ring branch by `dist_epoch >= end` and `retire` always calls it for a boosted vault, so a vault whose token account is gone (bare burn) cannot leave a due boost behind (BO.16/17). Retired records keep `boost_weight` as history and every reader skips `retired`/`!active` first. A boost on a vault whose `vault_ata` is frozen expires inside `claim` before the deferral (BO.37). **No defect.**

## R3. The draw

`blockhash_in_window` is pinned to the sysvar id, bounds the declared count, checks the buffer length, refuses an all-zero hash, and picks the smallest produced slot in `[want, want+64]`. `try_capture`'s C is at most `reveal + 64 + 75 + 75 = reveal + 214 < 300`, and A ≥ `reveal` is always inside the 512-entry buffer at a capture inside the window (the sysvar holds 512 *entries*, i.e. produced slots, so it spans ≥ 512 slots). FIFO: `index == revealed_total`. Burned head: the draw is taken and the Core write skipped (L.11). Attribute re-supply: hash-checked, and only MINT's PDA can write the Attributes plugin; the five owner-managed plugin kinds are measured not to block the write (R26.P1-P6, R34.G1b). Minter influence: none beyond limit 25; crank operator: withholding only; slot leader: limit 26.

**Is 26 worse than stated? Slightly, in one direction (INFO, below):** limit 26 says the three-group stride "removes every other leader's influence". It removes their influence on the *hash*, but not on *who C's leader is*: because B targets the first slot of group gA+2 and the lookup takes the smallest produced slot ≥ want, a leader who skips its entire 4-slot group moves the next target one group later. So A's leader (by skipping all four slots of group gA) or B's leader (likewise) can each shift C into the next leader's rotation, at the price of four forfeited blocks. That is a one-bit choice of C's leader per intermediate leader, which matters only if they collude with a candidate C leader. The same mechanism is why a rescheduler's choice of `now` chooses C's leader group. Limit 26 already states a validator can time a mint or a reschedule; the sentence "removes every other leader's influence" should be narrowed.

HOLDER-GUIDE now says "pick among several results ... That can be enough to choose the level of a vault created in the same moment (from the levels still left), and one choice affects every vault created in that moment at once." That is a true statement of the SPEC 26 bound. The "about two minutes" for recording a draw is the common case; with the worst skip pattern C exists only at `reveal + 214` and the window closes at `+300`, about 35 seconds. INFO precision only.

## Transaction history (`bank/txread.mjs`)

Validation is fail-closed on shape, and the truncation marker is matched exactly (a program's own text would be prefixed "Program log:"). **One silent-loss path (LOW, F2):** `need(Array.isArray(meta.logMessages) && every string)` accepts an **empty** log array for a transaction that executed one of our programs. Every executed top-level instruction emits `Program <id> invoke [1]`, so an empty array for a non-empty instruction list is an RPC that did not return logs, not a transaction with none; the reader returns it as a complete, event-free transaction and a walking scanner advances its cursor past a redemption, reschedule or deferral without a `log_coverage_gap`. Whether any provider ever returns `[]` here I cannot measure; the fix is a one-line consistency requirement (an invoke line per top-level instruction, or refuse/flag), and it belongs beside the truncation flag.

1. **Run the real thing with real adversaries, not a validator.** Items 22 and 53 are the only evidence that will ever exist of the crank, the alarm, the revenue cycle and the pages against mainnet RPC behaviour (rate limits, `[]` logs, DAS lag, Phantom's actual message handling). Record what the pages said and what the alarm paged, signature by signature.

Have a second person read every "WRONG ON CHAIN" line.

Publish the guide only after the pages are live and someone outside the project has opened a vault through them and read every box aloud.
