## R1 — Custody: the pairing holds

I re-attacked the open/burn pairing at each shape the prompt names:

- **CPI wrappers.** SEAL's open walks only top-level instructions after `load_current_index_checked`; BURN's burn walks only top-level instructions before it. A CPI'd open is invisible to BURN (`NoPrecedingOpen`); a CPI'd burn is invisible to SEAL (`NoTerminalBurn`); and `retire_redeemed` demands stack height `TRANSACTION_LEVEL_STACK_HEIGHT + 1` *and* a top-level `burn_vault` for the same asset at account 0, so a wrapped burn dies at the retire CPI (`NotFromBurn`). WR.1–WR.4 measure all three shapes and the vault's survival.
- **Two vaults, one transaction.** `[open A, sweep A, burn A, open B, sweep B, burn B]` pairs correctly; the rate limit refuses the second at a cap of one (4.9, 4.10a). Cross-paired `[open A, burn B]` fails (`NoTerminalBurn`, 4.10). Owner mismatch fails (3.10).
- **Account-index binding.** Both programs bind asset at index 0 and owner at index 2 of the other's instruction; the discriminators are name-derived, so a reorder keeps the discriminator and breaks the match — which refuses the thaw (fails closed, never leaks). The suite pins the discriminators and indices (3.1a–f, 3.1q–s).
- **A thawed vault never leaves a transaction unburned.** Open requires the matching burn later in the same transaction; a failed burn reverts the thaw atomically. No other instruction calls `set_frozen`.
- **Emptiness proof.** The reserve loop requires every reserve mint's ATA under both token programs declared, PDA-owned, undelegated (three byte ranges), extension-free (exactly 165), and empty; a non-token or sub-165 account at the address is skipped (the dust rule, R34.G2/R40). The second loop applies the same checks to any declared token account owned by the PDA and refuses a declared live `AssetV1` (`VaultStillHoldsAVault`). A Token-2022 account with extensions is refused (`ReserveHasExtensions`); a plain 165-byte Token-2022 account owned by the PDA must be empty. Undeclared holdings are destroyed — that is accepted limit 44, not a new finding.

## R2 / R2b — The pool invariant and the boost hold

**Invariant "pool ≥ ceil(owed)".** I re-derived every transition: `split_revenue` adds to the balance with owed unchanged; `credit` adds `delta*w ≤ avail*SCALE` to owed, so `ceil(owed)` grows by at most `avail`; `claim` moves `pay` sats and `pay*SCALE` owed together (`ceil` falls by exactly `pay`); `retire` subtracts the vault's whole pending from owed with the balance unchanged (the invariant only grows); `monthly_inline` is `credit`. `distribute`'s `PoolShort` is unreachable defense. P.32 asserts it; the BK.* arms assert the books after every money operation.

**Counters.** `pending_count`/`pending_this_epoch` move together on request, join, and retire (including the same-epoch retire case, F21.1/F21.2). `waiting_to_join = pending_count - pending_this_epoch` can only be positive for a vault from an earlier epoch, which anyone can join free — so the `JoinWaitingFirst` gate cannot be held shut by a griefer (a request in the current epoch is not "waiting"). `BoostsExpireFirst` is clearable by anyone free via `expire_boosts`, which needs only records — never a token account — so a vault whose account is gone cannot hold distributions shut.

**Boost exactness.** A boost bought in epoch `e` with `n` epochs ends at `e+n`, earns the distributions at `e+1..e+n` (exactly `n`; BO.21 and the reverse-order BO.35 pin both placements), becomes due when `advance_epoch` moves `dist_epoch` to `end`, and must be expired before the next distribution. `reweigh` moves owed to `carry` and restarts debt at the new weight, so nothing is gained or lost across a weight change (BO.7c, BO.14, BO.37). The ring: `n ≤ 63 = BOOST_RING - 1` and the due gate together guarantee no two live boosts share a slot; `unschedule_boost`'s due and not-due branches are both exercised on chain at a wrapped index (BO.34/BO.38) and the host tests drive 260 epochs through the program's own functions against a model. `total_active_weight`, `boost_weight_total`, `boosts_active`, `boosts_due` and the ring are asserted to agree after every operation.

## Findings

**INFO-1 (fixable layer, web/; outside (a)–(d)).** `web/src/lib/plan-redeem.mjs`, the reserve-account check refuses a frozen reserve account only when it holds a balance (`t.state === TOKEN_FROZEN && t.amount > 0n`). A frozen reserve account with a *zero* balance on an *active, owed* vault (pool unfrozen) is not refused by the page; the plan then carries a `claim` that pays into the frozen account, and the SPL transfer reverts the whole redemption. The dry run catches it and the page refuses with the generic dry-run message rather than its specific "Coinbase has frozen your vault's account" message. *What an attacker or accident gains:* nothing — the redemption is refused either way, nothing moves, and the holder waits for the unfreeze exactly as item 28 states. *Evidence if true:* a snapshot with a frozen, zero-balance cbBTC vault account, an active record with `owed > 0`, and an unfrozen pool produces no plan refusal and a redemption whose first instruction is the claim; simulating it fails at the claim's transfer (SPL `0x11`). *Fix:* refuse a frozen reserve account when the vault is owed a payout (keep allowing the frozen-empty, owed-nothing case, which the helper closes). INFO because the outcome is identical and item 28 states the block; only the message differs.

**INFO-2 (fixable layer, tooling; outside (a)–(d)).** The name `judgeRehearsal` is shared by two different gates: `scripts/check-launch-params.mjs`'s rehearsal mode (which, per SPEC 53, handles REHEARSAL-OPEN and REHEARSAL-NA statuses) and `web/src/lib/plan-ceremony.mjs`'s bounds check, which refuses *any* null value — including the rehearsal file's REHEARSAL-NA `lock_deadline`. *What an attacker or accident gains:* nothing; the page's copy is unreachable with the rehearsal file because the rehearsal profile refuses earlier (`launchValues: null` → preflight stops before `judgeRehearsal` is called), and the localnet profile's harness sets `lock_deadline`. *Evidence if true:* `web/src/pages/ceremony.mjs` preflight returns null when `launchJson()` is null, before `judgeValues` runs; the rehearsal profile's `launchValues` is null. *Fix:* rename one, or have the page's copy treat REHEARSAL-NA as absent-by-design. INFO because it is unreachable today and is a reading hazard in a project whose most repeated defect is a comment or name asserting a control that is not the one that runs.
