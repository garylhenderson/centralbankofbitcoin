## R5. The swap (`bank/swap.mjs`, `bank/revenue.mjs`)

**(a) Oracle math.** Correct. The formula `sats = lamports * sol.price * 10^(sol.expo - btc.expo) / (btc.price * 10)` is implemented with BigInt. The exponent handling is correct for both signs. The `satsPerLamport` float is only used for the deviation check; the actual floor uses BigInt. The `PYTH_EXPO_MIN/MAX` bounds (−18 to 0) prevent pathological exponents. The `minSats <= 0n` check catches dust.

**(b) Pyth verification.** Correct. Ownership check (`PYTH.receiver`), feed ID check, full verification level check (level 1), staleness (180s), future-dated (30s), confidence (30 bps). The account is a PDA under the push oracle, owned by the receiver. Only the receiver can write to it, and it verifies Wormhole signatures. An attacker cannot write arbitrary data. The clock is the chain's Clock sysvar, not the box clock.

**(c) Deviation filter.** Correct. `orcaSpot` computes `(sqrtPrice / 2^64)^2` which is the raw price in cbBTC base per wSOL base, matching `satsPerLamport` from the oracle. `meteoraSpot` computes `1 / (1 + binStep/10000)^activeId` which is sats per lamport (inverse of the DLMM's Y-per-X price). The 100 bps threshold is correct. Float precision is sufficient for the deviation check.

**(d) Minimum out.** Correct. `minSats` from `oracleFloor` is used as `other_amount_threshold` (Orca) and `min_amount_out` (Meteora), both in output token base units (sats). The 150 bps tolerance is correct.

**(e) The judge.** Correct for its stated scope. It checks the exact 7-instruction sequence, amounts, floor, programs, signers, and key positions. It does NOT check Meteora's `host_fee_in` (key 9) or the tick/bin arrays, but the venue programs validate those. The judge and builder are in the same file, so a compromised builder compromises the judge too — this is accepted limit 10(c). The post-swap delta check in `revenue.mjs` provides a second layer.

**(f) Account derivation.** Correct. Orca tick arrays: current and two below (a_to_b swap moves price down). Meteora bin arrays: current and two above (Y-to-X swap moves active bin up). The `orcaTickArrayStarts` and `meteoraBinArrayIndexes` functions are correct. The PDAs are derived correctly.

**(g) wSOL handling.** Correct. Wraps exactly `lamportsIn`, syncs, swaps (using `lamportsIn` as the exact input amount, not the full balance), closes. If the wSOL ATA has an existing balance, the swap uses only `lamportsIn` and CloseAccount returns the rest. A frozen wSOL ATA would cause the transaction to revert (acceptable). A delegate doesn't affect the swap.

**(h) Failure and retry.** Correct. `classifySendFailure` distinguishes refused (safe to try next venue), landed (record and continue), and unknown (stop, leave cycle open). A confirmation timeout on a landing transaction is classified as `landed` (if status shows success) or `unknown` (if status lookup fails). The cycle stays open until a cbBTC return is proven on chain.

**(i) Adversary extraction.** Bounded. With 100 bps deviation gate and 150 bps floor, the worst case is 100 bps loss per swap (pool at the edge of the deviation gate). With 10 SOL cap and 6-hour cooldown, that's ~0.1 SOL per cycle, ~0.4 SOL/day, ~12 SOL/month. A stale oracle (180s) is bounded by the confidence check (30 bps). A manipulated Meteora pool (~10× thinner) is bounded by the same deviation gate. The cycle size (≤10 SOL) makes this immaterial relative to the pool.

**Operator key worst case:** The key can take up to `max_sweep_lamports` per `sweep_cooldown_secs` until the guardian stops it. With launch values (10 SOL / 6 hours), that's ~40 SOL/day. The alarm reports sweeps. The key cannot touch cbBTC, the pool, or vaults.

**Ledger integrity:** `cycleIsOpen` correctly requires both return AND split. `closesCycle` correctly anchors on the return's block time. The `detectUnreconciledRevenue` and `detectSplitClaims` detectors hold the ledger to the chain. A failed cycle cannot read as closed.
