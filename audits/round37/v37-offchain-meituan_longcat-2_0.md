## R5. The swap (`bank/swap.mjs`) and the revenue cycle (`bank/revenue.mjs`) — no new defect

I verified:

**(a) The oracle math.** `oracleFloor` computes `sats = lamports * SOL_USD / (BTC_USD * 10)` with the exponent handled correctly: `e = sol.expo - btc.expo`; if `e >= 0`, `num *= 10^e`, else `den *= 10^(-e)`. The derivation: `cbBTC_sats_per_lamport = (lamports / 1e9) * (SOL_USD) / (BTC_USD) * 1e8 = lamports * SOL_USD / (BTC_USD * 10)`. The `satsPerLamport` is `Number(sol.price) * 10 ** sol.expo / (Number(btc.price) * 10 ** btc.expo) / 10`, which is the same quantity in floating point. The floor is `expectedSats * (10000 - SWAP_TOLERANCE_BPS) / 10000`, rounded down to whole sats. The confidence check `p.conf * 10000 > p.price * 30` is `conf / price > 0.3%`. The age check `nowSec - publishTime > 180` rejects stale prices. The future check `publishTime - nowSec > 30` rejects future-dated prices. All correct.

**(b) Pyth account verification.** `readPyth` checks ownership by `PYTH.receiver`, requires `verification_level === 1` (Full), reads the feed ID at the correct offset (bytes 41-72 after the 8-byte discriminator, 32-byte write authority, and 1-byte verification level), and compares it to the expected feed. The price, confidence, exponent, and publish time are read at the correct offsets (73, 81, 89, 93). The account address is derived via `pythAccount` (PDA of the push-oracle program, shard 0). Ownership by the receiver program is sufficient: only the receiver creates price accounts.

**(c) The deviation filter.** `orcaSpot(w) = (sqrtPrice / 2^64)^2` is cbBTC sats per lamport (Orca's sqrt_price is in raw smallest units). `meteoraSpot(p) = 1 / (1 + binStep/10000)^activeId` is cbBTC sats per lamport (Meteora's price is in raw units). `f.satsPerLamport` is cbBTC sats per lamport. All three are in the same units. `deviationBps(pool, oracle) = Math.abs(pool - oracle) / oracle * 10000`. A pool more than 100 bps from the oracle is skipped. The floating-point precision loss for realistic prices (sqrtPrice ≈ 2^57.6) is negligible relative to the 1% tolerance.

**(d) The minimum out.** Orca's `other_amount_threshold` and Meteora's `min_amount_out` are both set to `minSats` (the oracle floor). The judge checks `d.readBigUInt64LE(16) !== floor` for both venues. Correct.

**(e) The judge.** `judgeSwapInstructions` requires the exact seven-instruction sequence `swapInstructions` builds: SetComputeUnitLimit(400000) with no other budget instruction; CreateIdempotent for the operator's own wSOL ATA; System transfer of exactly `lamportsIn` from the operator to its own wSOL ATA; SyncNative of that ATA; CreateIdempotent for the operator's own cbBTC ATA; the venue's swap with the operator's wSOL in and cbBTC out at the pinned positions, amount `lamportsIn`, threshold `minSats`, and for Orca exact-input, a_to_b, at the minimum sqrt-price limit; CloseAccount of the wSOL ATA back to the operator. It checks allowed programs, one signer, no priority fee, Token instructions limited to SyncNative and CloseAccount, the swap's amount and floor, the swap's input/output accounts, and the swap's signer. A tampered builder that misroutes the output or drops the floor is caught after signing by `revenue.mjs`'s post-swap delta check (`delta < guaranteed` throws, cycle stays open). The judge catches builder defects; it cannot catch a tampered module (accepted limit 10(c)).

**(f) Account derivation.** Orca: tick arrays derived from pool and start (`orcaTickArrayStarts` + `orcaTickArray`), oracle PDA derived from pool, vault A/B read from the pool. Meteora: bin arrays derived from pool and index (`meteoraBinArrayIndexes` + `meteoraBinArray`), bitmap extension derived from pool (passed as program id if absent), `host_fee_in` as None, event authority derived, two token programs passed. The judge does not verify tick/bin arrays or the oracle; these are read-only accounts the pool program validates. Correct.

**(g) wSOL handling.** CreateIdempotent (idempotent if the ATA already exists), transfer exactly `lamportsIn`, SyncNative, swap, Close. If the ATA already holds a balance, the transfer adds to it, SyncNative converts the whole balance, the swap uses what it needs, and Close returns any remainder. Correct.

**(h) Failure and retry.** Orca first; Meteora only if Orca's program refuses (a program error or a failed preflight). An unconfirmed send is not a refusal: `classifySendFailure` reads the signature's status, and only a landed-and-failed or expired-and-absent signature is a refusal. A landed-and-succeeded signature is recorded. An unknown status stops the cycle, open and loud. The ledger cannot read a failed cycle as closed: `cycleIsOpen` returns false only for a cycle with a landed sweep AND a recorded split (or a provably empty revenue ATA). Correct.

**(i) What an adversary can extract.** The 100 bps deviation gate and 150 bps floor bound the per-swap loss to 150 bps of the input. With a 10 SOL cap and a 6-hour cooldown, that is 0.15 SOL per sweep, 0.6 SOL per day. The operator key's worst case is the cap times the number of cooldown windows until the guardian stops it (accepted limit 10). The thinner Meteora pool can be pushed to the edge of the gate but not past it; the floor still bounds the loss. No new extractable value beyond the accepted limits.
