## R1 — Custody: can anyone but the owner get value out of a sealed vault?

I attacked the pairing (CPI wrappers, two vaults per transaction, cross‑pairing, account‑index binding, sysvar parsing) and the emptiness proof (delegates, close authorities, T22 extensions, lamports, nested assets, declared‑but‑foreign accounts). **I found no defect.**

- The pairing binds asset **and** owner in both directions over **top‑level** instructions only; a wrapper needs a genuine top‑level burn/open for the exact pair, and each half independently refuses the borrowed half (WR.1–WR.4 measured; the code is unchanged here). `[open A, burn B]`, `[open A, open B, burn B, burn A]`, `[wrapper, real burn]` and `[real open, wrapper]` all fail closed.
- The emptiness proof's raw offsets are correct (delegate tag 72..76, delegated amount 121..129, close‑authority tag 129..133 — I recomputed these against the 165‑byte SPL layout; earlier rounds had a wrong‑offset class here and these are right). The T22 ATA derivation can never exist for a classic mint (round 25 W1, measured on mainnet), so that leg is defence in depth that always skips.
- A thawed vault cannot leave a transaction unburned: the thaw reverts with any later failure, and SEAL's walk requires the burn for the same asset+owner later in the same transaction.
- The seal plugin's authority is SEAL's off‑curve PDA; no instruction in any of our five programs signs it except `open_for_redemption`, and Core refuses plugin removal (permanent plugins are create‑only).

## R1s — The sweep helper

**(a) Owner-only.** Direct calls need the asset‑signer PDA's signature, which only Core provides; through Core, the pinned binary approves Execute only for `authority == owner` (SR.5/SR.5a/SR.5c refuse stranger, owner‑added transfer delegate, and a keypair collection update authority, all `0x1a` from Core, with the vault's balances preserved — SR.5e). While still frozen, Core rejects the Execute itself (3.7, with the decoded‑state read distinguishing 0x9‑frozen from 0x1a‑non‑owner). The one plugin route that could approve someone else (AgentIdentity + ExecutionDelegateRecord) cannot be added by an owner (R24.1a) and needs the collection update authority, which is MINT's off‑curve PDA (SR.5b). Sound today; the residual is Core's upgrade key (limit 40).

**(b) Pair list.** Same source twice: the first pair closes it, the second `read_token` fails on the system‑owned closed account → whole redemption reverts (SR.12a). Source==destination: impossible (owners must differ; `signer == dest` refused). wSOL source: transfer‑then‑close is the standard unwrap; a stranger‑planted wSOL account is unnamed‑and‑destroyed or swept‑if‑named, same as any stray classic account. Delegate/close‑authority on a source: cannot be set by a stranger (Approve/SetCloseAuthority need the PDA's signature, blocked by the seal). Frozen source: the token program refuses, redemption reverts (SR.14, limit 28). Odd count: `NotEnoughAccountKeys` (SR.7). Zero pairs: the lamports‑only sweep lands (SR.13). Destination = another vault's asset‑signer: possible, but only the *owner* can choose it, and it is their own value.

**(c) Destination checks.** Not compared to the asset owner — correctly, because (a) makes the owner the only signer; a hostile page with the owner's signature could move value with plain SPL instructions anyway (round 25 W2, correctly rejected). A lamport transfer to a non‑existent destination below rent is refused and blocks the redemption (documented, item 50/D9); to an existing non‑system account it succeeds.

**(d) Lamport sweep.** `signer.lamports()` is read at execution, after the pair loop (which cannot change the PDA's lamports — closes credit `dest`). Nothing can deposit between the sweep and the burn inside one atomic transaction; a stranger's deposit lands in another transaction, before or after the whole redemption. BURN's `lamports == 0` sees exactly what the sweep left plus whatever the owner's own later instructions did.

**(e) Emptiness interaction.** A closed reserve account is system‑owned, so BURN's reserve loop skips it — it passes *for the right reason* (it no longer exists). The prior‑transaction step (creating missing reserve ATAs) is sufficient for the classic case because the sweep moves **live** balances, so dust landing between the prior transaction and the redemption is swept. The accounts a stranger can plant that the sweep cannot name and BURN will not skip‑if‑declared are exactly the documented ones: Token‑2022 accounts (the helper reads only classic 165‑byte accounts; a T22 account *for a T22 mint* owned by the PDA can be created by anyone) and nested Core assets — both destroyed if undeclared, both blocking if declared (limit 44). I found no new member of that class.

**(f) Fit.** S8.0's 1,061 bytes includes claim + open + the ExecuteV1 (with all pair accounts in its account list) + burn, owner as fee payer; +52 (compute‑budget pair) +96 (separate payer) = ~1,209 of 1,232. A fourth pair (~66 bytes of accounts plus inner‑instruction data) does **not** fit — correctly disclosed as "not an upper bound for arbitrary extra token pairs" (a stray‑token rescue needs the prior transaction or a v0). The in‑line monthly run's accounts are already in the measured shape (claim and burn both carry the pool).

**(g) Evidence.** SR.0–SR.5e, S8.* exist, can fail, and are pinned to the failing program. The helper's suite‑deployed bytes are the bytes `build-mainnet.sh` proves (cmp against `target/deploy`, N6). The `localnet`‑feature removal that guarantees byte identity is in `Cargo.toml`.

## R2 — The pool

I re‑derived the invariant **pool ≥ ceil(owed)** through `credit` (delta·w ≤ avail·1e12, so ceil grows by ≤ avail), `claim` (floor‑pay, subtract exactly pay·1e12), `retire` (owed falls, balance unchanged), `reweigh`/`expire_boost` (owed_of preserved by construction: carry = old owed, debt = new weight·acc), and `join` (owed_of = 0 at entry). ## R2b — The boost

A boost bought at epoch e with N distributions earns exactly the distributions credited at dist_epoch = e…e+N−1 and becomes due at e+N (BO.21/BO.21a/BO.35/BO.35a pin both orderings). The ring's exclusivity holds because live end‑epochs always occupy a 63‑value window (max N = 63 < 64), so two live boosts never share a slot; a due‑but‑unexpired boost lives in `boosts_due`, not the ring, so a new boost scheduling the same slot cannot double‑count. `unschedule_boost`'s two branches match `dist_epoch >= boost_end_epoch` exactly. The host test's independent model plus BO.16/BO.17/BO.34/BO.38 cover early retirement, due retirement, wrap, and expiry through the program's own functions. Nothing earned is lost or gained on a weight change (the carry identity). No record can be expired twice (`boost_weight == 0` skip), early (`BoostNotDue` require), or never (the gate plus free permissionless expiry). Nobody can block distributions by boosting (expiry needs only records, not token accounts — `expire_boosts` exists precisely so a gone token account can't wedge the gate).

## R4 — Governance

**F2 [LOW] — `apply_guardian` / `apply_swap_operator` have no expiry.**
- **Construct:** MINT `apply_guardian` / `apply_swap_operator` — the only bound is `now >= pending_at + notice_secs`. Contrast `execute_proposal`'s `ProposalExpired` (7 days), which exists precisely because round 6 found a ratified decision held undetonated is "a grenade with the pin out".
- **What an attacker gains:** the *latest* ratified key change can be landed at any arbitrarily later moment by anyone. For a swap operator the guardian can cancel it; for a guardian there is no cancel (by design). The decision was validly ratified and the notice ran, so this is decision staleness, not an authority bypass — the hostile‑guardian consequence once landed is already limit 47, and the early‑small‑electorate concentration that could arm one is already DESIGN §10. The delay adds no new capability (an immediately‑applied hostile guardian is equally hard to replace once supply grows); what it adds is the *timing* being chosen by the applier years after the vote.
- **Evidence if I am right:** no `now <=` anywhere in either apply; `arm_guardian` replaces the pending key (so only the latest arm is live) but nothing ever expires it.
- **Fix:** refuse the apply after `pending_at + notice_secs + EXECUTION_WINDOW_SECS`, or write the unbounded apply into limits 34/47 as a stated consequence.

Otherwise: the electorate is fixed at creation (`index_snapshot`, live `quorum_supply`); the 10% turnout and the half‑of‑snapshot key‑change bar are ceiling‑divided and checked at execute; the two key changes can never share a proposal; `TightenSweep` is monotone and bounded at both creation and execution; overtaken actions are logged skips. A minority cannot carry anything I can construct: quorum+threshold+turnout all bind against the snapshot, and the snapshot can only shrink (burns), never grow mid‑vote. Governance cannot be frozen forever except via the documented paths (45: all vaults redeemed and supply exhausted; 47: sub‑half turnout on a guardian replacement).
