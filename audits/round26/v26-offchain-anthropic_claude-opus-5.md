## R5 / R0 findings

### F1 — LOW. Nothing establishes that a swap *can land* before the SOL leaves the revenue address, and the tick/bin arrays are passed without checking they exist

**Construct.** `bank/swap.mjs` `orcaSwapIx` / `meteoraSwapIx` pass three derived addresses each (`orcaTickArrayStarts` → `orcaTickArray`; `meteoraBinArrayIndexes` → `meteoraBinArray`). `market()` reads only the two pools, two Pyth accounts, the Meteora bitmap and the Clock — never the arrays. `bank/revenue.mjs` sweeps on the strength of `m1.venues.length > 0`, which is a price-band read only.

**What an accident gains.** Orca's `Swap` declares `tick_array_0/1/2` as `AccountLoader<'info, TickArray>` with `has_one = whirlpool`, so Anchor's account validation deserializes all three *before* the handler runs; the handler's `load_mut().ok()` on arrays 1 and 2 exists to tolerate the *same* address being passed twice (a double mutable borrow), which is exactly how the Orca SDK handles sparse liquidity: it repeats the last initialized array. Meteora's `swap` loads every remaining account as a `BinArray` and validates it against `lb_pair`. So if either of the two tick arrays *below* the current tick, or either of the two bin arrays *above* the active bin, is uninitialized, the pool program refuses the swap we built. Because this is only discovered *after* `sweep_sol_for_swap` has landed, the consequence is the exact scenario item 22 plans to rehearse: royalty SOL stranded on the operator key, `unreconciled_swap` CRITICAL, the hourly job wedged at the open-cycle guard, and a hand recovery. If both venues are affected at once there is no automatic path at all.

**Evidence that would exist if I am right.** (i) On mainnet today, `getMultipleAccountsInfo` on `orcaTickArrayStarts(w.tickCurrent, w.tickSpacing).map(orcaTickArray)` returns three live accounts (which is why SW.1 passes — note `sim/swap-fork.mjs plan()` clones only accounts that exist, so the fork faithfully reproduces absence). (ii) Simulate the same instruction with `tick_array_2` replaced by any unallocated address: the simulation fails with Anchor `AccountNotInitialized` (3012) / `AccountOwnedByWrongProgram` (3007) at instruction 5, **not** with a slippage error. (iii) The same substitution for a Meteora bin array fails in `load_bin_arrays`. If (ii) instead succeeds, this finding is wrong and only the pre-sweep feasibility half stands.

**Fix.** In `market()`, read the three Orca tick arrays and three Meteora bin arrays in the same `getMultipleAccountsInfo`; pass the array holding the current tick/active bin in place of any uninitialized successor (what the Orca SDK does — the program's `.ok()` already tolerates repeats), and drop a venue from `venues` if the array holding the current tick itself is missing. Note honestly in limit 10 that a *full* pre-sweep simulation is impossible (the operator does not yet hold `lamportsIn`, so the wrap would fail simulation), so an account-existence check is the available substitute.

### F2 — LOW. Two of the four value-moving sends are not classified, and a cycle keeps no record of a signature it attempted

**Construct.** `bank/revenue.mjs` routes only the sweep and the swap through `SW.classifySendFailure`. The **return** (`createTransferChecked` into the revenue ATA) and the **split** are bare `await sendAndConfirmTransaction`. Separately, on the swap's refusal path only `verdict.why` and `e.message.slice(0,140)` reach `cycle.swapFailure`; no attempted signature is stored.

**What an accident gains.** (a) A confirmation timeout on a **return that landed** throws before `cycle.returnedSats` is written. The cycle is then open with `swapSig` set and no return; the `returnedUnsplit` recovery only considers rows with `returnedSats > 0`, so nothing automatic can close it, and the alarm pages `unreconciled_swap` CRITICAL whose text asserts "NO cbBTC came back" — which is false, the cbBTC is in the revenue ATA. (b) On the `!st && expired` branch, `getSignatureStatuses` returning null for a transaction that in fact landed in the final valid block declares a refusal; for the swap that means Meteora is tried next. With an operator holding only the cycle's funds the second wrap fails (insufficient lamports) and the cycle stays open — but the ledger then holds **no signature at all** for the swap that did land, which contradicts limit 10's hand-recovery runbook ("look up the recorded `swapSig` (if any)"). With a float larger than the ruled instruction, the second swap can succeed and sell the operator's own SOL.

**Evidence that would exist if I am right.** For (a): a cycle row carrying `swapSig` and `swapVenue` but no `returnedSats`, with the revenue cbBTC ATA already holding the swap's output and the operator's cbBTC back at `operatorSatsBefore`; `--audit` lists it as unaccounted and `detectUnreconciledRevenue` emits `unreconciled_swap` with the "NO cbBTC came back" wording. For (b): a `swapFailure` string containing `its blockhash expired and it never landed` beside a confirmed, successful swap signature on chain that no ledger field names.

**Fix.** (1) Record every attempted signature on the row (`attemptedSigs: [{venue, sig, verdict}]`) before judging it, so the runbook always has something to look up. (2) On `expired` with a null status, re-poll once after a short delay (or require two consecutive nulls) before returning `refused`. (3) Classify the return and the split too, and extend the recovery to the closable case: `swapSig` present, `returnSig` absent, operator cbBTC back at `operatorSatsBefore`, revenue ATA credited by ≥ `floorSats` since `swapSig`'s block time ⇒ fill `returnedSats`/`returnBlockTime` from chain and carry on.

### R5(i) — what an adversary can extract within the tolerance (no finding; bound stated)

Per cycle the on-chain guarantee is `expectedSats × (1 − 150 bps)`, i.e. at most **0.15 SOL (~$18 at the measured price) of a 10 SOL cycle**, and at full ruled throughput (4 cycles/day) at most **~0.6 SOL/day, ~18 SOL/month**. A sandwich cannot realise that: to move Orca's 0.16%-fee, ~$10M pool 1.5% a sandwicher must round-trip six figures and pay ~0.32% on it, against an $18 prize; Meteora (~10× thinner) is ~$15k against $18 at a higher variable fee. The practical extractor is a *standing* adverse pool state inside the 100 bps gate plus our own impact, which the fork measures at 10 SOL (SW.8/SW.9). I consider the stated bound honest; the only number I would add to limit 10 is the monthly figure, because "150 bps" reads smaller than "up to ~18 SOL a month of royalty revenue".

## R1. The crank

### F3 — MEDIUM. The reveal lane's capture throughput is an order of magnitude below a plausible mint rate, so a fast sale lapses draw windows at scale

**Construct.** `bank/crank.mjs` `main()`: `for (const a of plan.capture) await run(...)` — one `capture_entropy` per transaction, each `await sendAndConfirmTransaction(..., 'confirmed')`, serially, under `flock -n` on `crank-reveal.flock` so an over-running pass causes every following minute to skip silently (limit 6).

**What an accident gains.** The usable window is `reveal_slot + ~16` (readySlot walks two 4-slot groups) to `reveal_slot + 300`, i.e. **~114 s**. At 1.5–3 s per confirmed send the lane clears roughly **20–40 captures/minute**, so a sustained mint rate above that leaves a growing backlog whose tail lapses. A 2,100-cap round — which SPEC itself warns one ordinary vote can open at the 21,000-sat floor — selling out in ten minutes is 210 mints/minute, five to ten times the lane's capacity. Consequences, in order of seriousness: every lapsed vault is **rescheduled to a fresh future slot**, which is exactly the re-roll of accepted limit 25 and, more importantly, hands limit 26's validator-grinding attack far more targets than "one re-roll per full window of silence" implies (a reschedule re-targets a slot a validator can aim at its own rotation); the FIFO cannot pass an uncaptured head, so reveals — and therefore `activate`, and therefore every holder's earnings — stall behind the churn; and `reveal_rescheduled` pages HIGH/URGENT per lapse, which is the loud direction but tells the operator nothing they can do at the time. Nothing in the crank, item 50 or item 54 requires the mint page to carry piggyback captures, and item 54 explicitly permits a page that "cannot rely on the wallet keeping its compute-budget instruction" to send **no** crank.

**Evidence that would exist if I am right.** In a rehearsal that mints faster than ~40/minute: `bank/.crank-reveal.lock` held across consecutive minutes with `ELOCKED` skips in `crank-reveal.log`; a `plan.capture` length that grows pass over pass; `CBOB_REVEAL_RESCHEDULED` log lines and `reveal_rescheduled` findings in proportion to (mint rate − lane rate); `reschedules` > 0 on a large fraction of `VaultRecord`s; and `revealed_total` advancing far slower than `minted_total`. Timing the lane directly (`time node bank/crank.mjs --reveal-only --live` against N due captures) gives the rate.

**Fix (cheap, and inside the mutable off-chain tree).** (1) Batch captures: `capture_entropy` costs 114,756 CU (item 54) and 2 accounts, so **10 per transaction** with an explicit `setComputeUnitLimit(1_200_000)` is ~1.15 M CU and a few hundred bytes — a 10× improvement with no program change. (2) Send independent capture transactions with bounded concurrency (8–10 in flight); captures are order-independent and every refusal is already in `BENIGN`, so a race cannot double-spend anything. Keep reveals serial and ordered. (3) Add to item 50's client list: the mint and charter pages SHOULD carry up to `MAX_CRANK` queued records with a CU limit, and the sale page must not be allowed to ship without it if the round cap is large.

**What I checked and did not find in the crank.** Every instruction's account list and mutability matches the Rust (`distribute`'s read-only pool, `split_revenue`'s read-only config, `claim`'s `crank_n = 0` → `k = 0`, `expire_boosts`' batch of 20 ≤ `MAX_EXPIRE_BATCH` 30). The planner's post-state arithmetic agrees with MINT instruction for instruction: `w = total_active_weight + preJoinWeight − retiringWeight − expiringWeight` matches `join`/`retire`/`reweigh`; `owedAfterRetire` matches `retire` freeing `owed_of` before `credit`; the `tick` branch's `pending_this_epoch − retiringThisEpoch` matches `NoActiveVaults`; `monthly_inline`'s `WAITS_FOR_JOINS` early return means the join batches cannot fire the in-line month ahead of the explicit `distribute`; `revealAttrSource` and `judgeRevealAttrs` match `AttributesMismatch` and the burned-asset skip; `attrsBorsh`/`attrsHash` reproduce `hashv(&[&Vec<VaultAttribute>.try_to_vec()])` including the program-appended `charter` at the tail. The planner never joins or pays a non-`'live'` asset, never plans a reveal out of `revealed_total` order, and sends no instruction that is not permissionless and destination-pinned.

## R2. The alarm

### F4 — MEDIUM. The alarm has every vault's owner on the wire each pass and watches none of it, so the leaked-custodial-key compromise the 2.1% cap exists for is undetected until redemptions begin

**Construct.** `bank/alarm.mjs` `listVaults()` already returns `all: [{id, owner, burnt}]` from DAS. `everyVault` is passed only to `detectNestedVaults`, which uses the owner for nesting and `isOnCurve` and discards it. `next` (the stored state) holds `vaults` as **ids only**; no detector, and no stored baseline, concerns itself with who owns what.

**What an attacker gains.** DESIGN-v6 §8 states the cap's purpose verbatim: "if Gary Club custodial wallet keys ever leak, a thief cannot empty them faster than we can move those vaults to fresh keys". Moving them requires *knowing*. A thief who transfers every custodial vault to their own wallet — unlimited, one transaction per batch, accepted limit 41 — produces **zero findings**. The first signal is `redemptions_near_cap` HIGH, which needs the thief to have begun redeeming and to have consumed 80% of a rolling hour's budget; by then ~36 of the first 45 vaults are already burned and their contents gone. The public-post alarm that was supposed to be the human-readable half (`bank/redemption-poster.mjs`) has no sender (item 50). So the one window in which the cap's premise can be acted on is the one window nothing watches.

**Evidence that would exist if I am right.** `grep -n "ownership\|\.owner" bank/alarm.mjs bank/detectors.mjs` shows the DAS owner reaching only `detectNestedVaults`; `state.json` after a pass contains `vaults: ["<id>", …]` with no owners; and a synthetic pass in which N vault owners change produces no CRITICAL/HIGH finding of any kind.

**Fix.** Store the DAS owners in state (≈2,100 × ~50 B, the same order as `balances`, already written every pass) and add one pure detector with a *rate* shape rather than a change shape, because resales are routine: page HIGH when more than `k` vaults change owner between two passes (e.g. `max(10, 2% of live)`), or when any single owner's share crosses a threshold (e.g. 10% of live). State the false-positive sources in the detector's own header: a marketplace listing sweep, a bulk transfer by Gary Club, and — importantly — **the remediation itself** (moving custodial vaults to fresh keys looks identical to the theft), so the operator expects the page when they act.

### F5 — LOW. Our own collection's update authority is not in the snapshot, while the Proof-of-Burn collection's is

**Construct.** `bank/layout.mjs` `collectionPluginsHash` starts hashing at `33 + name + uri + 8` — it deliberately skips `key(1) | update_authority(32)` so a mint's `num_minted` cannot page. `readConfigs` produces `collection.plugins_hash` only; `pob_collection.update_authority` is produced and watched at CRITICAL, `collection.update_authority` is produced nowhere and appears in neither `WATCH` nor `WATCHED_KEYS`.

**What an attacker gains.** Not much, today, which is why this is LOW: the CBOB collection's update authority is MINT's `["mint"]` PDA, and MINT's only Core CPIs are `CreateV2`, `AddCollectionPluginV1` (once, at `initialize`), `UpdatePluginV1` (the reveal) and `BurnV1`, so it cannot be reassigned while MINT is immutable. Pre-lock, an upgraded MINT could reassign it, and the *use* of a seized authority (adding an external plugin adapter Core consults on every `BurnV1` — the same brick class as accepted limit 46, but on **our** collection and therefore on every redemption) would change the plugin region and page `collection.plugins_hash` CRITICAL. So the gap is purely the warning *before* use, on the one account whose authority holders were told is a program PDA.

**Evidence.** `node -e` on the live collection shows bytes 1..33 differing from MINT's `["mint"]` PDA while every alarm pass reports clean; `grep "collection.update_authority" bank/` returns only `pob_collection.update_authority`.

**Fix.** Produce `collection.update_authority` in `readConfigs` exactly as the PoB one is (`acc.data[0] === 5`, bytes 1..33) and add it to `WATCH` at CRITICAL ("the CBOB collection's update authority — MINT's PDA, fixed forever"). One line each; `missingWatchedKeys` then guarantees a reader that forgets it turns the build red.

### F6 — LOW. The reconcile's level kinds are a stranger-triggerable daily CRITICAL that the ack system refuses to downgrade and that nothing ever closes

**Construct.** `reconcile()` calls `report(..., { fullPass: false })` and never writes state, so `sent.paged` is discarded: a level kind paged only by the daily reconcile (`undeclared_token_account`, `index_disagrees_with_chain`, `index_self_contradictory`) can **never** receive the `RECOVERY` that `planAlarmNotices` is built to send, because the 30-minute pass does not evaluate those kinds. Meanwhile `undeclared_token_account` is CRITICAL and is deliberately **not** in `ACKABLE_KINDS`, and `applyAcks` reports any attempt to ack it at full severity with an added "AN ACK FOR THIS FINDING EXISTS AND WAS REFUSED" line.

**What an attacker gains.** Anyone can create a token account owned by any vault's asset-signer PDA for ~0.00204 SOL and send it dust (proven impossibility 2; suite 9.7). That produces a CRITICAL every day, for ever, with no operator action that resolves it (the only resolution is that holder's eventual redemption sweeping it, per round 25 D7) and no way to silence it. For ~0.2 SOL a griefer plants 100 of them. The router bounds the delivery to roughly one e-mail a day on one stream, so this is noise rather than denial — but it is precisely the condition `detectors.mjs`' own header calls out: "A finding with no way to be answered is one that gets ignored", written above the mechanism that refuses to answer this one.

**Evidence.** Create a 165-byte Tokenkeg account for a vault PDA with 1 unit of any mint; `bank/alarm.mjs --reconcile` reports `undeclared_token_account` CRITICAL; an `acks.json` entry for it produces `ackRefused` at CRITICAL rather than INFO; and no pass ever emits `cbob-vault-alarm:undeclared_token_acct` with `RECOVERY`.

**Fix.** Either (a) make it one-shot per `(asset, account)` — keyed in state like `frozen`, paged at full severity when first seen and listed at INFO thereafter, which is the shape round 24 I5 already built for freezes — or (b) add it to `ACKABLE_KINDS` so a dated ack with a reason bounds it. (a) is better: it keeps the condition visible and stops the repetition without a mute. Separately, have `reconcile()` persist its `paged` kinds (merged, not overwriting the 30-minute pass's) so the recoveries it owes can be sent.

### F10 — INFO. The alarm pages that a proposal exists, never what it would do

`gov.proposal_count` drifting gives HIGH "A NEW PROPOSAL HAS BEEN OPENED" and nothing reads the proposal account's actions. Key changes are covered twice over (`swap_operator_armed` / `guardian_armed` CRITICAL plus a 7-day notice), so the uncovered cases are `SetRound` and `SetBoostTerms`, whose first signal is the post-execution `mint.round_id` / `mint.price` / `mint.cap` / `mint.boost_*` drift within 30 minutes. ## R4. The money arithmetic

**No finding.** `credit`, `pendingScaled`/`owed_of`, `ceilSats`, `available`, `reweigh`, `debtAtActivation` are line-for-line the Rust, including the order `weight·acc + carry − debt` (which is what makes a weight reduction impossible to express as a negative debt) and the claim settlement `carry = pending − pay·SCALE; debt = weight_now·acc`. The crank's three owed branches each match the program state at the moment its transaction runs: a pre-joined vault at `debt = w·acc_old`, an expired-boost vault at `atExpiry + levelWeight·(acc − acc_old)`, everything else at `owed_of`. Boost expiry ordering matches `BoostsExpireFirst` (`dist_epoch >= boost_end_epoch` before, `boost_end_epoch == dist_epoch + 1` after), retiring vaults are excluded from both expiry lists because `retire` unschedules the boost itself, and `expiringWeight` removes only the boost while `retiringWeight` removes level + boost. `cbob_mint`, `max_boost_weight`, `max_boost_epochs` are watched as fixed-forever at CRITICAL and `boosts_stalled` is armed in both directions.

## R6. The gates

### F7 — LOW. The launch gate routes only part of the ruled set through the alarm's production list, and SPEC item 38 claims all of it

**Construct.** `scripts/check-launch-params.mjs` `judgeLaunch` builds `cur` with 14 keys and runs `D.detectStandingRisks(cur, { production: true })`. The remaining ruled values — `max_supply`, `level_caps`, `charter_secs`, `max_boost_weight`, `max_boost_epochs`, `payment_mint`, `bank_treasury`, `reserve_mints`, `pob_root`, `pob_collection`, `cbob_mint` — are checked only by the local `PINS` table. For the pubkeys that is harmless (the same imported `D.*` constants), but `'2100'`, `'945,525,315,210,105'`, `'604800'`, `'12'`, `'24'` are **second copies** of literals that also live in `detectStandingRisks`' `want` list.

**What an accident gains.** SPEC item 38 says the gate passes "unless … every ruled value equals the alarm's production list (the same list, imported)". That is true of 14 of ~25 values. Since every `initialize` value is permanent and the alarm only reports a wrong one *after* it is written, the claim being wider than the mechanism is exactly the failure class item 38 exists to prevent. ### F8 — LOW. The rehearsal tree ships a cron installer that will seize the production crontab, and its own header understates what it patched

## GIVEN THAT NO HUMAN FIRM WILL EVER SEE THIS AND THE PROGRAMS WILL BE IMMUTABLE

Five things this process structurally cannot do, with what to do instead. I have ordered them by what I would refuse to launch without.

**1. Run the money, once, at full size, with the real clock. Nothing here has.** Item 22 is the single most load-bearing open item in the project, and my two MEDIUMs are both *throughput and detection* defects that no amount of reading finds, because they only appear under rate. Make the dress rehearsal a **load** rehearsal, not a smoke test: mint at the highest rate the sale page can actually produce (not one vault a minute), with the crank armed, and record (a) captures sent per minute, (b) `reschedules` per vault, (c) the lag between `minted_total` and `revealed_total`, (d) the wall-clock time of a full crank pass at 2,100 records, (e) the alarm's pass duration with that transaction volume. Publish those five numbers in SPEC. If (a) is below the mint rate, F3 is confirmed and the fix is a day's work; if the measured numbers say I am wrong, the record kills the finding permanently.

**2. Inject faults. An AI reads the happy path and the paths the author thought of.** Before the lock, deliberately break things on the rehearsal deployment and record what the pipeline did: point the RPC at a socket that accepts and never answers (times the 300 s stall for the alarm as well as the crank); delete `bank/state.json`; corrupt `revenue-ledger.json`; freeze a cloned cbBTC vault account; close a pool ATA; make Orca refuse by raising the floor; **delete a tick array from the fork's clone list** (that single run settles F1); kill the crank mid-pass holding the lock; let a split front-run the cycle. Each of these has a detector or a recovery written for it; not one has been *observed* firing on a live deployment. A gate that has only ever said OK is untested — the project's own rule, applied to the operational layer instead of the assertion layer.

**3. Have a second, adversarial implementation of the two numbers that decide money.** The payout accumulator and the oracle floor are mirrored once each, by the same author, in the same idiom, and the mirror is checked against the original by the author's own test. Have someone (or a model with no access to `bank/accrual.mjs` or `bank/swap.mjs`) write an independent calculator from SPEC alone — "given this config, these records and this pool balance, what is each vault owed, and what is the minimum out for N lamports?" — and diff it against both the mirror and a replay of the chain. A disagreement is a finding neither reader could have produced alone; agreement is the only evidence of the mirror that is not self-referential.

**4.
